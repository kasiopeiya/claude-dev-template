# auto-programmer

ボードの Ready に積まれた Issue を1件ずつ拾い、AI に実装させて PR にするツール。

読むのは、**このツールを自分の環境で動かす／別のリポジトリへ持っていく人が、何が起きるかと、どこを直せばよいかを知りたいとき**。

## 何をするか

`npm run auto-programmer` を1回打つと、次の順に進む。1件終えると 2 へ戻り、着手できる Issue が無ければ `pollIntervalMinutes` の時間だけ待って見直す。着手できない周が続いて `maxConsecutiveIdleWaits` 回待っても、まだ着手できなければ、放置のまま `gh` の呼び出しが積み上がらないよう自分で止まる（正常終了）。実装中に Ctrl+C で止めても、その1件の記録を残してから終わる。ただし claude のセッションが続けて失敗したら、カードを空振りで In progress へ送り続けないよう自分で止まる。

| 順  | すること                                                                                                                                                                                                                                                                                                                         | 担当                                      |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 1   | `gh` の認証と `claude` の有無の確認・AI 専用 clone の作成                                                                                                                                                                                                                                                                        | preflight                                 |
| 2   | 閉じ損ねた Issue を閉じる。衝突して止まった自分の PR があれば、Issue を選ぶ前にそれを解かせる（「衝突して止まった PR を解かせる」）。無ければ Ready・`ai-fixable`・自分が担当者の open Issue から着手できる1件を選ぶ。選んだ Issue のロックを取り、カードがまだ Ready かを引き直す（他のプロセスが着手中なら飛ばして次の候補へ） | このツール                                |
| 3   | 未コミットの変更を stash へ退避して clone をデフォルトブランチの最新へ戻し、トピックブランチを作り、依存を揃える                                                                                                                                                                                                                 | このツール                                |
| 4   | 選んだ Issue のカードを「In progress」へ動かす                                                                                                                                                                                                                                                                                   | このツール                                |
| 5   | Issue が open な sub-issue を持てば、子を Ready に載せて 13 へ飛ぶ。持たず `issue:checked` も無ければ、clone の中で `claude -p "/issue-check #<番号>"` を起動する                                                                                                                                                                | このツール・`.claude/skills/issue-check/` |
| 6   | やる必要があるかと、対応方針がポリシーに合うかを確かめ、判定をラベル・state・本文へ書き戻す。1つの PR に収まらず割れる Issue は、`/issue-split` で sub-issue に割る。初回の検査で、本文に新しい技術要素があれば、外部依存の制約も調べる                                                                                          | `/issue-check`                            |
| 7   | 6 で open な sub-issue ができていれば、子を Ready に載せる。続けて Issue のラベルと state を読み、子を載せたか止める理由があれば 13 へ飛ぶ                                                                                                                                                                                       | このツール                                |
| 8   | Issue から前回の `needs-human-check` を外し、clone の中で `claude -p "/auto-dev <番号>"` を起動する                                                                                                                                                                                                                              | `.claude/skills/auto-dev/`                |
| 9   | 実装・検証・コミット・push・PR 本文の差し替え                                                                                                                                                                                                                                                                                    | `/auto-dev`                               |
| 10  | push した commit の CI（`ci.workflowFile`）が終わるまで待つ                                                                                                                                                                                                                                                                      | このツール                                |
| 11  | CI が落ちていれば、clone の中で `claude -p "/auto-fix-ci <番号> <run ID>"` を起動し、10 へ戻る                                                                                                                                                                                                                                   | `.claude/skills/auto-fix-ci/`             |
| 12  | 落ちた原因を直し、コミット・push する                                                                                                                                                                                                                                                                                            | `/auto-fix-ci`                            |
| 13  | 予定した終わり方以外で終えていれば Issue に `needs-human-check` を付け、PR の URL・終了コード・CI の結果を記録ファイルへ1行追記する                                                                                                                                                                                              | このツール                                |

2 で「自分」とは、`gh` にログインしているアカウントを指す。複数人が同時に動かしても、担当者が1人なら同じ Issue を拾う台は1台だけになる。担当者の無い Issue は誰にも拾われないので、カードを Ready へ動かすときに実行する人を担当者にする。1つのアカウントで並べたプロセスどうしは、同じマシンなら Issue ごとのロックで取り合わない。別のマシンで同じアカウントを動かすと取り合う。

2 で「着手できる」とは、本文の `## ブロッカー` 節に並ぶ Issue が全部 closed であることを指す。着手できる Issue のうち、タイトル先頭の段番号（`/issue-deps` が書き込む）の小さい順、同じ段なら Issue 番号の小さい順に選ぶ。

2 で先に Issue を閉じるのは、自動マージされた PR の `Closes #N` が Issue を閉じないためである（`scripts/close-issues.mjs`）。読むのは、同じリポジトリのブランチから出て、作者が bot か書き込み権限を持つ人のマージ済み PR だけで、マージ後に一度 close されて開け直された Issue は閉じない。毎周閉じるので、回している間にマージされた PR の Issue も次の周で閉じ、それをブロッカーに持つ Issue を拾える。閉じられなくても、そのまま Issue を選びに進む。

5 と 7 で「子を Ready に載せる」とは、open な子をボードに載せ、Status を Ready にし、担当者を自分にすることを指す。載せた子は次の周から 2 で拾われる。親は実装せず、カードは In progress のまま残す。子を持つ親を実装すると、子と作業が二重になるためである。

載せるのは、次のどれにも当たらない子だけである。

- **自分以外の担当者がいる**：他人の担当を取り合わない
- **`ai-fixable` が無い・`needs-human-decision` か `ready-for-human` が付いた**：判断待ちや人間の作業の子を「着手してよい」Ready に置かない
- **カードが Todo・Ready 以外の列にある**：着手した後（In progress・In Review・Done）の子を Ready へ戻すと、同じ Issue をもう一度拾う。ボードに無い子は載せる
- **対象リポジトリ（`repository`）の外にある**：2 は対象リポジトリの Issue しか拾わないので、載せても拾われない

5 で `issue:checked` が付いていれば、6 を飛ばして 7 へ進む。監査の後に前提が崩れていれば、9 で `/auto-dev` が離脱する。

6 で外部依存の制約を調べるのは、`issue:checked` が無く、本文に出た外部の製品・サービス・ツールの名前が `docs/adr/`・`docs/design/`・各 `package.json` のどこにも無い Issue だけである。Plan を通らない Issue の前提の誤りを、実装の前に拾うためである。人間にまだ示していない制約のうち、対応方針を確実に実行できなくするものが見つかれば、判定は人間判断になり、7 で止まる。そうでない制約は、本文へ追記して監査を続ける。調べられなかったときは、Issue にコメントを残して監査を続ける。

7 で実装へ進まないのは、次のときだけである。`/issue-check` が「方針差し替え」に倒した Issue は、差し替わった本文のまま 8 へ進む。

- open な sub-issue ができた
- `issue:checked` が貼られていない（判定が書き戻されていない）
- `needs-human-decision` か `ready-for-human` が付いた
- `ai-fixable` が外れた
- close された

11 で直させるのは `ci.maxFixAttempts` 回までで、使い切っても落ちていれば Issue にコメントを残し、13 で `needs-human-check` を付けて次へ進む。キャンセルされた run・`ci.runWaitLimitMinutes` 分待っても終わらない run は、差分を直しても通らないので直させない。9 で `/auto-dev` が離脱したときは 10 へ進まない。

AI が触るのは **AI 専用 clone の中だけ**で、人間の作業ツリーには一切触れない。実行をローカルにしているのは、hook・Policy・SubAgent を含むこのリポジトリのハーネスがそのまま動き、実行時間の上限も無いためである。Projects の読み書きも、ローカルの `gh auth` をそのまま使えるため追加の認証情報を要しない。

## 衝突して止まった PR を解かせる

このツールは CI が通った時点で PR を手放す。その後、同じファイルを触る別の PR が先にマージされると、手放した PR は衝突したまま止まり、マージされない。止まった PR の Issue をブロッカーに持つ Issue も、それまで拾われない。そこで 2 で Issue を選ぶ前に、次の順で、止まった PR を1件ずつ解かせる。

1. 記録ファイルに URL が残る open な PR のうち、GitHub が衝突していると判定したもの（`mergeable` が `CONFLICTING`）を、PR 番号の小さい順に選ぶ。判定がまだ出ていない PR（`UNKNOWN`）は次の周に回す
2. 選んだ PR の Issue のロックを取り、PR と Issue を引き直す。次のどれかなら、ロックを外して飛ばす
   - もう衝突していない・PR がもう open ではない
   - PR の head が、記録の中でこのツールが最後に CI を待った commit と違う
   - Issue が閉じた・Issue に `needs-human-check` が付いた
3. PR の auto-merge が有効なら外し、記録の `isAutoMergeDisabled` を `true` にする
4. clone を、PR のブランチの、引き直しで確かめた commit へ切り替え（未コミットの変更は stash へ退避する）、依存を揃えて、clone の中で `claude -p "/auto-resolve-conflict <番号>"` を起動する。`/auto-resolve-conflict`（`.claude/skills/auto-resolve-conflict/`）は、デフォルトブランチを取り込んで衝突を解き、検査を通して push する
5. push された commit の CI を、10〜12 と同じく待って直させ、13 と同じく記録する。記録の行には `isConflictResolution: true` が付く

記録ファイルで見分けるのは、このツールが作った PR を見分ける手がかりが、それしか無いためである。PR はどれも `pipeline.yml` が作り、対話セッションも同じ形のブランチ名を使うので、作成者やブランチ名では見分けられない。人間が対話で作業中のブランチへ AI が push すると、人間の次の push が拒否される。記録ファイルはマシンごとにあるので、同じアカウントで別のマシンを動かしても、同じ PR を取り合わない。`UNKNOWN` を待たないのは、GitHub が判定を裏で計算するので、引いた瞬間にはまだ出ていないことがあるためである。

head を照らし合わせるのは、後から人間や別の仕組みが push したブランチは、もうこのツールの持ち物ではないからである。その中身を、権限確認を飛ばした無人セッションと `npm ci` で走らせない。確かめた後にリモートへ push が入っても、clone は確かめた commit から始めるので取り込まず、push はリモートに拒否される。`needs-human-check` が付いた PR を飛ばすのは、解けずに離脱した PR を、人間が見るまで何度も解かせ直さないためである。

auto-merge を外すのは、残っていると、解いた push の CI が通った瞬間、`pr-ai-triage.yml` が中身を見る前にマージされうるからである。外しておけば、ふだんの PR と同じく、`pr-ai-triage.yml` が中身を見てから付け直す。衝突中の PR に auto-merge が残るかは確かめられていないので、どちらでも安全な側に倒している。外すのは AI のセッションではなくこのツールである。`gh pr merge` は、`.claude/hooks/` が AI のセッションから打つのを止める。

## 対話セッションの push の後にも、`/auto-fix-ci` が使われる

人間が「issue #110 対応して」のように進める対話セッションでも、AI が push した後に CI が落ちると、`.claude/hooks/wake-on-ci-failure.mjs`（PostToolUse の hook）が裏で CI を待つ。落ちたときだけセッションを起こして、`/auto-fix-ci` を実行させる。

- **無人のセッションでは、hook は何もしない。** このツールは、起動する `claude` に環境変数 `AUTO_PROGRAMMER_UNATTENDED_SESSION=1`（名前と値は `unattendedSessionEnv.mjs`）を渡す。hook はこれを見て終わる。CI を待って直させるのはこのツールなので、hook も起こすと二重になる。`/auto-fix-ci` も同じ環境変数で、無人か対話かを見分ける
- **hook は `config.mjs` の `repository` と `ci` を読む。** 待つワークフロー・見直す間隔・待ち上限・直させる上限は、このツールと同じ値を使う。`config.mjs` は同期で上書きされないので、これらの項目が無いと hook は何もしない
- **対話では、離脱しても Issue にコメントもラベルも付けない。** 別のブランチにいる・未コミットの変更がある・直せないと分かったときは、セッションで報告して終わる。人間がその場に居るためである

## 週次スクリプトが Issue を供給する

2 で拾う `ai-fixable` の Issue の一部は、週次スクリプトが人手を介さず自動起票したものである。Policy・Rule を変えたときに違反になった既存コードは、コードに差分が出ないので通常のレビューに掛からない。それを拾う専用の週次チェックが2本ある。

| スクリプト                                    | 対象                                                               | 起票ラベル               |
| --------------------------------------------- | ------------------------------------------------------------------ | ------------------------ |
| `scripts/ci/doc-consistency-weekly-issue.mjs` | `docs/` 全体（`/doc-consistency`）                                 | `doc-consistency-weekly` |
| `scripts/ci/code-policy-weekly-issue.mjs`     | `app/`（`/code-review` の「決まりどおりか」「設計の形」の2レンズ） | `code-policy-weekly`     |

`scripts/ci/doc-consistency-weekly-issue.mjs` の設計判断：

- **起票だけを GitHub Actions（`doc-consistency-weekly.yml`）が行い、実行そのものは人間か Auto Programmer が行う**：このテンプレートは、GitHub Actions で Claude Code を使えないプロジェクトへの配布も前提にしている。実行そのものを Actions に持たせると、そうしたプロジェクトでは仕組みごと動かない。
- **専用ラベル（`doc-consistency-weekly`）が付いた open な Issue が既にあれば起票しない**：処理待ちの週次 Issue は1件で足りる。起点を前回処理以降の変更に絞れば、処理が1週遅れても次回でその分を追いつけるため、未処理のまま複数積み上げる必要が無い。
- **起点は、実行結果コメントが付いた直近の週次 Issue の HEAD SHA から今回の HEAD までに変わった `docs/**/*.md` にする**：2文書間の重複・矛盾は、どちらかが変わったときにしか生まれない。最初に1回全体を見て、以後の変更を途切れずに起点へつなげれば、すべての組み合わせを一度は見たことになる。該当する週次 Issue が無い、または SHA を読み取れない場合だけ、これまでどおり `docs/` 全体を対象にする。

`scripts/ci/code-policy-weekly-issue.mjs` の設計判断：

- **docs 用の週次 Issue とは別の Issue・別ラベルにする**：1つの Issue に両方載せると、どちらかが未処理のまま残ったとき「open なら起票しない」という決まり（両スクリプト共通）で両方のチェックが止まる。ラベルと Issue を分ければ、一方の遅延がもう一方を妨げない。
- **起点を計算せず、毎週 `app/` 全体を対象にする**：docs 用は前回処理以降の差分に絞るが、これは差分計算の実装コスト（処理済み Issue の探索・HEAD SHA 記録・読み戻し）と引き換えに、文書数が増えても1回あたりのチェック量を抑える対策である。コード側の対象は当面小規模で、差分計算を持たなくても週1回全体を見るコストが見合う。実測の所要時間が閾値を超えたら、差分計算への切り替えを検討する。
- **`samples/` は対象にしない**：参照実装で AI が書き換えられない（リポジトリルートの README「変更してはならないパス」）ため、対象に含めても指摘を直せない。
- **レンズは「決まりどおりか」「設計の形」の2本に絞る**：重複コード（SSoT違反）・単一責任・アプリ設計ポリシー準拠は「設計の形」レンズの担当で、「決まりどおりか」には含まれない。バグ探し・セキュリティ・テストの3レンズは対象外にする。既存コードの潜在バグ・テストの穴を狙う観点は、Policy 変更と無関係に前週と同じ指摘を繰り返しやすいためである。

## 使う前に済ませておくこと

GitHub CLI のログインと Claude Code の導入は、人の操作が要るので自動化できない。ボードを読み書きするトークンには `project` スコープが要るので、ログインの後に足す。

```bash
gh auth login
gh auth refresh -s project
```

対象リポジトリに Issue 用のラベルが無ければ、`./scripts/setup-labels.sh` で作る。

ボードの Workflows 画面で、組み込みワークフロー「Pull request linked to issue」の移し先を `In Review` にする（既定は `In progress`）。PR が Issue に紐づいた時点でカードがレビュー待ちへ動くのは、この設定によるもので、このツールは動かさない。公開 API に組み込みワークフローの設定を変える手段が無いため、画面で1回やる。

これ以外の準備（clone・依存のインストール）は自動で行う。初回の実行と、並べて動かして新しい番号の clone を作るとき（「設定値」の末尾を見る）は、そのぶん時間がかかる。

```bash
npm run auto-programmer
```

起動してよいのは人間だけである。AI のセッションから打つと `.claude/hooks/` が止める。権限確認を飛ばした `claude` を、AI が自分で増やせないようにするためである。

## 設定値（`config.mjs`）

接続先と表記はすべて `config.mjs` に集めてある。**他のファイルにこれらの値は書かれていない**（例外は `branchPrefix` だけ。「別のリポジトリで使うとき」を見る）。

| キー                          | 意味                                                                                      | 調べ方                                                                                        |
| ----------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `repository`                  | Issue と PR の相手（`owner/repo`）                                                        | `gh repo view --json nameWithOwner`                                                           |
| `board.owner`・`board.number` | GitHub Projects の持ち主と番号                                                            | `gh project list --owner <owner>`                                                             |
| `board.statusFieldName`       | 進捗を持つフィールドの表記                                                                | `gh project field-list <番号> --owner <owner>`                                                |
| `board.todoStatusName`        | 積まれただけで、まだ着手待ちにしていないことを表す選択肢の表記                            | 同上                                                                                          |
| `board.readyStatusName`       | 「着手してよい」を表す選択肢の表記                                                        | 同上                                                                                          |
| `board.inProgressStatusName`  | 「着手中」を表す選択肢の表記                                                              | 同上                                                                                          |
| `targetIssueLabel`            | 対象にする Issue のラベル                                                                 | `gh label list`                                                                               |
| `branchPrefix`                | トピックブランチ名の前に付ける接頭辞（`'st2'` なら `st2/feat/issue-123`。空なら付けない） | ライン（`main`・`main2` など）ごとに CI を分けているときだけ設定する。前提は表の下に書く      |
| `sessionTimeoutMinutes`       | claude セッション1回（Skill 1つぶん）を打ち切るまでの分数                                 | 長いほうの実装に掛かる時間の上限として決める                                                  |
| `sessionModel`                | claude セッションに `--model` で渡すモデル（既定 `sonnet`）                               | `claude --help` の `--model`。別名（`sonnet`・`opus`）か正式名                                |
| `sessionEffort`               | claude セッションに `--effort` で渡す effort（既定 `xhigh`）                              | `claude --help` の `--effort`                                                                 |
| `pollIntervalMinutes`         | 着手できる Issue が無かったとき、ボードを見直すまで待つ分数                               | 短すぎると `gh project` の呼び出し頻度が上がり、GitHub API のレートリミットに達しやすくなる   |
| `maxConsecutiveIdleWaits`     | 着手できない周が続いたとき、待ってよい回数の上限（使い切っても着手できなければ止まる）    | 放置を許せる時間（`pollIntervalMinutes` × この回数）から決める                                |
| `ci.workflowFile`             | push で走り、マージ可否を決めるワークフローのファイル名                                   | `.github/workflows/` の下のファイル名                                                         |
| `ci.pollIntervalSeconds`      | CI の run の状態を見直す秒数                                                              | 短すぎると `gh run list` の呼び出し頻度が上がる                                               |
| `ci.runWaitLimitMinutes`      | CI の run 1回が終わるまで待つ上限の分数                                                   | `needs` で直列に並ぶジョブの `timeout-minutes` の合計（最も長い連なり）に、起動待ちの分を足す |
| `ci.maxFixAttempts`           | CI が落ちたとき、`/auto-fix-ci` に直させる回数の上限                                      | 使い切っても落ちていれば人間へ回す                                                            |

フィールド ID・選択肢 ID は設定に持たせない。表記から実行時に引き直す。各 Status が何を意味するかは [issue-policy](../../docs/policy/issue-policy.md)「ボードの Status の意味」が定める。

この設定は `scripts/move-issue-card.mjs`（`npm run move-issue-card -- <Issue番号>`）も共有する。AI が着手の直前に打ってカードを着手中へ動かすスクリプトで、ボードの設定を2か所に持たないためである。`repository` が今いるリポジトリと違えばボード未設定とみなし、警告だけ出して終了コード 0 で終わる。

トピックブランチを切る元も設定に持たせない。GitHub に設定されたデフォルトブランチを、このツールと `/auto-dev`・`/auto-fix-ci`・`/pr-body` がその場で引く。PR の作成先は `pipeline.yml` がデフォルトブランチに決めるので、設定で別の値を持てると、切る元と PR の作成先が食い違うためである。

`branchPrefix` が変えるのはブランチ名だけである。だから AI に作業させるライン（例：`st2` → `main2`）について、次が成り立っている必要がある。崩れると、ブランチが別のラインから切られるか、別のライン宛ての PR になる。

- そのラインのブランチ（例：`main2`）が GitHub のデフォルトブランチである
- そのラインのワークフローが、PR をデフォルトブランチ宛てに作る
- `ci.workflowFile` がそのワークフローを指す

`sessionTimeoutMinutes` は壁時計（wall-clock）で数える。OS がアイドルスリープすると、寝ていた時間もここに数えられ、無人セッションが実際より早く打ち切られる。`index.mjs` は起動直後にこれを防ぐコマンド（macOS は `caffeinate`、Windows は同梱の `sleepGuard.ps1`）を起動し続けるが、ノートPCの蓋を閉じたことによるスリープ（クラムシェルスリープ）までは止められない。実行中は蓋を閉じないか、外部ディスプレイに繋いでおくこと。Linux は `CLOCK_MONOTONIC` がサスペンド中に止まるため、この問題自体が起きず、何もしない。

`sessionModel`・`sessionEffort` は、どの Issue にも同じ値を使う。Issue の `opus` ラベルは読まないので、`opus` の Issue を回すときは、この2つを最上位モデル・effort 最大に変えるか、人間が対話で回す（[development-flow](../../docs/guide/development-flow.md)「フェーズごとにどのモデルで回すか」）。値を `claude` に渡すのは、渡さないと無人セッションが `~/.claude/settings.json` を継ぐからである。そこは対話で `/model` を打つたびに書き換わるので、無人実行のモデルが人間の最後の選択に引きずられる。2つのキーのどちらかが欠けていると、Issue を拾う前に止まる。

AI 専用 clone と実行記録は `~/dev/auto-programmer/` の下に置かれる。置き場を変えたいときは、`config.mjs` を編集せず環境変数 `AUTO_PROGRAMMER_HOME` で指定する。

同じマシンで端末ごとに `npm run auto-programmer` を打てば、何本でも並べて動かせる。各プロセスは起動時に、使われていない一番小さい番号の clone を取り、終わるまでその clone だけを使う。1番は `workspaceDir`（`~/dev/auto-programmer/<リポジトリ名>`）、2番以降はその後ろに `-2`・`-3` … を付けたディレクトリである。clone を分けるのは、1つを共有すると、一方の作業中にもう一方が stash・`git reset --hard`・`git clean` で作業ツリーを巻き戻すからである。番号を自動で取るのは、人間に番号を選ばせずに済み、clone の数が同時に動かした本数の最大値で止まるからである。

- **ロックの置き場**：使用中の番号は `AUTO_PROGRAMMER_HOME` の下の `locks/<リポジトリ名>/workspace-<番号>.lock` が示す。中身はプロセスの PID と作った時刻で、プロセスが終わると外れる。落ちて残ったロックも、PID のプロセスがいないか、マシンの起動より前に作られたものなら、次に起動したプロセスが空きとみなして取り直す
- **clone は自動で消えない**：使わなくなった番号の clone（1つ数百 MB）は残る。要らなければ、動かしていないときに手で消す
- **同じマシンなら、同じ Issue を取り合わない**：2 で選んだ Issue は、ブランチを準備する前に `locks/<リポジトリ名>/issue-<Issue 番号>.lock` を取る。取れなければ、他のプロセスが着手中とみなして飛ばす。持つのは CI 待ちと修正まで含めて1件を終えるまでで、中身と取り直しの決まりは clone のロックと同じである。ロックをこのマシンの中に置くのは、並べたいのが同じマシンの別の端末だからである。排他作成なら一瞬で決まるので、2つの端末をほぼ同時に起動しても1つしか取れない。カードを先に In progress へ動かす手では、動かすのが一瞬で終わらず、同時に起動した2本が同じ候補を引く
- **ロックを取った後にカードの Status を引き直す**：候補の一覧は1周に1回しか引かない。他のプロセスが短い経路（子への引き継ぎ・`/issue-check` での停止）で数十秒で終えてロックを外すと、古い一覧のままでは同じ Issue を取り直せてしまう。この経路はブランチを push しないので、「リモートに … が残っています」の検査でも止まらない。引き直してカードがもう Ready に無ければ、ロックを外して飛ばす
- **別のマシンでは取り合う**：ロックはそのマシンの中でしか効かない。同じアカウントを別のマシンで動かすと、同じ Issue を拾いうる（2 の「自分」はアカウントで決まる）

## 画面の読み方

このツール自身が出す行には、どれも時刻とレベル記号が付く。`claude` セッションの出力は、時刻の幅だけ字下げした `│` の後ろに続く。

```
10:35:37 ℹ ▶ /issue-check #805 を実行
         │ #805 は「方針差し替え」と判定しました。
10:46:46 ✓ /issue-check #805  11分9秒
```

`npm ci` の出力は画面に出さず、成功したら所要時間付きの ✓ の1行だけを出す。失敗したときだけ、取り込んだ出力を `│` 付きで全文出す。記号も `│` も付かない行は、`gh repo clone` がそのまま流している出力である。

| 記号 | 意味                               | 行き先 |
| ---- | ---------------------------------- | ------ |
| ℹ    | 進行中の出来事                     | stdout |
| ✓    | うまくいった                       | stdout |
| ⚠    | 処理は続くが、人間に見てほしいこと | stderr |
| ✗    | 異常                               | stderr |
| ⏳   | 待っている間の状況                 | stdout |

起動した直後に、このプロセスが使う clone の番号とパスが1行出る。Issue 1件の始まりには、`══ #123 ═══…` の二重罫線の下にタイトル・ブランチ名・作業する clone を並べた区切りバナーが出る。claude のセッションが流す大量の出力の中から、このツール自身の話に戻った場所をここで見つける。claude セッションの終わりには、終了状態（正常なら ✓、それ以外は ⚠ と終了コード）と所要時間の1行が出る。1件の終わりには、所要時間・CI の結果・PR の URL・記録先がまとめて出る。

色は端末に直接出すときだけ付く。ファイルへリダイレクトしたときと、`NO_COLOR=1` を付けたときは自動で落ちる。

## 1件を終えたときの読み上げ

Issue 1件の締めの表示に合わせて、macOS では `say`、Windows では `powershell.exe -NoProfile` から System.Speech（Windows 標準の音声合成）の `SpeechSynthesizer` で、次の1文を読み上げる。声は指定せず、OS の既定の声に任せる。

```
issue <番号>、<結果の言葉>。<タイトル>
```

タイトルの頭の段番号（`3. ` や `3〜5. `）は外す。長いタイトルも切り詰めない。結果を先に読むので、長いタイトルは聞き流してよい。

結果の言葉は、画面の締めの記号と同じ判定で決める。次の上から順に当てて、最初に当たったものを読む。

- 例外で落ちた（✗）：「失敗しました」
- 人間の手当てが要る（⚠）：「要確認です」
- 成功（✓）で、子 Issue を1件以上着手待ちに載せた：「子の issue に引き継ぎました」
- 成功（✓）：「完了しました」

次の場合は読み上げない。

- macOS と Windows 以外の OS
- 衝突した PR を解かせる流れ。Issue を終えることではないため

Windows では、読む文を環境変数 `AUTO_PROGRAMMER_SPEECH_SENTENCE` で渡し、`-Command` の文字列はタイトルによらず固定にする。タイトルは GitHub から来る外部が書ける文字列で、`-Command` に埋め込むと、`"` や `;` を含むタイトルがコマンドとして実行されるためである。既定の声が日本語に対応していない PC では、日本語のタイトルが読まれないことがある。

読み上げの終わりは待たない。`say` や `powershell.exe` を起動できなかったときと、0 以外で終わったときは、⚠ の警告を1行出して続ける。並べて動かした複数のプロセスが同時に終えると、声は重なる。

## 待っている間の表示

待っている間は、ステータス行が表示される。この行は、対話的な端末で直接見ているとき（TTY）と、`npm run auto-programmer 2>&1 | tee` のようにファイルやパイプへ流したとき（非TTY）とで見え方が変わる。

| 場面                      | TTY                                                                                    | 非TTY                                                              |
| ------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 着手できる Issue が無い間 | ⏳ の1行がその場で書き換わり続ける                                                     | ⏳ の行を、見直すたび（`pollIntervalMinutes` ごと）に1行追記する   |
| claude セッションの間     | `\| 実行中  [████████░░░░░░░░░░░░]  24:31 / 60:00` の1行が、スピナーを回して書き換わる | `⏳ 実行中… 経過 24分31秒 / 上限60分` の行を、5分ごとに1行追記する |
| CI を待っている間         | ⏳ の1行がその場で書き換わり続ける                                                     | ⏳ の行を、5分ごとに1行追記する                                    |

claude セッションのバーは、`sessionTimeoutMinutes` の上限まであとどれだけかを20マスで示す。スピナーとバーはどれも Windows の標準等幅フォントが持つ記号で描くので、Git Bash でも崩れない。ただし Git Bash（mintty）では TTY と判定されないことがあり、そのときは非TTY の表示になる。

Issue を見つけた・close した・異常が起きたなど状況が変わったときは、通常の行として追記される。TTY ではその直前にステータス行が消える。

## 実行の記録

Issue 1件につき1行の JSON が `runLogPath` に追記される。端末を閉じた後でも、いつ・どの Issue を・どうなったかを追える。並べて動かしたプロセスはどれも同じファイルへ追記するので、各行の `workspaceDir` に、その Issue を作業した clone を載せる。

```bash
tail -3 ~/dev/auto-programmer/runs.jsonl | jq .
```

## 別のリポジトリで使うとき

直すのは次のものだけ。

- **`config.mjs`**：上の表の値をその環境のものへ書き換える。書き換えないと `npm run move-issue-card` はボード未設定とみなして何もしない。テンプレートの同期（`scripts/sync-template.sh`）は `config.mjs` を上書きしないので、同期で `maxConsecutiveIdleWaits` のような新しいキーが増えたときは手で足す（無いと起動時に落ちる）。逆に `baseBranch` のように使われなくなったキーは残っても害が無いが、値を変えても何も起きないので消してよい。clone の番号とロックの置き場は既存の `workspaceDir` から導くので、同期した後も古い `config.mjs` のまま、キーを足さずに並べて動かせる
- **`package.json`**：`auto-programmer`・`move-issue-card`・`close-issues` のスクリプトを写す
- **`ci.workflowFile` のワークフロー**：`branchPrefix` を設定したときだけ、push トリガー（`on.push.branches`）に同じ接頭辞を足す（例：`'st2/**'`）。足さないと CI が走らず、PR も作られない。接頭辞は既存のブランチ（`main2` など）と同じ名前にできない（git がその下にブランチを作れないので、起動時に止まる）
- **`.claude/skills/auto-dev/`・`.claude/skills/auto-fix-ci/`・`.claude/skills/auto-resolve-conflict/`・`.claude/skills/issue-check/`**：そのリポジトリの `.claude/skills/` へ写す（`/auto-dev`・`/auto-fix-ci`・`/auto-resolve-conflict` が無いと手順が無い。`/issue-check` は `.claude/agents/issue-auditor-agent/` と、割るときに使う `.claude/skills/issue-split/` も要る。`/issue-split` は正典として `.claude/skills/to-issues/`・`.claude/skills/quick-issue/` を参照するので、これも写す。初回の検査で外部依存の制約を調べるために `.claude/agents/premise-checker-agent/` も要る。これは一次資料の定義を `.claude/skills/origin-search/` から読むので、これも写す。`issue-auditor-agent` は過去の決定を引く手順を `.claude/skills/past-decision-search/` から読むので、これも写す）

`/auto-dev` は移した先の CLAUDE.md・Policy・hook をそのまま使う。実装の進め方をそのリポジトリに合わせたいときは、Issue 本文の「実装フロー（使用するSkill）」で指定する。

## 止まったとき

予定した終わり方以外で終えた Issue には、`needs-human-check` が付く（どれを予定とするかは issue-policy が定め、`needsHumanCheck.mjs` が判定する）。止まった Issue は `gh issue list --label needs-human-check` で引ける。下の表で直したら、ラベルを外す。付けられなかったときは、記録の `needsHumanCheckLabelError` に理由が残る。
