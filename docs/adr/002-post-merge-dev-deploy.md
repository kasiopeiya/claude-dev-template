# ADR-002: dev への deploy を main マージ後に行う

> [!IMPORTANT]
> **TL;DR（この決定の要点）**
>
> - dev 環境への deploy を、トピックブランチへの push 時ではなく **main へマージした後**に行う
> - マージ可否の判定からは実環境（AWS）への依存を外し、cicd-gate は AWS に触れずに答えが出るものだけで決める
> - 対価として PR レビュー時点で deploy 成功が未確認になる。cdk diff の提示と、deploy 失敗時の Issue 自動起票で受ける

## コンテキスト（なぜ決めるのか）

旧設計の芯は「**deploy 成功をレビューの Entry Criteria とする**」だった。CDK は deploy しないと分からないエラーが多いため（IAM の制約・リソース名の衝突・サービス上限など）、未 deploy のコードをレビューに回すとレビューがやり直しになりうる、という理由である。

この構成では、マージ可否を決める `cicd-gate` が deploy と結合テストの完了を待つ。トランクベース開発は小さい変更を頻繁に main へ入れることで成り立つが、マージの手前に最も遅い工程が居座ると、変更が小さいほど待ち時間の割合が大きくなる。

deploy が経路のどこに位置するかを、旧設計と対比する。

| 工程                     | 旧設計                      | 新設計                      |
| ------------------------ | --------------------------- | --------------------------- |
| 検査（静的解析・テスト） | マージ前                    | マージ前（変わらず）        |
| dev への deploy          | マージ**前**（gate に含む） | マージ**後**                |
| 結合テスト               | マージ**前**（gate に含む） | マージ**後**                |
| cdk diff の提示          | なし                        | マージ前（gate に含まない） |
| deploy 失敗の検知        | gate が赤くなる             | GitHub Issue を自動起票     |
| dev へ deploy できる経路 | すべてのトピックブランチ    | main だけ                   |

## 決定（何を選んだか）

dev への deploy と結合テストを `deploy-dev.yml`（main への push が起点）へ移し、`cicd-gate` の判定対象から外す。設計の芯を「**マージ可否の判定から、実環境への依存を外す**」に差し替える。

deploy 処理の中身（AWS 認証・`cdk deploy`）は #31 の完了までコメントアウトのままとし、この決定では実行タイミングの構成だけを変える。

## 採用理由（なぜこれを選んだか）

マージまでの経路に最も遅い工程を置かないことで、小さい変更を頻繁に main へ入れられるようにするため。deploy をマージの後ろへ回すと、マージ可否は実 AWS 環境に触れずに決まるものだけで判定できるようになり、AWS 側の障害や dev の奪い合いがマージを止めなくなる。

副次的に、dev へ deploy する経路が main だけになるため、dev 環境にスタックがあるときは必ず main の姿になる（スケジュール destroy の後は空になる）。旧設計で許容していた「ブランチ間での dev の奪い合い・上書き」は起きなくなる。

## 検討した代替案（なぜ却下したか）

| 案                                          | 内容                                                                    | 却下理由                                                                           |
| ------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| マージ前 deploy を維持する（旧設計）        | トピックブランチ push で dev へ deploy し、成功を Entry Criteria とする | マージの手前に最も遅い工程が居座り、変更が小さいほど待ち時間の割合が大きくなる     |
| マージ前 deploy を advisory 化する          | deploy は残し、`cicd-gate` の `needs` からだけ外す                      | deploy 結果が誰の判断にも使われないまま dev を奪い合い続ける。待ち時間だけが残る   |
| PR ごとの使い捨て（ephemeral）環境を作る    | PR ごとに独立した環境を立てて deploy する                               | 1アカウント1環境という前提を崩す。コストと複雑さもテンプレートの初期足場として過剰 |
| トピックブランチの手動 deploy 経路を残す    | `workflow_dispatch` で任意ブランチを dev へ deploy できるようにする     | dev へ入る経路が2つになり、「dev にいま何があるか」が一意に決まらなくなる          |
| cdk diff を `cicd-gate` の `needs` に入れる | PR 時点の cdk diff をマージ可否の判定に含める                           | 実環境への疎通がマージ可否に混ざり、AWS 側の一時障害でマージが止まる               |
| deploy 失敗時に revert PR を自動生成する    | 壊れたマージコミットを自動で差し戻す                                    | 原因がコード側にないとき（AWS 側の一時障害など）に余計な差し戻しが起きる           |

## トレードオフ・影響

| 受け入れる制約・リスク                        | 影響範囲                                                  | 緩和策                                                                                      |
| --------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| PR レビュー時点で deploy 成功が未確認になる   | CDK・アプリを変更するすべての PR のレビュー               | PR 時点で `cdk diff` をジョブサマリに出し、意図しない置換・削除をレビューで見えるようにする |
| deploy の失敗が required check の外側で起きる | main ブランチ                                             | 失敗したら GitHub Issue を自動起票し、壊れた main に持ち主を作る                            |
| 実環境を通らない変更が main に入る            | `infra/` を変更する PR（`needs-human-review` が付かない） | レビュー方針としての選択。壊れた結果は上記の deploy 失敗 Issue で拾う                       |
| マージ前に dev で動作を確かめる手段が無くなる | 開発者の手元の確認                                        | なし（手動 deploy 経路を用意しないと決めたため）                                            |
| 壊れた main が全ブランチへ配られる            | 進行中のすべてのトピックブランチ                          | なし（ブランチ最新化の要求は「検査したコード ≒ マージされるコード」を保つために維持する）   |

得るもの：dev の奪い合いが消え、dev にスタックがあるときは main の姿だけを映す。マージ可否が AWS の可用性に左右されなくなる。
