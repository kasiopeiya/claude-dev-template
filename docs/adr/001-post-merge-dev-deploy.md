# ADR-001: dev への deploy を main マージ後に行う

> [!IMPORTANT]
> **TL;DR（この決定の要点）**
>
> - dev 環境への deploy と結合テストは、main へマージした**後**に実行する
> - マージ可否を決める `cicd-gate` には、実環境（AWS）に触れずに答えが出る検査だけを入れる
> - 対価として PR レビュー時点で deploy 成功が未確認になる。`cdk diff` の提示と、deploy 失敗時の Issue 自動起票で受ける

## コンテキスト（なぜ決めるのか）

CDK は deploy しないと分からないエラーが多い（IAM の制約・リソース名の衝突・サービス上限など）。そのため「dev へ deploy して成功したことをレビューの前提にしたい」という力が働く。deploy をマージの前に置けば、壊れたコードが main へ入らない。

一方でこのプロジェクトはトランクベース開発を採る。小さい変更を頻繁に main へ入れることで成り立つので、マージの手前に最も遅い工程が居座ると、変更が小さいほど待ち時間の割合が大きくなる。さらに dev は1アカウント1環境なので、すべてのトピックブランチが dev へ deploy できると、ブランチ間で環境を奪い合う。

deploy をマージのどちら側に置くかは、この2つの力のどちらを取るかの選択である。

## 決定（何を選んだか）

dev への deploy と結合テストは `deploy-dev.yml`（main への push が起点）で実行し、`cicd-gate`（マージ可否を決める required check）には含めない。**マージまでの経路には、速く答えが出るものだけを置く**。

| 工程                 | 実行タイミング | `cicd-gate` に含むか |
| -------------------- | -------------- | -------------------- |
| 静的解析・単体テスト | マージ前       | 含む                 |
| `cdk diff` の提示    | マージ前       | 含まない（advisory） |
| dev への deploy      | マージ後       | —                    |
| 結合テスト           | マージ後       | —                    |

## 採用理由（なぜこれを選んだか）

マージまでの経路に最も遅い工程を置かないことで、小さい変更を頻繁に main へ入れられるようにするため。マージ可否が実 AWS 環境に触れずに決まれば、AWS 側の障害も dev の奪い合いもマージを止めない。

dev へ deploy できる経路が main だけになる効果もある。dev 環境にスタックがあるときは必ず main の姿になり（スケジュール destroy の後は空になる）、「dev にいま何があるか」が一意に決まる。

## 検討した代替案（なぜ却下したか）

**決定の軸：dev へいつ deploy するか。**

| 案                                   | 内容                                                                 | 却下理由                                                                           |
| ------------------------------------ | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| トピックブランチへの push 時         | push で dev へ deploy し、その成功をレビューの Entry Criteria とする | マージの手前に最も遅い工程が居座る。dev をブランチ間で奪い合う                     |
| 手動実行のみ                         | `workflow_dispatch` で任意のブランチを dev へ deploy する            | dev へ入る経路が一意に決まらず、「dev にいま何があるか」が分からなくなる           |
| PR ごとに使い捨て（ephemeral）環境へ | PR ごとに独立した環境を立てて deploy する                            | 1アカウント1環境という前提を崩す。コストと複雑さもテンプレートの初期足場として過剰 |

## トレードオフ・影響

| 受け入れる制約・リスク                        | 影響範囲                                                  | 緩和策                                                                                      |
| --------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| PR レビュー時点で deploy 成功が未確認になる   | CDK・アプリを変更するすべての PR のレビュー               | PR 時点で `cdk diff` をジョブサマリに出し、意図しない置換・削除をレビューで見えるようにする |
| deploy の失敗が required check の外側で起きる | main ブランチ                                             | 失敗したら GitHub Issue を自動起票し、壊れた main に持ち主を作る                            |
| 実環境を通らない変更が main に入る            | `infra/` を変更する PR（`needs-human-review` が付かない） | レビュー方針としての選択。壊れた結果は上記の deploy 失敗 Issue で拾う                       |
| マージ前に dev で動作を確かめる手段が無い     | 開発者の手元の確認                                        | なし（手動 deploy 経路を用意しないと決めたため）                                            |
| 壊れた main が全ブランチへ配られる            | 進行中のすべてのトピックブランチ                          | なし（ブランチ最新化は「検査したコード ≒ マージされるコード」を保つために求める）           |
