序章：コーディングエージェントは、超ハイスペック新人である

コーディングエージェントは、何でも知っているのに、あなたの会社のことは何も知りません。

一般的な技術知識では、AIはすでに人間を超えています。言語も、ライブラリも、設計手法も、あなたより多く知っている。 それなのに、あなたの会社のルールも、プロダクトの事情も、去年その設計にした理由も、何ひとつ知りません。

これは超ハイスペック新人と同じ状態です。 だから最初にやることも同じ ── オンボーディング。仕事の環境を用意し、目的を伝え、成果物を別の人に見てもらう。 人間の新人に対してやってきたことが、そのまま効きます。

コーディングエージェントとは、指示を受けて、自分でファイルを読み書きし、コマンドを実行して作業を進めるAIのこと。 チャットに答えを出すだけのAIとの違いは、手を動かすところにあります。

このガイドの読み方

このガイドは、新人として扱うという考え方をベースにします。やることの多くは、それで決まります。

ただしAIには、人間とは違う性質もあります。真似る速さ、記憶の持ち方、そして手が止まらないこと。 ここに新人と同じ感覚を持ち込むと、うまくいきません。そこで2つに分けて説明します。

PART 1 新人だと思えば、やることは決まる

01人間の仕事は、AIが働きやすい環境を整備することである

AIの精度が悪いのは、あなたのせいかもしれません。

出力がひどいとき、私たちはAIを疑います。でも原因は、たいてい渡した情報の方にあります。 情報がAIに届いていないなら、どれだけ賢くても答えようがありません。壁は2つあります。

壁① 場所 ── 手が届かない情報は、無いのと同じ

個人のOneDrive、社内Wikiの奥、Slackの会話、そしてあなたの頭の中。 そこにある情報は、AIから見れば存在しません。

壁② 形式 ── 問うべきは「読めるか」ではない

今のAIはPDFもExcelも読めます。だから「AIが読める形式か」を基準にすると、判断を間違えます。 問題はその先です。情報は一度書いて終わりではなく、探され、一部だけ読まれ、直され続けるものだからです。

形式の違いは、書いた後に効いてくる
Markdown（テキスト） PDF・Excel（バイナリ）
探す 必要な箇所だけ検索して読める まるごと読むしかない
直す AI自身が直せる AIが直せない
変更を見る 差分が見え、人間がレビューできる 何が変わったか見えない

つまり正しい基準は「AIが読める形式」ではなく、AIが探せて、直せる形式です。

Excel方眼紙・神Excelは、絶対にやめる

結合セル・セルの色・配置で意味を表した文書は、テキストになった瞬間にその意味が落ちます。読み込めたのに、内容が伝わらない。 Excelは表計算の道具であって、ドキュメントの道具ではありません。

最初の仕事は、AIが探せて直せる形式で、AIが手を伸ばせる場所に情報を置くこと

一度整えれば、以降すべての作業で効き続ける。いちばん費用対効果が高い投資です

02目的を書け。手段はAIが知っている

カーナビに、曲がる場所を一つずつ教える人はいません。行き先を告げれば済むからです。

AIは手段を大量に知っています。言語、ライブラリ、設計手法、アルゴリズム。その量ではすでに人間を超えています。 一方で、AIは目的を持ちません。何のためにやるのかを持っているのは、あなただけです。

目的が決まらなければ、手段は選べません。同じ「ログを出す」でも、障害調査のためか監査のためかで設計は変わります。 だから指示に書くのは「何のために」。「どうやるか」は書かなくていい ── そちらはAIの方が詳しいのですから。

同じ依頼を、手段で書くか目的で書くか
書き方 指示の例
❌ 手段 この関数に try-catch を入れて
⭕ 目的 この処理が失敗したとき、利用者に何が起きたか分かるようにしたい

ただし制約は書きます。使ってよいライブラリ、守るべき規約、越えてはいけない予算。 制約は目的の一部であって、手段の指定ではありません。見分け方は簡単です ── 越えてはいけない線を引くなら制約、やり方を決めるなら手段。

03自分の答案を、自分に採点させてはいけない

自分の書いた文章の誤字は見つからないのに、他人の文章の誤字はすぐ見つかる。AIも同じです。

AIは、自分が作ったものを甘く評価します。自己偏愛バイアスと呼ばれる現象です。 理由は単純で、自分の出力を「正しい」という前提で読んでしまうから。人間が自分の文章を校正できないのと、同じ構造です。 そして同じ構造である以上、意欲や指示の強さでは直りません。

だから同じセッションで「レビューして」と頼んでも、意味のある指摘は出ません。返ってくるのは「問題ありません」です。

SubAgentとは、元のセッションとは別に立ち上がる独立したAIのこと。会話の経緯を引き継がないので、作った側の都合を知りません。 知らないことが、ここでは強みになります。

さらに効く言い方があります ── 「これは新人が書いたコードです。徹底的にレビューしてください」。 作者が自分ではないという前提を与えると、遠慮が消えます。

これはAI特有の話ではありません。人間の開発でも、コードレビューやQAで役を分けてきました。同じ仕組みを、AIにも持ち込むだけです。

04毎回指示するな。仕組みを作れ

新人が一人前になった合図は、あなたが席を外せるようになったことです。AIも同じです。

あなたが指示する → AIが作る → あなたが見る → また指示する。 この輪の中に、あなたが座っています。AIは、あなたが次の一言を打つまで止まっています。

Loop Engineering とは、その席から降りることです。やることは一つ ── プロンプトを出す役を、人間からシステムへ移す。 2026年6月に Addy Osmani が名付けた考え方で、Claude Code を率いる Boris Cherny も、プロンプトする相手はループの方だと述べています。

Prompt ── モデルへの話し方 → Context ── モデルに見せるもの → Harness ── 足場全体 → Loop ── 回し方
ハーネスとは、AIが仕事をするための足場一式のこと。読ませる文書、使える道具、守らせるルール、走らせる手順 ── Claude Code そのものと、あなたがリポジトリに置いた設定が、これにあたります。

注目してほしいのは検証役です。作った本人に採点させない（節3）が、そのままループの部品になっています。 そして記憶は会話ではなくIssueに置く。会話は次の周回へ渡せませんが、Issueは渡せます。

そして、止め方のないループは予算を溶かします。

ループを作る前に、止め方を決める。新しい時代の仕事は、指示を出すことではなくループを設計すること
PART 2 ただし、新人とは決定的に違う

05AIは増幅器である

ゴミしか作れない人がAIを使っても、ゴミを高速に作れるようになるだけです。

AIは既存のコードを見て、それに合わせて書きます。ここまでは人間の新人と同じです。 違うのは倍率。新人が1日かけて真似る量を、AIは数分で真似ます。

AIは、あなたの質を掛け算します。 だから「最初が肝心」。最初の1ファイル、最初の1つの設計書に、いちばん時間をかけてください。

今日からできること ── 新しいパターンは手本を1つだけ丁寧に作り、「これに倣って」と言う。10個まとめて作らせない

起きるのはコードだけではありません。ドキュメントも、テストも、コミットメッセージも、同じように増幅されます。

06AIの記憶は、有限で、汚れていく

同じセッションで粘るほど、AIはバカになります。

AIが一度に見られる情報には上限があります。会話を続けるほど、そこに過去のやり取りが積み上がっていきます。 そして2つのことが起きます ── 埋もれることと、汚れることです。

コンテキストウィンドウとは、AIが一度に見られる情報の上限のこと。 これまでの会話も、読んだファイルも、すべてここに載ります。載りきらなくなると、古いものから押し出されます。

症状はこうです ── 一度直した間違いを繰り返す。さっき決めた方針を無視する。急に的外れなことを言い出す。 これはAIの性能ではなく、会話の長さの問題です。

ここが人間と決定的に違うところです。人間は忘れることで整理します。AIは全部抱えたまま質が落ちます。 しかも本人に自覚がないので、最後まで自信たっぷりに「分かりました」と答え続けます。

対処 ── 会話を捨てるか、圧縮するか、外に出すか
手段 使いどころ
/clear 会話を捨てて最初から。タスクが変わったら切るが原則
/compact 要約して圧縮する。同じ作業を続けたいときはこちら
ファイルに書く 大事なことは会話ではなくファイルやIssueへ。汚れないし、次のセッションにも渡せる
情報は多いほど良い、ではない。必要な時に、必要な分だけ渡す。長い会話は積み上げではなく劣化です

07AIは暴れ馬である。手綱を握るのが、あなたの仕事

放っておくと、AIは足し算しかしません。引き算は、あなたの仕事です。

AIは放っておくと、必ず何かを作ります。そして必ず長くなります。 設計書を頼めば章が増える。コードを頼めば使わない抽象化が入る。説明を頼めば表と箇条書きが山盛りになる。

理由は、AIが「網羅的で具体的なもの＝良いもの」として扱うからです。足りないより多い方が安全な側に倒れます。 ここも新人とは違います。人間の新人は迷って手が止まり、遠慮して聞いてきます。AIは止まらないし、疲れない。しかも自信満々に出してきます。

だからあなたの指示は、いつも同じ形になります ──「もっと短く」「もっとシンプルに」「ここは要らないから消して」。 そして、これを毎回打っている状態は、効率的ではありません。 同じ指示を繰り返しているなら、それは節4で見た「輪の中に座っている」サインです。

削る背骨になる原則は2つ。YAGNI（You Aren't Gonna Need It ── 必要になるまで作らない）とLess is more（少ないほど豊か）。 AIはどちらも知っているのに、放っておくと守りません。守らせる方法が、口で言うことではないだけです。

やることは、削る基準を指示から仕組みへ移すことです。

  • ポリシーに書く ── 「良い設計書とは何か」「良いコードとは何か」を先に文書で決めておく。AIは書く前にそれを読むので、最初から短く出てきます
  • レビューの手順に組み込む ── 削除テストのような判定を手順として持たせ、AI自身に当てさせる。人が気づく前に、AIが自分で削ります
削除テスト ── その行を消したとき、読者は困るか

困らないなら消す。「具体的な方が親切そう」は、残す理由になりません。この一文を口で言い続けるのではなく、文書に書いて読ませます。

手綱の握り方は、毎回「短く」と言うことではない。何を良しとするかを先に書いて、AIに読ませること

終章：それでも、理解だけは委譲できない

「なぜこの実装なんですか」と聞かれて「AIがそう書いたので」と答える日が来ます。

ここまで、設計も実装も判断もAIに任せられると書いてきました。実際、任せられます。 ただ一つ、理解だけは任せられません。

なぜか。責任が人間に残るからです。障害が起きたとき、直すのも説明するのも人間です。 「なぜこの設計なのか」に答えられないプロダクトは、もう変更できません。

しかもAIは、自信満々に嘘をつきます。存在しないAPI、それらしい根拠、もっともらしい説明 ── 口調は、正しいときと寸分違いません（ハルシネーション）。理解していない人には、見抜く手段がありません。 これは節3の「自己採点が甘い」とは別の問題です。あちらは評価の甘さ、こちらは事実そのものの誤りです。

ジュニアエンジニアを対象にした実験でも、AIを使った群は理解度テストの点が低く出ました。 ただし中身は二分していました。低かったのは、丸投げした人と、最初は質問していたのに次第に全部任せるようになった人。 高かったのは、生成後に質問を重ねた人と、コードと説明をセットで求めた人です。

だから最良の使い方は、理解するためにAIを使うこと。 AIは、何でも知っているメンターでもあります。「なぜこう書いたのか説明して」「他にどんな選択肢があったか」「この設計の弱点は」。

AIを使って理解を深める人と、理解を避ける人がいる。道具は同じ。結果ばかり求めているとスキルが空洞化する。
