# ドキュメント作成ポリシー（人間が画面で読む文書） <!-- omit from toc -->

全文書に効く規定は [documentation-policy.md](documentation-policy.md) が持ち、本ポリシーは人間が画面で読む文書にだけ上乗せする。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - **先に俯瞰、あとに詳細。** 同種の詳細が2件以上並ぶなら、その直前に1項目1行の一覧を置く
> - **表は見比べるための道具。** 表にするのは3列以上になるときだけで、1行ぶんの説明・理由は表の直下へ出す
> - **一覧を分断する詳細は畳む。** 表・一覧に対応する詳細が3つ以上並ぶなら、トグルに畳む

## 対象読者

人間が画面で読む Markdown 文書を書く／レビューする人 / AIエージェントが、一覧・目次・表・トグルをどう置くか迷ったとき。

> [!IMPORTANT]
> **（AI・必須）** 本ポリシーを改訂したら、`.claude/skills/quick-doc-review/SKILL.md` と `.claude/agents/doc-reviewer-agent/doc-reviewer-agent.md` のチェック項目の追従要否を判断すること。どちらも速度のため本ポリシーから判定基準を書き下した派生コピーであり、追従しないと**どのゲートも通らない規約が生まれる**。載せないと判断した場合は、その理由を quick-doc-review の「チェック項目に載せない規約と理由」に書く。

## この方針が決めていること

- [1つの文書の中でも俯瞰を先に置く](#1つの文書の中でも俯瞰を先に置く)：同種の詳細が2件以上並ぶなら、その直前に1項目1行の一覧を置く。文書の行数では決めない
- [400行を超えたら目次を置く](#400行を超えたら目次を置く)：400行超の文書に `###` までネストした目次を置く。決定を添えたポリシー・ADRの目次だけは `##` のみ
- [項目の並びは箇条書きを既定にし、3列以上になるときだけ表にする](#項目の並びは箇条書きを既定にし3列以上になるときだけ表にする)：表にするかは列数だけで決める。2列以下の表は作らない
- [表は俯瞰のためにある——セルに詳細を詰め込まない](#表は俯瞰のためにあるセルに詳細を詰め込まない)：1行ぶんの説明・理由・列挙は表の直下へ出す。列数に応じたセル文字数の上限を守る
- [視覚的に文字を強調する](#視覚的に文字を強調する)：太字は伝わりにくい。バッククォート・Admonition・HTMLタグで強調する
- [冒頭に「決定事項」を3行で先出しする（TL;DR）](#冒頭に決定事項を3行で先出しするtldr)：突出した決定がある文書にだけ、最大3行で置く
- [詳細と理由はトグルに畳む](#詳細と理由はトグルに畳む)：対応する詳細が3つ以上並ぶとき、20行超のコードブロックのとき、図の直下に判断の理由を書くときは畳む

## 構造設計

### 1つの文書の中でも俯瞰を先に置く

ぱっと見のシンプルさは、1つの文書の中でも作れる。**先に俯瞰、あとに詳細**の順に並べれば、開いた瞬間に目に入るのは全体像だけになる。読者の全員が詳細まで知りたいわけではなく、多くは全体像だけを確かめに来るからである。

**同種の項目についての詳細が2件以上並ぶなら、その直前に1項目1行の俯瞰の一覧を置く。** 1件では並べて見比べる相手がいないので、俯瞰にならない。

- ❌ NG：機能A・機能B・機能Cを、いきなり節で1つずつ説明しはじめる
- ✅ OK：機能名と1行説明の一覧を置いてから、各節で1つずつ説明する

**発火するのはその並びの直前であって、文書の冒頭ではない。文書の行数も関係しない。** 長い文書でも同種の並びが無ければ要らず、短い文書でも並びがあれば要る。行数で決めると、手順書にも用語集にも文書全体の要約表を強いることになり、種別によっては見出しの言い換えしか書けなくなる。

> [!IMPORTANT]
> **（AI・必須）** 目次があることは、俯瞰の一覧を置かない理由にならない。目次が示すのは話題だけで、俯瞰の一覧は各項目の中身を1行で示す。

### 400行を超えたら目次を置く

捜索者は見出しの一覧を見て「自分の探している話題があるか」を判断する。目次が無ければ、その判断のために本文をスクロールさせることになる。

400行以下なら置かなくてよい。見出しだけで全体を見渡せるからである。

目次は次のように置く。

- `## 目次` を対象読者の直後に置く
- `##` と `###` の見出しをアンカーリンクで並べ、`###` は `##` の下にネストさせる。重要な内容を `###` に置く文書では、`##` だけの目次からは中身が見えないからである
- 文書タイトル（`#`）と `## 目次` 自身は目次に入れない。どちらも読者の行き先にならないからである（タイトルは文書を開けば見えており、「目次」の行き先は自分自身）

除外は見出し行の末尾に `<!-- omit from toc -->` を付けて明示する。自動生成しても手で書き直しても同じ結果になる。

```markdown
# 文書タイトル <!-- omit from toc -->

## 目次 <!-- omit from toc -->
```

`####` 以下は Markdown All in One の既定（`markdown.extension.toc.levels` が `1..6`）のままだと混入する。`.vscode/settings.json` で `2..3` に絞る。

#### ポリシー・ADR は目次の各行に「決めていること」を添えてよい

1つの節が1つの決定に対応する文書——ポリシー・ADR——では、目次の各行に、その節で決めたことを1行で添えてよい。リンクだけ拾えば目次として使え、添えた1行まで読めば本文を開かずに何が決まったかを拾える。

```markdown
- [節の見出し](#アンカー)：決めていること
```

**決定を添えた目次は `##` 見出しだけを並べる。** 1節＝1決定を前提に決定を1行ずつ並べる形式なので、`###` を足すと行と決定の1対1が崩れる。

**他の種別には広げない。** 手順書は「手順1をやる」のように見出しの言い換えしか書けず、用語集・インターフェース一覧は文書自体が一覧なので、一覧の一覧になる。

## 視覚表現

### 項目の並びは箇条書きを既定にし、3列以上になるときだけ表にする

**同じ種類の項目を並べるときは、まず箇条書きにする。表にするのは、表にしたとき3列以上になる——1項目が名前のほかに2つ以上の情報を持つ——ときだけである。** 見比べる列が1本しかない並びを表にしても、罫線と余白が増えるだけで速くは読めない。並びではない単一の主張・理由は、文章のままでよい。

表にするかを列数で決めるのは、数えれば誰が判定しても同じ答えになるからである。「項目と属性に分けられるか」で決めると、どんな並びも説明を属性とみなせば表になり、書き手は表に倒れ続ける（refined-engineer-judgment-principles「判断軸は『既定値＋反転条件』で与える」）。

| 1項目が持つ情報                                | 書き方                                               | 例                         |
| ---------------------------------------------- | ---------------------------------------------------- | -------------------------- |
| 名前だけ                                       | 箇条書き。並べ替えると意味が変わるなら番号付きリスト | 対象ファイルの一覧         |
| 名前と説明                                     | 用語リスト：`- **名前**：説明`                       | 用語と定義                 |
| 名前と決まった値（必須/任意、✅/❌、数値など） | 値ごとにまとめた箇条書き：`- 必須：A、B`             | サブ項目ごとの必須・任意   |
| 悪い例と良い例の対                             | `- ❌ 悪い例 → ✅ 良い例`                            | 冗長な書き方と直した書き方 |
| 名前と2つ以上の情報                            | 表                                                   | 対象・既定・理由           |

**文の中に、動詞を含む項目を3つ以上並べていたら、箇条書きに出す**（「A を作り、B を分析し、C を削除する」）。名詞の並び（「図・表・箇条書き」「多対多の関係、階層、状態遷移」）は、文のままでよい。

> [!IMPORTANT]
> **（AI・必須）** 「2項目の対比だから」「表の方が整って見える」は、2列以下の表を作る理由にならない。

> [!WARNING]
> **（AI・必須）** 箇条書きも表も、静的な並びに使う。**逆変換テストで図にすると決まった構造は図にする**（documentation-policy「図にする前に『逆変換テスト』を通す」で決め、「図種は『情報の形』から選ぶ」で形を選ぶ）。

### 表は俯瞰のためにある——セルに詳細を詰め込まない

**方針**：表は全体を並べて見比べるための道具である。1行ぶんの説明・理由・列挙は表に置かず、**表の直下**に書く。出した先をトグル（`<details>`）に畳むかどうかは、詳細の数で決まる——条件は「詳細と理由はトグルに畳む」が定める。

表にする対象を増やすことは、1つのセルに説明を詰め込む理由にならない。説明を直下へ出して表が2列以下になったら、表をやめて箇条書きにする。

**理由**：表の幅は画面で決まり、列が増えるほど1列は狭くなる。長いセルは1行だけで画面を埋め、短い列は1文字ずつの縦書きに潰れる。潰れた表はもう並べて見比べられず、表である意味を失う。

#### 歯止めとしての上限

- 4列以下：上限なし
- 5〜6列：150文字
- 7列以上：80文字

7列以上を厳しくするのは、**そこが「列を削れないか疑うべき表」だからである。** 上限に収める前に、まず列そのものを減らせないかを見る。取れる手は次のとおり。

- **表を分ける**：関心事が2つ混ざっているなら、2つの表にして別々に並べる
- **列をまとめる**：`大分類`・`中分類`・`小分類` を1列の階層表記にする
- **列の取りうる値を縛る**：自由記述をやめ、決まった値だけを書く列にする（例：`出所` 列）

どれも当たらず、それでも7列以上が要るなら作ってよい。1セル80文字の上限に収めること。

数えるのは**文字数**である（半角・全角を区別せず1文字と数える）。区別しないのは、ID の羅列（半角）が実際の幅より甘く、日本語の説明文（全角）が額面どおりに判定されるからである。止めたいのは説明文の方なので、この偏りは望ましい向きに働く。

上限は歯止めであって、可読性を保つ主役ではない。主役は方針そのもので、上限はそこで取りこぼした桁違いのセルを拾う。

上限を超えたら、**超えた理由で直し方を分ける。** 問いは1つ——そのセルは行に分けられるか。

- **行に分けられる**（2つ以上の項目が入っている）：行を分ける
- **行に分けられない**（1つの項目の必須要素が並ぶ）：表から外し、表の直下へ移す

### 視覚的に文字を強調する

Markdown記法の `**太字**` は実際のViewerではわかりにくい。特に重要な箇所は次の手段で強調する。用語リストの名前を太字にするのは、強調ではなく行の見出しなので対象外。

- バッククォート： `重要キーワード`
- Admonition記法（GitHub Flavored）
- HTMLタグ

> [!NOTE]
> ViewerはGitHub Flavored Markdownを前提とする。

## 文章の書き方

### 冒頭に「決定事項」を3行で先出しする（TL;DR）

捜索者は自分の知りたい情報を探すために来る。文書の冒頭に「何を・なぜそう決めたか」を、**決定1件1行の箇条書きで最大3行**にまとめる（1段落にまとめない）。目次は「何について書いてあるか（話題）」しか示さないが、TL;DRは「で、どう決めたのか（結論や決定事項）」を示す。両者は別物なので重複しない。

> [!IMPORTANT]
> **（AI・必須）** 絶対に3行まで。4行になったら、それはTL;DRではなく本文である。短くまとめられないなら、まだ設計判断が定まっていない兆候。

ただし**突出した決定がある文書に限る**。事実を列挙するだけの文書（用語集・API一覧・テーブル定義）には決定がない。同格の決定を並べただけの文書（コーディング規約集）は、どれも本文の一部なので3つ選ぶ行為が恣意的になり、本文との二重管理でずれる。どちらも索引・見出しで足りる。設計書も対象外で、冒頭の基本方針（考え方1文＋方針の箇条書き）がTL;DRの役割を兼ねる（[design-doc-policy](design-doc-policy.md)）。

- ✅ 置く：ADR、ポリシー
- ❌ 置かない：設計書（`docs/design/` 配下）、用語集・API一覧・テーブル定義、コーディング規約集

### 詳細と理由はトグルに畳む

**方針**：次のどれかに当たったら、下の「畳まないもの」を除き、**必ず**トグル（`<details>`）に畳む。当たらないものは畳まない。

- 表・一覧の項目に1対1で対応する詳細が**3つ以上並ぶ**（並んだ全部を畳む）
  - 例：表の各行の理由・本文・内訳／機能ごとの補助図
- Mermaid 以外のコードブロック・出力例で**20行を超える**もの
  - 例：設定ファイルの全文・コマンドの実行ログ
- **図の直下**に書く、その図の設計意図
  - 例：構成図の下の「なぜこの構成か」
- 要件定義書（`docs/requirements.md`）で [requirements-doc-policy](requirements-doc-policy.md) が詳細トグルへ出すと定めた項目（**件数を問わない**）
  - 例：属性の値制約一覧の値制約の根拠

**理由**：同じ型の詳細が並ぶと、読者はそれを1件ずつ読むのではなく、一覧を追う。開いたままの詳細は一覧を分断し、読者が全体を見比べるのを妨げる。

条件を「長いか」「補足か」ではなく**数で決める**のは、長さ・重要度の評価を書き手に委ねると、書き手はほぼ常に「これは本文に要る」と結論するからである（refined-engineer-judgment-principles の「判断軸は『既定値＋反転条件』で与える」）。数えられる条件だけがゲートとして働く。要件定義書だけ件数を問わないのは、どの行に詳細を作るかを requirements-doc-policy が表ごとに名指ししていて、書き手が判断する余地がもともと無いからである。

**畳まないもの**：見出し（`####` 等）を持つ節。トグルに見出しは入れられない。規定・結論を並べた節がまとめて隠れる事故をこれが防ぐ。

> [!IMPORTANT]
> **（AI・必須）** 畳んでよいのは**削除テストを通った内容**だけ。消せるものは畳まず消す。トグルは、消すべき内容の捨て場ではない。

> [!IMPORTANT]
> **（AI・必須）** **トグル削除テスト**：畳んだ部分を伏せて本文だけを通しで読み、読者が判断・行動できるか。できないなら本文が足りていない。結論・規定は畳まない——その理由・根拠は畳んでよい。

#### 記法

```markdown
<details>
<summary>F-03 失効処理</summary>

（詳細）

</details>
```

- **`<details>` の直後と `</details>` の直前に空行を置く**：無いと中の Markdown がレンダリングされない
- **中に見出しを置かない**：トグルにできないため
- **`summary` は中身が分かる識別語にする（`ID 名前`・項目名）**：「詳細」「補足」では開くまで中身が読めない
- **対応する表・一覧と同じ順に並べる**：読者が表の行から詳細を引けるようにする
