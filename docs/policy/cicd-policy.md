# CI/CDポリシー

CI/CD パイプラインを設計・実装・レビューする開発者／AIが、**どのツールを使うかに関わらず成り立つ方針**を知りたいときに参照する。特定の CI サービスを捨てて別のものへ移っても、ここに書かれた方針は生き残る。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - コードが書かれてからリリースされるまでの間に、**人間が手で行う定型作業を置かない**。人間に残すのは判断だけにする
> - 自動化の目的は速さではなく**再現性**
> - **判断そのものは自動化しない。** 機械に委ねてよいのは正解が一意に決まる作業だけ

## なぜ手動手順を置かないのか：人間は繰り返しに弱いから

人間は判断に強く、繰り返しに弱い。手順が定型であるほど注意力は下がり、間違いは静かに起こる——マージ先を取り違える、手順を1つ飛ばす、前回と違う値を入れる。どれも**その場では正しく見える**ので、気づけない。「気をつける」で防げるものではない。

速さを目的にすると、この効果を取り逃す。速いだけの自動化は、間違いを速く繰り返すこともできてしまうからだ。同じ入力に同じ結果が返る状態を作って初めて、人間は「これでよいか」という本来の仕事に集中できる。

## どこまで機械に委ね、どこから人間が判断するか

線引きは「**正解が一意に決まるか**」で引く。手順が決まっていても正解が状況で変わるなら、それは作業ではなく判断である。

| 機械に委ねる（正解が一意）                   | 人間に残す（正解が状況で変わる）               |
| -------------------------------------------- | ---------------------------------------------- |
| ビルド・テスト・静的解析の実行と成果物の生成 | 検出された問題を受け入れるか、直してから出すか |
| 定義済みの閾値に対する合否判定               | その閾値をいくつにするか、例外を認めるか       |
| 決められた環境へのデプロイ手順の実行         | いつ・どの範囲に出すか                         |

判定基準を言葉にできていない段階でゲートを自動化すると、機械は「基準がないこと」を隠したまま通してしまう。まず基準を書き、一意に決まると確認できたものだけを自動化する。

残った判断を人間が何に照らして下すかは [refined-engineer-judgment-principles](refined-engineer-judgment-principles.md) の領分。
