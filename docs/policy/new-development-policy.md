# 新規開発ポリシー（グリーンフィールド）

新規開発——システム・モジュール・境界づけられたコンテキストを **0 から立ち上げる**とき——の「進め方」で判断が分かれる事柄に、我々の既定の立場を declare する。判断の上位原則 [refined-engineer-judgment-principles](refined-engineer-judgment-principles.md)（特に**詳細の決定を遅らせる**・**必要になるまで作らない**）を継承し、マクロ構造は [application-architecture-policy](application-architecture-policy.md) を継承する。本ポリシーは**それらに含まれない新規開発固有の差分だけ**を declare する。

教科書的なテクニック解説は書かない。載せるのは「**判断が分かれるが、我々はこうする**」という既定の立場だけである。いずれの立場も既定であり、文脈が強ければ覆る。

> [!NOTE]
> 立ち上げの**進め方（手順）**は [new-development-guide](../guide/new-development-guide.md) に委ねる。本ポリシーは立場だけを declare し、手順は持たない。

## 対象読者

新しいシステム・モジュールを 0 から設計／実装する人・AIエージェントが、立ち上げの進め方で迷ったとき。

## 曳光弾（walking skeleton）を既定にする——薄い縦スライスを先に通す

**既定：レイヤーごとの水平な積み上げ・big-design-up-front ではなく、入口から出口まで動く薄い縦スライス（曳光弾＝tracer bullet）を最初に1本通し、本番品質で残したうえで以降そこへ肉付けする。**

判断が分かれる点：水平（各レイヤーを層ごとに作り込んでから繋ぐ）か、垂直（薄い1経路を端から端まで先に通す）か。我々は**垂直を既定**にする——早期に統合してフィードバックを得られ、「全部作ったが繋がらない」を避けられるため。

| ❌ NG                                                              | ✅ OK                                                                  |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 認証基盤・DB スキーマ・共通ライブラリを作り込んでから画面へ繋ぐ    | 入口 → ユースケース → 永続化スタブ → 出力の1経路を先に通し、肉付けする |
| 通せる形になるまで DB 製品・外部サービスの選定を終わらせようとする | スタブで代用して先に通し、選定は確信を持てるまで遅らせる               |

## スパイクは使い捨て——本番に昇格させない

**既定：不確実な技術的問いは、使い捨てのスパイク（throwaway prototype）で答えだけを得て破棄し、本実装はやり直す。スパイクのコードを「もったいない」と育てて本番にしない。**

判断が分かれる点：学習のために書いたコードを育てるか、捨てるか。我々は**捨てる**——学習目的のコードはテスト・エラー処理・設計という品質の前提を欠いており、育てると負債の土台になる（コードは資産ではなく負債）。

曳光弾とスパイクは、どちらも「薄く早く動かす」ため実務で最も混同されやすい。区別の起点は**目的**であり、そこから扱いが決まる。

| 観点         | 曳光弾（残す）                       | スパイク（捨てる）                   |
| ------------ | ------------------------------------ | ------------------------------------ |
| 目的         | 入口から出口までの到達経路を作る     | 特定の不確実性を1つ潰す              |
| コードの扱い | 本番品質で残し、以降そこへ肉付けする | 答えを得たら破棄し、本実装は書き直す |
| テスト       | 書く（残るコードだから）             | 書かない（残さないから）             |
| 完了の合図   | 薄い1経路が端から端まで動いた        | 問いに答えが出た                     |

| ❌ NG                                                          | ✅ OK                                                      |
| -------------------------------------------------------------- | ---------------------------------------------------------- |
| 検証で書いたコードが動いたので、テストを後付けして本実装にする | 得た答えだけを残してコードは捨て、本実装は設計からやり直す |
| 曳光弾を「どうせ後で書き直す」と割り切って雑に書く             | 曳光弾は最初から本番品質で書く                             |

## ドメイン／コアから着手する——FW・DB から始めない

**既定：新規開発は FW 選定・DB スキーマ・画面から書き始めず、ドメインモデル（コアのビジネスロジック）から書き始める。**

判断が分かれる点：何から書くか。我々は**コアから**——詳細を先に決めるとドメインが詳細に従属し、後から差し替えられなくなる。詳細は境界の外に置き、決定を遅らせる。

| ❌ NG                                                       | ✅ OK                                                          |
| ----------------------------------------------------------- | -------------------------------------------------------------- |
| FW のプロジェクト生成 → テーブル定義 → 画面、の順に着手する | 業務ルールを持つドメインモデルから書き、詳細はスタブで代用する |
| 業務ルールをコントローラや ORM エンティティの中に直接書く   | ドメインは FW に依存しない素のコードで書き、アダプタ越しに繋ぐ |

## ディレクトリ構成の方針を先を見越して最初に決める

**既定：新規開発の初期に、ディレクトリ構成の*方針*を場当たりに育てるのではなく、プロジェクトの成長を見越して意図的に選ぶ。**

判断が分かれる点：構成は必要に応じて育つに任せるか、先に方針を決めるか。我々は**先に決める**——ディレクトリ構成は後から変えるほど高くつき（広範なファイル移動と import 修正、レビュー差分の肥大）、最初の方針が以後「どこに置くか」の基準になるからだ。

**この節は、冒頭で継承した「詳細の決定を遅らせる」の例外である。** 遅延が得になるのは、境界を引けば後から差し替えられる詳細に限る。差し替えられるなら、待つほど判断材料が増え、待ったコストは増えない。ディレクトリ構成は差し替えの対象ではなく、境界をどこに置くかという**器そのもの**なので、待っても選択肢は増えず移動コストだけが上がる。

| 対象                   | 既定       | 理由                                       |
| ---------------------- | ---------- | ------------------------------------------ |
| DB・FW・外部サービス   | 遅らせる   | 境界の外に置けば後から差し替えられる       |
| ディレクトリ構成の方針 | 先に決める | 差し替え対象ではなく、待つほど移動が増える |

ただし最適な構成はプロジェクトによって大きく異なり、アプローチも複数ある（技術レイヤー型／機能・ドメイン型／その混成 …）。**どのアプローチをどう選ぶかの具体は [directory-structure-guide](../guide/directory-structure-guide.md) に委ね、本ポリシーは「先を見越して意図的に決める」立場だけを declare する。** 方向性の既定は、ディレクトリ・レイヤー構成に FW ではなくドメイン（何のためのシステムか）を語らせること（Screaming Architecture）である。

| ❌ NG                                                       | ✅ OK                                                            |
| ----------------------------------------------------------- | ---------------------------------------------------------------- |
| 置き場に迷うたびディレクトリを足し、構成を後から育てる      | 立ち上げ時に「何を軸に切るか」を決め、以後はその基準で判断する   |
| `controllers/` `services/` `models/` と FW の語彙で構成する | ディレクトリ名がドメイン（何のためのシステムか）を語る構成にする |

> [!NOTE]
> このプロジェクトの**具体的な**ディレクトリ構成は設計の領分であり、[design-hub](../design-hub.md) 配下の設計書が SSOT。本ポリシーは方針（先を見越して意図的に決める）だけを declare し、具体パスは持たない。
