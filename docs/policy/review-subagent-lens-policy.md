# レビュー系 subagent のレンズ分けポリシー

AIエージェントが、`*-reviewer-agent` を新設・編集するとき、または `*-review` Skill を並列起動の複数レンズ（並列に起動する subagent 1回分の担当範囲）に分けようとするときに参照する。「どう割るか」を毎回一から考えると、割り方の基準が先例の模倣頼みになり、中心の観点の担当が抜け落ちても気づけない（#486 で /code-review の「ロジックの正しさ」の担当が立っていなかった実例）。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - **分けるかどうかは、1体の取りこぼしで決める。** 既定は1体のまま。欠陥を仕込んだ対象で1体が取りこぼしたときだけ分ける
> - **レンズは観点一覧の行を束ねて作る。** 束ね方・統合・ファイル数の判断は下の早見表の問いを通す
> - **束ねる軸はポリシーの節ではなく「対象に向ける問いの種類」にする。** 節ごとに割ると、レビューの中心観点の担当が抜けても気づけない（#486）
> - **レンズに分けるレビューは採点しない。** 観点ごとの準拠／違反と severity 付きの指摘で出す

## 早見表：新設・編集の前に通す問い

- **⓪ 1体で取りこぼしを確かめたか**：確かめずに分けない（「分けるかどうかは1体の取りこぼしで決める」）
- **① レンズの元になる観点一覧はあるか**：無ければ先に作る（「レンズは観点一覧の観点を束ねて作る」）
- **② 束ねる軸はポリシーの節になっていないか**：「対象に向ける問い」で束ねているか（「束ね方は『対象に向ける問い』ごとにする」）
- **③ 統合で判定を決め直していないか**：メインセッションが判断するのは、レンズ間の食い違いの裁定だけか（「統合はメインセッションで行い、判断は食い違いの裁定だけにする」）
- **④ agent ファイルを増やす前に、実際に2つ以上の Skill が同じレンズを呼んでいるか**：呼んでいないなら1ファイルのまま引数で渡す（「agent ファイルは既定で1つにする」）
- **⑤ 採点（点数・合算）を持ち込んでいないか**：レンズに分けるレビューは採点しない

## 分けるかどうかは1体の取りこぼしで決める

1体の subagent で完結しているレビューは、**既定では分けない。** 次のどちらかに当たるときだけ、レンズに分ける。

- 欠陥を仕込んだ対象を1体に3回掛け、1回でも取りこぼした
- 実運用で、1体が見落とした欠陥の実例がある

仕込む欠陥は、分けて拾いたい種類にする。そのレビューで一番見落としたくない観点の欠陥である。拾いやすい欠陥を仕込んでも、分ける必要があるかは測れない。

分けると、起動の回数と費用はレンズの数だけ確実に増える。一方、見落としが減る効果は、1体が取りこぼさない限り測れない。下の「1回の起動に1つの問い」は分けた後の束ね方の基準であり、それだけを理由に分けない。

## レンズは観点一覧の観点を束ねて作る

レンズ分けレビューを新設・改修するときは、先に**観点一覧**（レビューで見る観点を1行ずつ並べた表。例：`.claude/skills/code-review/references/review-criteria.md`）を用意する。まだポリシーに基準の無い観点も、一覧には行として載せる——載せなければ、その観点はどのレンズにも入りようがなく、存在ごと消える。

観点一覧は Skill 側の `references/` に置き、観点をレンズへ束ねた「レンズ→担当観点」の対応表は agent 定義側に置く（`code-reviewer-agent.md` の「レンズ一覧と担当観点」がこの形）。観点一覧が唯一の正典で、対応表側に観点の判定基準を書き写さない。

レンズは、この一覧の行を1つ以上束ねて作る。**ポリシーの節（ファイル単位）で束ねない。** ポリシーの節は文書の都合で切られており、レビュー対象が実際に壊れる観点の重心とは一致しない。`/code-review` は当初ポリシーの節でレンズを割ったところ、レビューの中心である「ロジックの正しさ（バグ探索）」が独立した担当を持たず、どのレンズにも埋もれた（#486）。

**穴出し**とは、観点一覧の行のうち、どのレンズの担当観点にも入っていない行が無いかの確認である。観点一覧と「レンズ→担当観点」の対応表を突き合わせて行う。新しい観点を一覧に足したら、対応表のどのレンズに入れるかを同時に決める。

## 束ね方は「対象に向ける問い」ごとにする

観点を束ねる軸は、対象に向ける**問いの種類**——読み方の違い——にする。

- ❌ ポリシーの節ごと（例：`documentation-policy` 担当レンズ／`design-doc-policy` 担当レンズ）：文書の切れ目で割ってしまい、複数の節にまたがる中心の観点の担当が立たない
- ✅ 問いの種類ごと：**疑って読む**（性善説を捨て、壊れる入力・分岐を能動的に探す）／**攻撃者の目で読む**（悪用できる隙を探す）／**文書・規約と見比べる**（書かれた基準と実物を1行ずつ照合する）

1回の起動に1つの問いだけを持たせることで、見落としが減る。複数の問いを1レンズに混ぜると、疑って読む注意力が規約照合に流れ、一番見つけたい欠陥への集中が薄まる。

各レンズが向ける問いは、そのレンズを担当する agent 定義に1文で書く。

## 統合はメインセッションで行い、判断は食い違いの裁定だけにする

各レンズの実行後、結果をまとめる**統合**はメインセッション（`/code-review` などの呼び出し側）が行う。統合でやってよいのは、レンズの出力を集約してフォーマットを揃えることと、下に定める**食い違いの裁定**だけである。**判定・severity・修正案をメインセッションが決め直さない**——それぞれレンズ側が該当コードを見て決め切ったものであり、メインセッションが再評価すると、レンズを分けた意味（1レンズ1問いへの集中）が統合の段階で薄まる。

統合を opus の subagent に任せない。メインセッションが直接行う——統合の判断は食い違いの裁定に限られ、別モデルを挟んでも待ち時間が伸びるだけである。

### 食い違いは2段で裁く

**食い違い**とは、同じ箇所に別々のレンズが逆向きの指摘（足せと削れ、など）を出した状態をいう。並列のレンズは互いの出力を見られないので、食い違いは統合でしか解けない。両方を並べたまま流すと、どちらを採るかを下流の誰も決めない。

1. **AI が裁定する（既定）**：どちらを採るかを、ポリシーの条文を引用して決める。該当するポリシーが無ければ `refined-engineer-judgment-principles` に照らして決める。捨てた指摘と根拠は報告に残す。迷ったら AI が決める——指摘の修正は git で戻せるので、誤っても失うものが小さい
2. **人間に回す（例外）**：次のどちらかに当たるときだけ、その食い違い1件を `issue:needs-human-decision` として起票する。ほかの指摘の処理は止めない
   - どちらを採っても、要件やプロダクトの方針が変わる
   - どちらかを採ると、取り消せない操作や外部に出る操作になる

## agent ファイルは既定で1つにする

レンズごとに agent ファイルを分けない。既定は**1つの agent ファイルにレンズ名を引数で渡す**構成にする（`code-reviewer-agent` はこの形）。共通の手順・前提を1か所で直せ、まだ使い回されていないレンズを先回りして分けても得るものが無い。

**反転条件**：同じレンズを2つ以上の Skill が実際に呼ぶようになったとき、そのレンズだけを別ファイルに切り出してよい。「将来複数の Skill から呼ばれそうだから」という見込みでは切り出さない——実際に2つ以上の Skill が呼んでいるかは、コードを見れば確かめられる外形的な事実である。

## レンズに分けるレビューは採点しない

レンズに分けたレビューは、点数（合計点・平均点等）を出さない。出力は、観点ごとの**準拠／違反**の判定と、違反には severity（Critical / Recommended / Suggested 等、レビュー対象の既存の分類に従う）を付けた指摘だけにする。採点を残すと、レンズごとの点数を合算する手順が統合に要り、統合に食い違いの裁定以外の判断が入る（前節「統合はメインセッションで行い、判断は食い違いの裁定だけにする」に反する）。

## 適用範囲

このポリシーは、frontmatter 冒頭の `hook.applies-to` が指す agent 定義・Skill 定義を編集する前に自動で差し込まれる。

既定は、命名にかかわらず**レンズに分けて並列起動するレビューには本ポリシーに従う**。レンズ分けするレビューを新しく作ったら、そのパスを `applies-to` に足す。単一の subagent でレビューを完結させる仕組みは対象外とする。ただし「分けるかどうかは1体の取りこぼしで決める」の節だけは、1体のレビューをレンズに分けるか検討するときにも当てる。

## 上位原則との関係

本ポリシーは横断原則の具体化である。判断に迷ったら [refined-engineer-judgment-principles](refined-engineer-judgment-principles.md) に立ち返る。

- **判断軸は「既定値＋反転条件」で与える**：レンズに分けるかどうかは、既定を1体とし、「取りこぼしたか」という作文では満たせない事実で反転する。agent ファイルを分けるかどうかは、見込みではなく「2つ以上の Skill が実際に呼んでいるか」という外形的事実で判定する。食い違いの裁定も、既定を AI、人間に回すのを名指しした例外だけにする
- **振り分け順**（policy-driven-development-policy）：レンズの割り方は「どれを選ぶか」の立場なので Policy に置き、統合の具体的な手順（How）は各レビュー Skill 側に書く
