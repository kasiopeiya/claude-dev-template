# 設計書作成ポリシー

**AIエージェントが、設計書を書く・レビューし、良い設計書と悪い設計書を見分ける基準を知りたいとき**に参照するドキュメント。読み終えたとき「良い設計書とはこういうもの・悪い設計書とはこういうもの」を自分の言葉で言えるようになることが、この文書の目的。**構成の書き方（How）**は [design-doc.md](../../.claude/rules/design-doc.md)（Rule）が定める。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - **良い設計書**＝コードから読み取れないこと（全体の構造・流れ・なぜ）だけを直感的に示した文書。**悪い設計書**＝コードを読めば分かること（実装詳細・手順・仕様）を書き写した文書（保守段階で二重管理になり腐る）
> - What（振る舞い）か設計かで迷ったら、項目を「振る舞い・構造と理由・具体値」の3層に割ってから振り分ける。設計書に残すのは構造・流れ・なぜだけ
> - 却下案（ADR 対象の判断で、なぜBでなくAか）は設計書に書かず ADR へ出す。まだ無いものは書かない

## 基盤との関係：documentation-policy を継承し、差分だけを足す

設計書も文書なので、**まず [documentation-policy](documentation-policy.md) と、人間が画面で読む文書に上乗せする [documentation-policy-for-humans](documentation-policy-for-humans.md) の全原則に従う**。本ポリシーはそれを再掲せず、**設計書という種別に固有の指針だけ**を上乗せする。runbook-policy が documentation-policy に対して持つ関係と同じ、独立・単体完結の専用ポリシー。

## 前提：本ポリシーが定義するのは「保守され続ける設計書」である

**具体値だらけの設計書は、保守段階でコードと同じ情報を二重に抱える「二重管理」になり、必ず腐る。**

ただし一次資料として作ること自体は否定しない（初期設計の検討・合意のスナップショットなど）。本ポリシーが定義するのは、その先の**コードと共に生き続け、保守され続ける設計書**。

| 設計書の種類                               | 具体値だらけでよいか | 本ポリシーの対象    |
| ------------------------------------------ | -------------------- | ------------------- |
| 一次資料（保守しない、作った時点の記録）   | ✅ よい              | — 対象外            |
| 保守され続ける設計書（コードと共に生きる） | ❌ 二重管理で腐る    | ✅ 本ポリシーが定義 |

## 定義：良い設計書とは「コードから読み取れないこと」を直感的に示した文書である

良い設計書か悪い設計書かは、次の理屈で決まる。

1. **良い設計書とは、コードからは読み取れないことが書かれた文書**（容易に読み取れないことを含む）。コードが SSoT（Single Source of Truth）だから、コードを読めば分かることの書き写しは、前述の二重管理＝悪い設計書にすぎない
2. 大局的な**構成や関係性**は、コードからは容易に読み取れない（何ファイルも追って初めて頭の中で再構築できる）
3. 構成や関係は、**図表で示すのが最も直感的でわかりやすい**（documentation-policy「可視化されていないドキュメントは怠慢」）
4. ゆえに、**良い設計書は構成・関係・流れを図表で直感的に示す**

「容易に読み取れない」の中身は**散在**である。1ファイルずつ読めば各行の意味は分かるが、全体を一覧して把握することはできない——このとき、散らばったものを1枚に集めた**一覧そのものに価値がある**。だから判定は「コードに書いてあるか」ではなく **「集約に価値があるか」** で行う。集約の形は図とは限らず、表でもよい（例：CI が何を検査しているかのジョブ一覧）。ただし置くのは概要だけで、各行の中身（個々のルール・閾値）はコードが正なので書かない。

> [!IMPORTANT]
> **（AI・必須）** これは「図表**だけ**書け」という意味ではない。**設計書を削っていったとき、最後に残すべきは図表である** という意味である。人は文章より図表を見る。WHY（なぜ）も図の注記・吹き出しに書き込めるので、図表を最優先にしても「なぜ」は失われない。**削るときは文章から先に削り、図表を本体として残す。**

良い設計書と悪い設計書は、次の軸で見分けられる。

| 観点 | ✅ 良い設計書                                                | ❌ 悪い設計書                                                    |
| ---- | ------------------------------------------------------------ | ---------------------------------------------------------------- |
| 中身 | コードに書いていない／容易に読めないこと（構造・流れ・なぜ） | コードを読めば分かること（実装詳細・手順・仕様）を書き写している |
| 主役 | 図表が主役、文章は補足                                       | 文章の壁。図がない、または文章を箱に詰め替えただけの図           |
| なぜ | 冒頭の基本方針から、個々の判断が演繹的に読める               | 判断が並ぶだけで、どういう考え方から来たのか読めない             |
| 寿命 | コードと二重管理にならず腐りにくい                           | コードと重複し、変更のたびに片方が陳腐化する                     |

## 悪い設計書の典型：コードに書いてあることを混入させる

悪い設計書の最大の症状は **混入**——コードや他文書に居場所がある情報を、設計書に書き写してしまうこと。次のものは設計書に**混入させない**。それぞれ別の居場所がある。

| 混ぜないもの | 性質                                                 | 正しい居場所                                      |
| ------------ | ---------------------------------------------------- | ------------------------------------------------- |
| 手順         | 行動と再現（セットアップ・デプロイ・運用・障害対応） | 手順書 → [runbook-policy](runbook-policy.md)      |
| 仕様         | 振る舞いの契約・入出力の網羅（WHATの詳細）           | 業務What→requirements.md／契約→型＋テスト／コード |
| 実装詳細     | 具体ロジック・命名・行レベルの中身                   | コード（SSoT）                                    |

> [!IMPORTANT]
> **（AI・必須）** 設計書を書く・レビューするとき、各記述に **「これはコードを読めば分かるか？」** を問う。分かるなら、次に **「1箇所ずつしか読めず、一覧できないものか？」** を問う。一覧できないなら、概要だけを表に置いてよい。そうでなければ設計書に書かない（書けば二重管理で腐る＝悪い設計書化する）。手順は手順書へ、仕様の網羅は業務Whatなら requirements.md・技術契約なら型＋テストへ、実装詳細はコードへ逃がす。

## 迷ったら：What（振る舞い）か設計か（項目を分解して振り分ける）

「これは What（振る舞い）か設計か」で迷う項目は多い。迷う原因は、**項目名が「振る舞い（What）」「構造・なぜ（How/Why）」「具体値」の3層を混ぜて含んでいる**こと。項目を丸ごと振り分けようとするから割れない。**まず層に分解すれば、各層の行き先は一意に決まる。**（ここで決めるのは内容の行き先）

What はさらに2つの居場所に分かれる——**業務用語で書けるビジネスの振る舞いは requirements.md、コード読者向けの入出力・エラー契約は型＋テスト**。専用の仕様書 markdown は作らない（型・テストが実行可能な SSoT であり、markdown に書き写すと二重管理で腐る）。

**例外は、外部への納品物になるインターフェース仕様書だけ**（`docs/design/interface-specification.md`）。他システムとの接続や他社への展開では、契約書そのものが成果物として要求され、相手が型・テストを読める前提に立てない。この1文書に限り、入出力・エラー契約の網羅を markdown に書いてよい。二重管理は承知のうえで受け入れる——**正はあくまで実装（型＋テスト）**であり、乖離が見つかったら仕様書を実装に合わせる。

| 行き先                      | 何を書くか                             | ひとことテスト                           |
| --------------------------- | -------------------------------------- | ---------------------------------------- |
| requirements.md（業務What） | 正しい振る舞い・業務ルール（業務用語） | 外から観測でき、業務で検証できるか？     |
| 型＋テスト（技術契約）      | 入出力・エラーの契約（コード読者向け） | 型・テストで表現・検証できるか？         |
| 設計書                      | 構造・流れ・なぜ（How/Why）            | コードを読んでも分からない作り・理由か？ |
| コード/設定                 | 具体値・実装そのもの（SSoT）           | 値が変わるたびに直る具体物か？           |

同じ項目名でも、層ごとに行き先が分かれる：

| 項目             | What：振る舞い・契約（業務→requirements.md／契約→型＋テスト） | 設計書（How/Why・構造）                                          | コード/設定（具体値）            |
| ---------------- | ------------------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------- |
| 環境変数         | （振る舞いを定義する変数なら）その契約                        | 何を設定軸にし、なぜ外出しするか                                 | 変数名と値（`.env`・パラメータ） |
| ビジネスロジック | 業務ルール＝正しい結果（例：ポイント1%・有効期限1年）         | 実現の流れ（シーケンス図）・なぜその方式か                       | 計算・判定の実装                 |
| API              | 入力／出力／エラーの契約                                      | 認証・認可の流れ、コンポーネント連携                             | ハンドラ実装                     |
| データモデル     | 各項目の制約・整合性ルール                                    | エンティティ関係（ER図）・なぜこのモデルか                       | スキーマ定義（DDL）              |
| 画面／UI         | 表示・入力・バリデーション・画面遷移のルール（操作→遷移先）   | 画面の状態管理・コンポーネント構造・なぜこの画面分割／遷移設計か | コンポーネント・ルーティング実装 |
| 非機能           | 可用性・性能の目標値（要件）                                  | 目標をどう達成するかの方式・トレードオフ                         | タイムアウト等の設定値           |
| エラー定義       | 呼び出し側が受け取るエラー契約                                | 失敗モードの俯瞰・なぜこの分類か                                 | エラーコード値・実装             |

**図かどうかは行き先を決めない。** 画面遷移図・業務フロー図は「仕様（外から観測できる振る舞い）を図にしたもの」で、図でも仕様。「設計書の主役は図表」は*設計書の中での話*にすぎない。振り分けは形式（図か文か）ではなく **「外から観測・検証できる振る舞いか／内部の構造・なぜか」** で行う。

> [!IMPORTANT]
> **（AI・必須）** 迷ったら項目を丸ごとどちらかに入れようとせず、まず3層に割る。設計書に残すのは「構造・流れ・なぜ」だけ——振る舞い（What）は業務なら requirements.md・契約なら型／テストへ、具体値はコードへ逃がす（混入させない）。

## まだ無いものは書かない

仕様駆動開発では、これから実装するつもりのことまで設計書に書いてしまいやすい。だが未実装の記述は、実装が変われば嘘になり、実装されなければ嘘のまま残る。**設計書に書くのは、いま存在するものだけ**（原則集「YAGNI」）。予定は Issue に置く。

例外は2つある。1つは、意図的にやらないと決めたこと。これは「前提と制約」に書く。

もう1つは、**入れ物は実在するが中身がまだ空**という状態。入れ物は現に存在するので図に描き、中身が無いことは `TODO(#31)` のように Issue 番号を添えて示す（documentation-policy「進捗・経過・状態は Issue 化し番号で残す」）。「※現在は中身なし」のような番号の無い進捗表現は書かない。

## 現在の理由は設計書、比較衡量と経緯は ADR

設計書が言うのは **現在の設計の「なぜ」**（＝なぜ今この構造か）だけである。**なぜ B ではなく A を選んだか**という比較衡量と、**なぜ旧設計から変えたか**という経緯は ADR（`docs/adr/`）の領分。混ぜると設計書に検討の履歴が溜まり、「現在の姿だけ読みたい読者」が困る（documentation-policy「書き手の事情は本文に書かない」と同根）。

- **なぜ今この構造・方式か（現在の理由）**：設計書（基本方針・各セクション）
- ADR 対象の判断で、なぜ B ではなく A を選んだか（**却下案**）：ADR（`docs/adr/`）
- **なぜ旧設計から変えたか（意思決定の経緯）**：ADR（`docs/adr/`）

**却下案かどうかは、比べている判断の重さで決まる。** ADR 対象の判断——アーキテクチャの水準で、後から変えるのが高くつくもの——について、採らなかった案の優劣を論じていれば却下案である。それより軽い判断は、理由が「別の形にするとこう壊れる」という対比で書かれていても現在の理由なので、設計書に残す。

採用した案の代償（「〜になるが〜を優先した」）も却下案ではない。「受け入れた不便」なので「前提と制約」に書く。

> [!IMPORTANT]
> **（AI・必須）** **却下案を設計書に書かない。** ADR 対象の決定なら ADR へ書き、設計書からはリンクする。ADR 対象でない小さな判断の却下案は、**どこにも書かない**（記録は失われる）。これは意図した取引である——却下案は現物と突き合わせて検証できないので、設計書に置くと腐っても誰も気づかない。蒸し返しコストが高い決定は ADR の判定基準に引っかかるので、失うのは蒸し返されても安い判断だけになる。

## 前提と制約は1節にまとめ、技術的制約と組織の制約に分ける

設計の解説ではなく**変更しようとする人への警告**は、性質が同じなので1節にまとめる。

節の中は `###` の2小節に分ける。自分たちの判断で決めた制約と、外から課されて動かせない制約とでは、読んだ人が取れる手が違うからである（前者は設計を変えれば消せる。後者は消せないので、その中でどう作るかを考えることになる）。該当がなければ小節ごとに「**なし**」＋一言理由を書いて閉じる。

| 小節           | 書くこと                                                       | 例                                                                                                              |
| -------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **技術的制約** | 触ると壊れる前提・意図的にやらないと決めたこと・受け入れた不便 | リポジトリ設定で required check が登録されていること／stg・prd は持たない／レビュー時点で deploy が未検証になる |
| **組織の制約** | 組織・ガバナンスから課され、こちらでは変えられない制約         | リソース命名規約・タグ規則・暗号化要件・リージョン制約                                                          |

「意図的にやらないこと」と却下案の境界は、**判断の重さ**で分かれる。ADR 対象の判断について「他案と比べて劣るから」と書きたくなったらそれは却下案なので ADR へ出す。それ以外は現在の状態なので設計書に残す。

---

> [!IMPORTANT]
> 本ポリシーで最も重要な原則。
>
> - **良い設計書はコードから読み取れないことだけを書く**：コードを読めば分かること（実装詳細・手順・仕様）の混入が悪い設計書（保守段階で二重管理になり腐る）。ただし保守しない一次資料は対象外
> - **迷ったら3層に割る**：振る舞い（What）は requirements.md か型＋テストへ、具体値はコードへ。設計書に残すのは構造・流れ・なぜだけ
> - **却下案とまだ無いものは書かない**：ADR 対象の判断の比較は ADR へ出す。予定は Issue に置く
