# ドキュメント作成ポリシー

ドキュメントを作成・編集・レビューするときの共通の土台を定める。手順書・設計書・要件定義書といった文書種別ごとの差分は、本ポリシーを継承した各ポリシーが定める。

**良いドキュメントとは、読まれるドキュメントである。** 読まれるのは、ぱっと見がシンプルで「これなら読めそうだ」と思える文書だけである。正しくても、網羅していても、読まれなければ価値は生まれない。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - **対象読者と目的が全てを決定する。** 誰が何のために読むかで、書く内容も説明の深さも変わる
> - **「なぜ」を必ず書く。** 理由がなければ読者は変更してよいか判断できない
> - **図表で可視化する。** 文章はほとんど読まれない。行と列に収まるなら表、分岐・ループがあるなら図にする

## 対象読者

Markdown でドキュメントを書く／レビューする人 / AIエージェントが、何を書き・何を削り・どう可視化するか迷ったとき。

> [!IMPORTANT]
> **（AI・必須）** Markdown 文書を新規作成・大きく加筆したら、報告前に `/quick-doc-review` を確認なしで自動実行すること。本ポリシーは読んで守るものなので、書き上げた後に照合しないと守れたか分からない。

> [!IMPORTANT]
> **（AI・必須）** 本ポリシーを改訂したら、`.claude/skills/quick-doc-review/SKILL.md` のチェック項目の追従要否を判断すること。同スキルは速度のため本ポリシーから判定基準を書き下した派生コピーであり、追従しないと**どのゲートも通らない規約が生まれる**。載せないと判断した場合は、その理由を同スキルの「チェック項目に載せない規約と理由」に書く。

## 基本原則

### ドキュメンテーションとプログラミングは本質的に同じである

両者は多くの本質を共有する。プログラミングで重要な原則は、ドキュメンテーションにもそのまま当てはまる。

| 観点       | プログラミング                 | ドキュメンテーション         |
| ---------- | ------------------------------ | ---------------------------- |
| 目的       | SRP原則、アクターと目的が重要  | 誰に何を伝えるかが全て       |
| ネーミング | 変数名・関数名が可読性を決める | 見出し・用語が可読性を決める |
| 保守性     | 変更容易性を考慮した設計       | 更新容易性を考慮した構造     |
| 重複       | DRY原則                        | DRY原則                      |
| 抽象化     | 適切な粒度での分割             | Progressive Disclosure       |
| シンプルさ | 短く明快なコードが良い         | 短く明快な文章が良い         |

> [!TIP]
> **（AI・推奨）** 迷ったら「これがコードならどう書くか？」と自問する。

### 対象読者と目的が全てを決定する

対象読者と目的が異なれば、書く内容も書き方も異なる。ドキュメント作成において最も重要な本質は「対象」と「目的」。

#### 対象読者は「想定シーン」として具体化する

対象読者は役割名だけ（例：開発者）では不十分。「◯◯な人が△△したいとき」という想定シーンを一文で書く。読者の前提知識と目的をまとめて表現することで、捜索者が「自分のための文書か」を即座に判断できる。

|         | 例                                                                            |
| ------- | ----------------------------------------------------------------------------- |
| ❌ 弱い | アプリケーション/インフラ開発者                                               |
| ✅ 強い | RDB設計の経験はあるがAuroraは初見の開発者が、設計思想と選定理由を知りたいとき |

> [!TIP]
> **（AI・推奨）** 具体化の判断基準は「その読者像によって書き方が変わるか？」である。用語解説の要否や説明の深さが変わるなら書く。

#### レビュー：設定した対象読者と表現が合っているか確認する

文中の専門用語・前提知識を、設定した読者像が「知っている」前提と照合する。ズレは双方向に起きるので両方見る。読者像が明示されていなければ、まずその不在を指摘する。

| ズレの方向 | 症状                                     | 直し方               |
| ---------- | ---------------------------------------- | -------------------- |
| 説明不足   | 読者が知らないはずの用語を補足なしで使用 | 補足レイヤーに逃がす |
| 過剰説明   | 読者が当然知っている用語をくどく説明     | 削る                 |
| 深さのズレ | 目的に対し浅すぎる／細かすぎる           | 必要な深さに合わせる |

### 良いドキュメントとは読者目線のドキュメントである

読者が抱くであろう疑問を先回りして提示する。

例：「外部接続用クラスは単体テストを実施しない」と書いたら、次の見出しを `なぜ外部接続用クラスは単体テストを実施しないのか？` とする。

### 本文には読者が使う情報だけを書く——書き手の事情は書かない

**書き手の事情を本文に書いてはならない。** 書き手の事情とは、進捗・記載判断・文書の構成のように、**読者は使わないのに、書いた側だけが親切だと思っている情報**である。

| 書き手の事情     | ❌ 本文に直接書く                                                                          | ✅ どうするか                       |
| ---------------- | ------------------------------------------------------------------------------------------ | ----------------------------------- |
| 進捗・経過・状態 | 「※この節は作成中」「暫定。今後変更の可能性あり」「旧仕様では〜だった」                    | Issue化し `TODO(#300)` と番号で残す |
| 記載・作図の判断 | 「省略理由：〜のため」「この表を図にしない理由は〜」「〜も行にしているのは〜だからである」 | ユーザーへの回答に書く              |
| 文書の構成説明   | 「図＝流れ、下表＝相手」「〜で対応づけている」「上の表は〜を示す」「以下では〜を説明する」 | 消す（逃がし先はない）              |

<details>
<summary>書き手の事情を本文に書けない理由</summary>

- **進捗・経過・状態：** 修正されないまま残り続ける——「工事中」と書かれたページが永遠に工事中なのは、どこにでもある光景。いつ外すべきかは書いた本人すら分からなくなる
- **記載・作図の判断：** どう書くか決め終わった後の読者には効かない
- **文書の構成説明：** 読者が図表を見れば分かることの言い換えでしかない

</details>

対象は語だけではない。**色分け・バッジ・ハイライトなど、視覚表現で「今回追加した箇所」を示すのも同じ禁止対象**である。読者には意味が伝わらないまま残り、時間が経てば事実としても誤りになる。

**文書種別による例外は作らない。** サンプル・テンプレート・要件定義書も対象である。

> [!IMPORTANT]
> **（AI・必須）** 書き手の事情を本文に書いてよいのは、人間から明示の指示があったときだけ。指示がなければ書かない。「親切のつもりの注記」を、読者が読み飛ばす行にしない。

## 構造設計

### 文書を分割する（Progressive Disclosure）

AIおよび人間が、必要な時に必要なドキュメントだけを読み込める構造にする。1つのドキュメントに情報を詰め込みすぎると、コンテキストを圧迫するため避ける。

|       | 例                                                                                            |
| ----- | --------------------------------------------------------------------------------------------- |
| ❌ NG | テスト設計書を1つ作り、全ての情報をまとめる                                                   |
| ✅ OK | 単体テスト・統合テスト・E2Eテストそれぞれの設計書を作り、ハブとなるテスト仕様書からリンクする |

分割検討の目安：600行

分割を検討する際の判断基準

- 独立した関心事が複数含まれているか
- 読者が一度に全てを読む必要があるか
- 特定セクションだけを参照するユースケースがあるか

分割する場合は、ハブとなるドキュメントから個別ドキュメントへリンクする構成にする。

> [!TIP]
> **（AI・推奨）** 600行を超えたドキュメントを編集・作成する際は、分割の要否をユーザーに提案すること。

### 1つの文書の中でも俯瞰を先に置く

ぱっと見のシンプルさは、1つの文書の中でも作れる。**先に俯瞰、あとに詳細**の順に並べれば、開いた瞬間に目に入るのは全体像だけになる。読者の全員が詳細まで知りたいわけではなく、多くは全体像だけを確かめに来るからである。

同種の項目についての詳細が2件以上並ぶなら、その前に1項目1行の俯瞰の一覧を置く。1件では並べて見比べる相手がいないので、俯瞰にならない。

スクロールせずに全体が見える文書を二層にしても、読者の得はない。

| 文書の行数 | 求めること                     |
| ---------- | ------------------------------ |
| 100行以下  | 対象外。素のまま書いてよい     |
| 101〜499行 | 俯瞰の一覧を置けないか検討する |
| 500行超    | 俯瞰の一覧を必ず置く           |

対象は人間が読む文書に限る。AIに全文が読み込まれる文書（Skill・エージェント定義）は、俯瞰も詳細も同時にコンテキストへ載るので、二層にする意味がない。

**必要になるまで作らない（YAGNI）**。文書を1本増やせば、読み・直し・リンクを守るコストが増え続ける。

| 詳細の姿                | 逃がし先                                                                        |
| ----------------------- | ------------------------------------------------------------------------------- |
| 見出しが要らない        | トグルに畳む                                                                    |
| 見出しが要る・600行未満 | 本文に残してよい                                                                |
| 見出しが要る・600行以上 | 別文書へ出すかを[分割の判断基準](#文書を分割するprogressive-disclosure)で決める |

> [!TIP]
> **（AI・推奨）** 101〜499行の文書で俯瞰の一覧を置かないと判断したら、ユーザーへの回答でその旨を提案すること。

> [!IMPORTANT]
> **（AI・必須）** 目次があることは、俯瞰の一覧を置かない理由にならない。目次が示すのは話題だけで、俯瞰の一覧は各項目の中身を1行で示す。

### 500行を超えたら目次を置く

捜索者は見出しの一覧を見て「自分の探している話題があるか」を判断する。目次が無ければ、その判断のために本文をスクロールさせることになる。逆に、**AIに全文が読み込まれる文書は行数によらず対象外**とする。目次の役目は読者を目当ての場所へ飛ばすことだが、全文がまとめてコンテキストに載るなら飛ぶ先を探す必要がないからである。

| 文書                                              | 目次                                   |
| ------------------------------------------------- | -------------------------------------- |
| 人間が読む文書で、500行を超える                   | 必須                                   |
| 人間が読む文書で、500行以下                       | 任意（見出しだけで全体を見渡せるため） |
| AIに全文が読み込まれる文書（Skill・エージェント） | 対象外                                 |

- `## 目次` を対象読者の直後に置く
- `##` 見出しだけをアンカーリンクで並べる。`###` 以降まで載せると、目次そのものが長くなってざっと見渡せなくなる

### 詳細な記載よりシンプルで短い方が良い

いくらわかりやすい文章でも、長い文章は読まれない。プログラミングと同じで、シンプルで短い記載が良いドキュメント。短さの根拠は上位原則にある——「YAGNI——必要になるまで作らない」「Less is more——少ないほど豊か」（[refined-engineer-judgment-principles](refined-engineer-judgment-principles.md)）は文章にもそのまま効く。

> [!TIP]
> 「もっと時間があれば、もっと短い手紙を書けたのだが」——短く書くことは、長く書くことより難しい。

AIは「正しい情報」「網羅した情報」を良いものと誤解し、読者が今必要としない情報まで盛り込みがち。**各文・各行・各語は、その箇所の目的に奉仕するものだけを残す。** 正しいだけの情報・読者の判断を変えない修飾・他の箇所で説明済みの属性は、文章を伸ばすノイズでしかない。

| ❌ NG（冗長）                                                               | ✅ OK（必要十分）                                          |
| --------------------------------------------------------------------------- | ---------------------------------------------------------- |
| DB 初期化 Lambda（DataInitializer・SharedResourceStack 配下）を Invoke する | DB 初期化 Lambda を Invoke する                            |
| ある属性（所属スタック・分類など）を登場のたびに繰り返す                    | その属性を主題とする箇所で一度説明し、他所は名前で参照する |
| 表に該当する全項目を機械的に列挙する                                        | 図や本文で伝わらない、判断に効く項目だけに絞る             |

> [!TIP]
> **（AI・推奨）** **削除テスト**：その語・行・項目を消したとき、この箇所の読者は困るか？ 困らないなら消す。「具体的な方が親切そう」は残す理由にならない。

### 短さと丁寧さが衝突したら、本文を伸ばさず補足レイヤーに逃がす

専門用語の補足を入れたいが本文が長くなる——この衝突は「本文に書く or 省く」の二択で考えるから起きる。第3の道として、本文は短いまま、補足を別レイヤー（トグル `<details>`・用語集へのリンク・脚注）に逃がす。熟練者は読み飛ばし、初学者は開く。両者の要求を同時に満たせる。

そもそも補足の要否は対象読者が決める（「対象読者と目的が全てを決定する」参照）。文書ごとに読者像を定め、その読者が知らない語だけ補足する。全文書を初学者向けに揃える必要はない。

補足する語は次の2条件のAND（両方満たす）で絞る。片方でも欠けたら省く。

- その文書の対象読者が知らない可能性が高い
- その語を理解しないと読者が判断・行動できない

### 「どうやって」より「なぜ」の方がずっと大事

`なぜ` が書かれていないドキュメントほど不親切なものはない。「なぜ」のない設計書では、変更して良いのか判断できず読者が安心できない。

> [!IMPORTANT]
> **（AI・必須）** 設計判断には必ず理由を添えること。

### DRY原則を遵守する、ただし最重要事項は繰り返す

重複記述はメンテナンス性を損なうためDRY原則を遵守する。ただし、最も重要な事項についてはあえて繰り返すことで重要性を強調する。

DRYは1文書内だけでなく**文書間でも守る**。AIは他文書の存在を意識せず同じ説明を書きがちなので、書く前に「この説明はどの文書の主題か」を判断する。避けるべきは、主題でない文書が長い説明を丸ごと抱え込むことである。

ただし**文書間の重複を解く手段はリンクだけではない**。食い違うと実害が出る値・定義・一覧はSSOTへリンクし、理由・考え方は結論だけを短く転記して単体完結させる（「他文書へのリンクは既定で張らない」）。

### 他文書へのリンクは既定で張らない

**他文書へのリンクは、必要と示せたときだけ張る。既定は「張らない」。** 読者がこの文書だけで判断・行動できる状態を守るためである。

リンクは書くのが一瞬なので無料に見えるが、実際には次を払う。

| コスト     | 何が起きるか                                       |
| ---------- | -------------------------------------------------- |
| 壊れる     | リンク先の移動・改名で、参照側が無言で壊れる       |
| 飛ばされる | 読者が文書を行き来する羽目になり、単体完結性を失う |
| ずれる     | リンク先が改訂されると、こちらの文脈が静かに崩れる |

#### リンクするか、転記するかを対象で決める

同じ「他文書に書いてある」でも、対象によって扱いが逆になる。

| 対象                                     | 既定                       | 理由                                                             |
| ---------------------------------------- | -------------------------- | ---------------------------------------------------------------- |
| 値・定義・一覧（食い違うと実害が出る）   | SSOTへリンクする           | 二重に持つと必ず食い違い、どちらが正か読者に分からなくなる       |
| 理由・考え方・立場（読んで納得するもの） | 結論を自分の言葉で転記する | 表現が揺れても実害が小さく、単体完結の価値が上回る（DRYよりSRP） |
| ハブ文書・`docs/reference/` の索引       | 対象外                     | リンクを配ることがその文書の役目                                 |

> [!IMPORTANT]
> **（AI・必須）** **リンク削除テスト**：そのリンクを消したとき、読者はこの文書だけで判断・行動できるか？ できるなら、深掘り用の出口として1本だけ残してよい。**できないなら本文が足りていない**——結論を1〜2文で転記してから、必要ならリンクを残す。リンクを書こうとした時点でこのテストを通すこと。

#### 禁則

| 禁則                                     | ❌ NG                               | ✅ OK                                      |
| ---------------------------------------- | ----------------------------------- | ------------------------------------------ |
| 同一リンク先は1文書に1回まで             | 同じ `[原則](p.md)` を本文で5回張る | 初出で1回だけ張り、以降は文書名だけ書く    |
| リンク先の内部番号・見出しを名指ししない | `[原則2](p.md)` ／ `[x §1](x.md)`   | 内容を一言で転記する（「決定を遅らせる」） |
| 「参照」で終えず、結論を本文に書く       | 「詳細は x.md を参照」で節を終える  | 結論を書き、深掘り先として x.md を添える   |

### ドキュメントもメンテナンス性が重要であると理解する

ドキュメントもコードと同様に保守対象。関数名・ファイル名・クラス名などの直接記述（ハードコード）は、リネーム時の修正コストになる。一方で、抽象化しすぎるとかえって読者の理解を妨げる。

判断基準は「メンテナンスコストを上回る読者価値があるか」。あるなら書く、ないなら書かない。

変更が予想されるものはハードコードしない

- ファイルパス、ファイル名
- 関数名、クラス名、変数名
- モジュール構成、ディレクトリ構造の詳細
- **件数・列挙の転記**（「5つの問い」のような個数、別セクション／別文書にある項目リストの再掲）。項目が増減するたび全転記先の修正が必要になるため、件数を書かず、本体（SSOT）への参照に置き換える（例：「5つの問い」→「早見表の問い」）

ただし、ハブから配下文書へのリンク（相対パス参照）は、ナビゲーションが役目なので許容する。それ以外のリンクは「他文書へのリンクは既定で張らない」に従う。

| 状況                                                 | 判断                                       |
| ---------------------------------------------------- | ------------------------------------------ |
| 抽象表現で十分に意図が伝わる                         | ハードコードしない                         |
| 具体名がないと読者が実装を追えない                   | ハードコードする                           |
| 具体名そのものが議論の対象（API仕様・ADR等）         | ハードコードする                           |
| ハブから配下文書へのリンク                           | 許容する（ナビゲーションが役目）           |
| 単に「具体的な方が親切そう」という理由               | ハードコードしない                         |
| 件数・他所の列挙を本文に転記する（増減で更新が要る） | 転記せず、本体（SSOT）への参照に置き換える |

> [!TIP]
> **（AI・推奨）** 判断に迷ったら「この名前が変わったとき、このドキュメントを更新する価値があるか？」と自問する。Yesなら書く、Noなら抽象化する。

> [!IMPORTANT]
> **（AI・必須）** 個別判断に迷う場合は、勝手に決めず、ユーザーにハードコードするかどうか確認すること。

## 視覚表現

### 可視化されていないドキュメントは怠慢である

文章はほとんど読まれないものと考える。人間はほとんど図や表しか見ていない。図やテーブルを使ってなるべく可視化する。

> [!IMPORTANT]
> **（AI・必須）** ドキュメント作成・レビュー時は、必ず「図や表で可視化できる箇所はないか」を検討すること。不要と判断したら、その理由を**ユーザーへの回答に書く**（本文には書かない）。

> [!IMPORTANT]
> **（AI・必須）** **良い図とは、文章を読まずに構造（関係・流れ・階層・分岐）が一目で掴める図である。** 文章をそのまま箱に詰め替えただけの図は、可視化ではなくノイズなので作らない。

### 図にする前に「逆変換テスト」を通す

> **逆変換テスト**：その図を表・箇条書きに戻したとき、**文章を読まずに構造を掴めるか**。掴めるなら図は要らない。掴めなくなるなら図にする。図の価値は**2次元配置でしか一目で掴めない構造**——分岐・合流・ループ・並行・多対多・階層・状態遷移——にある。

測るのは情報量ではなく**認知負荷**である。Mermaid はテキストで書くので、情報量で測るとどんな図も必ず復元でき、すべての図が「不要」に落ちる。

| 観点   | 図にする（戻すと目で追わないと掴めない） | 図にしない（戻しても一目で掴める） | 戻す先   |
| ------ | ---------------------------------------- | ---------------------------------- | -------- |
| 線の形 | 分岐・合流・ループ・並行がある           | 一直線（A→B→C）                    | 箇条書き |
| 関係   | 多対多・階層・状態遷移がある             | 1対1の対応・単純な列挙             | 表       |

**「図にしない」と決めたら、戻す先まで書く。** 決めずに捨てると、図を弾いたぶんだけ可視化が減る。

### 行と列に収まる構造はデフォルトで表にする（シンプルでも）

可視化の既定値を反転する。**行と列に収まる構造は、まず表にする。** 文章で書くのは表にできない／不自然なときだけである。「文章で書いて、表も検討する」ではなく「表で書いて、表にできないものだけ文章にする」という順序にすることで、ラクな方（文章）に倒れる癖を断つ。

> [!WARNING]
> **（AI・必須）** 「表にする」は可視化の唯一形ではない。**関係・時系列・手順の流れ・階層・状態遷移は、表ではなく図にする**（後述「図種は『情報の形』から選ぶ」で形を選ぶ）。順序・分岐・流れがあるものを表に押し込めない。表化の対象は、行と列に収まる静的な構造に限る。

表が向く「行と列に収まる構造」＝次のどれかに当てはまる（**2項目でも該当する**）：

| 構造のパターン          | 例                                         |
| ----------------------- | ------------------------------------------ |
| 項目 × 属性             | 「AはX、BはY」の形                         |
| 2つ以上の対比・分類     | 旧方式と新方式、許可と禁止                 |
| 静的な条件 → 結果の対応 | 入力Xなら結果Y（分岐・順序を伴わないもの） |

> [!IMPORTANT]
> **（AI・必須）** シンプルさ・短さは表にしない理由にならない。むしろ2行2列の小さな構造こそ、表なら一瞬で読める。「短いから文章で十分」と感じたら、それは表にすべきサインである。

**例外は名指しの1件だけ**：`CLAUDE.md` は全セッションで毎回読み込まれるため、表の罫線とパディングのぶんのトークンを払い続ける。ここでは箇条書きを選んでよい。他の文書（`.claude/skills/` の SKILL.md を含む）は呼ばれたときだけ読まれるので、例外にしない。

> [!TIP]
> **（AI・推奨）** **表化テスト**：「この内容を『項目 → 属性』に分解できるか？」分解できるなら文章にせず表にする。逆に、単一の主張・理由・流れ（narrative）は分解できないので文章のままでよい。これが文章と表の線引きになる。

### 表は俯瞰のためにある——セルに詳細を詰め込まない

**方針**：表は全体を並べて見比べるための道具である。1行ぶんの説明・理由・列挙は表に置かず、**表の直下**に書く。出した先をトグル（`<details>`）に畳むかどうかは、詳細の数で決まる——条件は「並んで繰り返す詳細はトグルに畳む」が定める。

表にする対象を増やすことは、1つのセルに説明を詰め込む理由にならない。

**理由**：表の幅は画面で決まり、列が増えるほど1列は狭くなる。長いセルは1行だけで画面を埋め、短い列は1文字ずつの縦書きに潰れる。潰れた表はもう並べて見比べられず、表である意味を失う。

#### 歯止めとしての上限

| 列数    | 1セルの上限 |
| ------- | ----------- |
| 4列以下 | なし        |
| 5〜6列  | 150文字     |
| 7列以上 | 80文字      |

7列以上を厳しくするのは、**そこが「列を削れないか疑うべき表」だからである。** 上限に収める前に、まず列そのものを減らせないかを見る。取れる手は次のとおり。

| 手                   | 具体例                                                        |
| -------------------- | ------------------------------------------------------------- |
| 表を分ける           | 関心事が2つ混ざっているなら、2つの表にして別々に並べる        |
| 列をまとめる         | `大分類`・`中分類`・`小分類` を1列の階層表記にする            |
| 列の取りうる値を縛る | 自由記述をやめ、決まった値だけを書く列にする（例：`出所` 列） |

どれも当たらず、それでも7列以上が要るなら作ってよい。1セル80文字の上限に収めること。

数えるのは**文字数**である（半角・全角を区別せず1文字と数える）。区別しないのは、ID の羅列（半角）が実際の幅より甘く、日本語の説明文（全角）が額面どおりに判定されるからである。止めたいのは説明文の方なので、この偏りは望ましい向きに働く。

上限は歯止めであって、可読性を保つ主役ではない。主役は方針そのもので、上限はそこで取りこぼした桁違いのセルを拾う。

上限を超えたら、**超えた理由で直し方を分ける。** 問いは1つ——そのセルは行に分けられるか。

| セルの状態                                    | 直し方                     |
| --------------------------------------------- | -------------------------- |
| 行に分けられる（2つ以上の項目が入っている）   | 行を分ける                 |
| 行に分けられない（1つの項目の必須要素が並ぶ） | 表から外し、表の直下へ移す |

### 図種は「情報の形」から選ぶ（フローチャートは最後の選択肢）

可視化すると決めたら、次に選ぶのは**図の種類**である。ここで既定値をフローチャートにしてはならない。フローチャートはほぼ何でも表現「できてしまう」が、できることと適していることは違う。状態遷移をフローチャートで描くと状態と遷移条件の区別が失われ、読者は結局本文を読む羽目になる。図の目的は本文を読ませないことなので、これは図の失敗である。

選ぶ基準は、依頼者が使った**言葉**ではなく、描こうとしている情報の**形**。

| 情報の形                             | 向く可視化                     |
| ------------------------------------ | ------------------------------ |
| 2項目以上の対比・属性列挙            | 表（2項目でも表にする）        |
| 複数の主体が時間順にやり取りする     | シーケンス図                   |
| 1つの主体が状態を移る                | 状態遷移図                     |
| 実体どうしの所有・多重度             | ER図                           |
| 階層構造・ディレクトリ構造           | ツリー図                       |
| 階層＋各要素の量                     | ツリーマップ                   |
| 集合の重なり・共通部分               | ベン図                         |
| 数値の比較・推移                     | グラフ                         |
| 複数軸のスコア比較                   | レーダーチャート               |
| 2軸での評価・分類                    | 4象限図                        |
| 結果に対する要因の分解               | 特性要因図                     |
| 日付・期間の軸                       | ガントチャート／年表           |
| 上のどれにも当てはまらない分岐・合流 | フローチャート（最後の選択肢） |

> [!IMPORTANT]
> **（AI・必須）** フローチャートを選んでよいのは、他のどの形にも当てはまらなかったときだけ。選んだ場合は「なぜ他の図種でないか」を**ユーザーへの回答に**一言添える。説明できないなら選び直す。

具体的なMermaid図種への対応と構文は [design-doc-mermaid スキルの選択表](../../.claude/skills/design-doc-mermaid/references/diagram-type-selection.md) を参照する。

> [!TIP]
> **（AI・推奨）** 「文章で書けているからOK」ではなく「図にした方がもっと伝わるのでは？」を基準に判断する。

### 視覚的に文字を強調する

Markdown記法の `**太字**` は実際のViewerではわかりにくい。特に重要な箇所は次の手段で強調する。

- バッククォート： `重要キーワード`
- Admonition記法（GitHub Flavored）
- HTMLタグ

> [!NOTE]
> ViewerはGitHub Flavored Markdownを前提とする。

### Admonition（callout）の先頭に「宛先・強制力」ラベルを置く

`[!IMPORTANT]` / `[!TIP]` などの callout は、人間向けの強調とAIへの行動指示が混ざりやすい。**行動を促す callout は、本文の先頭を `**（宛先・強制力）**` で始め、誰がどの強さで従うべきかを一目で示す。** callout の種別（IMPORTANT/TIP）はAIにとって描画ではなくテキストの意味として効くため、宛先をラベルで言い切ることで取り違えと指示の素通りを防げる。

| 要素   | 取りうる値                    |
| ------ | ----------------------------- |
| 宛先   | AI / 人間 / AI・人間          |
| 強制力 | 必須（MUST） / 推奨（SHOULD） |

両対象なら `**（AI・必須 / 人間にも）**` のように併記する。単なる補足・前提（`[!NOTE]` 等で行動を促さないもの）にはラベル不要。

```markdown
> [!IMPORTANT]
> **（AI・必須）** 仕様にない依頼には即着手せず、まず仕様にあるか確認する。
```

## 文章の書き方

### 見出しとトピックセンテンスに全てを注ぐ

人間は目次の見出しと、各見出し直後の1〜2文までしか読まないというデータがある。見出しの内容と冒頭1〜2文に、全てのエッセンスを詰め込む。

見出しは多少長く説明的でも構わない。良いドキュメントとは見出しだけで内容を想像できるドキュメント。

例（書き出しは違っても、どちらも結論を冒頭に置いている）：

```markdown
## なぜクリーンアーキテクチャを採用したのか？

ひとことで言うと、変更に強い設計にすることを、ほかの何よりも優先したからです。...
```

```markdown
## 外部接続用クラスはなぜ単体テストしないのか？

応答をこちらで制御できず、本物の不具合ではなく接続状態でテストが落ちてしまうからです。...
```

### 見出しに連番を振らない

見出しを `## 1. 目的` のように番号付きで書かない。項目を1つ挿入・削除するだけで以降の全番号と、他文書からの参照（`§3` など）を書き換える羽目になるからだ。番号が伝えるのは並び順だけで、その情報量は書き換えコストに見合わない。

| 例                                   | 評価                                    |
| ------------------------------------ | --------------------------------------- |
| `## なぜ番号を振らないのか？`        | ✅                                      |
| `## 3. なぜ番号を振らないのか？`     | ❌ 節が増減するたび全体を直す           |
| `[命名規則](typescript.md#命名規則)` | ✅ 参照は見出し名かアンカーリンクで     |
| `typescript.md §4 を参照`            | ❌ 番号がずれると参照先が壊れる         |
| `[原則2](x.md)`                      | ❌ リンク先の番号が変わると無言で壊れる |

**例外は、実行順序そのものが情報である手順書**（runbook・セットアップ手順・移行手順など）。「上から順に実行する」ことを読者に伝える必要があるなら番号を振ってよい。順序に意味がない列挙は、手順書の中でも番号を振らない。

### 専門用語は使ってよいが、文章はシンプルで短くする

AIは「賢そうに見える文章＝良い文章」と誤解し、硬い言い回し・名詞化・入れ子の文構造で無駄に飾りがち。だが価値を生むのは読者の理解だけ。目指すのは「**専門用語を別の記号に置き換えたとき、残りの文を中学生が一度で追える**短さと、シンプルな構造・論理」。

専門用語そのものは避けなくてよい。むしろ専門用語で一言にできるなら、その方が短くて良い。難しさの原因は用語ではなく、言い回しと文の組み立てにある。

| 種類               | 例                                                                            | 評価                          |
| ------------------ | ----------------------------------------------------------------------------- | ----------------------------- |
| 専門用語でシンプル | GSMフレームワークを使って設計した                                             | ✅ そのままで良い             |
| 専門用語でシンプル | flakyなテストの「オオカミ少年問題」を避けるため、タグで自動テストから隔離した | ✅ そのままで良い             |
| 硬い言い回し       | 変更耐性の最大化を企図したため                                                | ❌ → 変更に強くしたかったから |
| 名詞化・硬い動詞   | 〜が最優先事項であると判断した                                                | ❌ → 〜を何よりも大事にした   |

直すのは用語ではなく言い回しと構造：

- 漢語の硬い動詞を和語に：「企図する」→「ねらう」、「担保する」→「保つ」
- 名詞化をほどく：「変更への耐性を担保する」→「変更に強くする」
- 一文の主語・述語は1組まで：長い一文は切って、論理を一直線にする

> [!TIP]
> **（AI・推奨）** 自己判定テスト。**専門用語は数に入れない**。
>
> - **中学生テスト**：専門用語を別の記号に置き換えても、文の構造と論理を中学生が追えるか。追えないなら言い回しか構造が難しすぎる。
> - **音読テスト**：声に出して言わない硬い言い回し（「〜を企図する」等）は、書き言葉としても難しすぎる。

### 冒頭に「決定事項」を3行で先出しする（TL;DR）

捜索者は自分知りたい情報を探すために来る。設計書の冒頭に「何を・なぜそう決めたか」を、**決定1件1行の箇条書きで最大3行**にまとめる（1段落にまとめない）。目次は「何について書いてあるか（話題）」しか示さないが、TL;DRは「で、どう決めたのか（結論や決定事項）」を示す。両者は別物なので重複しない。

> [!IMPORTANT]
> **（AI・必須）** 絶対に3行まで。4行になったら、それはTL;DRではなく本文である。短くまとめられないなら、まだ設計判断が定まっていない兆候。

ただし**突出した決定がある文書に限る**。事実を列挙するだけの文書（用語集・API一覧・テーブル定義）には決定がない。同格の決定を並べただけの文書（コーディング規約集）は、どれも本文の一部なので3つ選ぶ行為が恣意的になり、本文との二重管理でずれる。どちらも索引・見出しで足りる。

| 文書の種類                                   | TL;DR                       |
| -------------------------------------------- | --------------------------- |
| アーキテクチャ設計、ADR（なぜその構成か）    | ✅ 決定事項を3行で先出し    |
| ポリシー（何を良いとするかの宣言）           | ✅ 決定事項を3行で先出し    |
| 用語集、API一覧、テーブル定義（事実の列挙）  | ❌ 不要、索引・目次で足りる |
| コーディング規約集（同格の決定を並べたもの） | ❌ 不要、見出しが索引になる |

### 並んで繰り返す詳細はトグルに畳む

**方針**：下表のどちらかに当たったら、**例外なく**トグル（`<details>`）に畳む。当たらないものは畳まない。

| 畳む条件                                                                | 例                                           |
| ----------------------------------------------------------------------- | -------------------------------------------- |
| 表・一覧の項目に1対1で対応する詳細が**3つ以上並ぶ**（並んだ全部を畳む） | 表の各行の理由・本文・内訳／機能ごとの補助図 |
| Mermaid 以外のコードブロック・出力例で**20行を超える**もの              | 設定ファイルの全文・コマンドの実行ログ       |

**理由**：同じ型の詳細が並ぶと、読者はそれを1件ずつ読むのではなく、一覧を追う。開いたままの詳細は一覧を分断し、読者が全体を見比べるのを妨げる。

条件を「長いか」「補足か」ではなく**数で決める**のは、長さ・重要度の評価を書き手に委ねると、書き手はほぼ常に「これは本文に要る」と結論するからである（refined-engineer-judgment-principles の「判断軸は『既定値＋反転条件』で与える」）。数えられる条件だけがゲートとして働く。

**畳まないもの**：

| 対象外                      | 理由                                                                               |
| --------------------------- | ---------------------------------------------------------------------------------- |
| 見出し（`####` 等）を持つ節 | トグルに見出しは入れられない。規定・結論を並べた節がまとめて隠れる事故をこれが防ぐ |
| `CLAUDE.md`                 | 毎回読み込まれ、タグのぶんのトークンを払い続ける（表の例外と同じ範囲）             |

> [!IMPORTANT]
> **（AI・必須）** 畳んでよいのは**削除テストを通った内容**だけ。消せるものは畳まず消す。トグルは、消すべき内容の捨て場ではない。

> [!IMPORTANT]
> **（AI・必須）** **トグル削除テスト**：畳んだ部分を伏せて本文だけを通しで読み、読者が判断・行動できるか。できないなら本文が足りていない。結論・規定・判断そのものは畳まない。

#### 記法

```markdown
<details>
<summary>F-03 失効処理</summary>

（詳細）

</details>
```

| 決まり                                              | 理由                                       |
| --------------------------------------------------- | ------------------------------------------ |
| `<details>` の直後と `</details>` の直前に空行      | 無いと中の Markdown がレンダリングされない |
| 中に見出しを置かない                                | トグルにできないため                       |
| `summary` は中身が分かる識別語（`ID 名前`・項目名） | 「詳細」「補足」では開くまで中身が読めない |
| 対応する表・一覧と同じ順に並べる                    | 読者が表の行から詳細を引けるようにする     |
