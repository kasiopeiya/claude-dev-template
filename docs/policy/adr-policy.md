# ADR 判定ポリシー

AIエージェントが、決めたことをどこに書くか（ADR にするか、別の場所に書くか）を判断するときに参照する。判定は ADR を書き始める前——Issue の「対応方針」や Plan を書く段階——に行う。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - **ADR にするのは、コア部分についての決定で、変えるときに移行作業が要るものだけ。** 使う言語・フレームワークのような、後戻りが難しい決定の水準で使う
> - **判定は「人間の指示 → 作らない条件 → 作る条件 → 迷ったら作らない」の順に当てる。** 条件は見れば分かる事実だけで書き、重要そうかを判定に使わない
> - **ADR にしない決定も理由は残す。** 書き先はその仕組みの本文で、却下案と経緯は決定した Issue に残す。書き先が無いことは ADR を作る理由にならない

## ADR は後戻りが難しい決定だけに使う

判断した理由を残さないと、半年後に同じ案が蒸し返され、変えてよい決定と変えてはいけない決定の区別も付かなくなる。だから決定の理由は消さない。

いっぽうで ADR を増やすと、一覧（`docs/adr/adr-index.md`）が誰にも読まれなくなり、WHY の受け皿としては働かなくなる。件数が増えたぶんだけ1件の重みが薄まるので、**残す件数を絞ることが ADR を機能させる条件**である。

だから「理由を残すか」と「ADR にするか」を切り離す。理由は仕組みの本文に残し、ADR にするのは、覆すと作ったものを作り直すことになる決定だけにする。ファイルを数か所直せば戻せる決定は、ADR にしなくても本文の理由を読んで変えられる。

## 判定手順：上から順に当て、決まったら下は見ない

| 順  | 段                       | 判定                                                         |
| --- | ------------------------ | ------------------------------------------------------------ |
| 1   | 人間の指示               | 人間が明示的に ADR 作成を指示した → **作る**（2・3より優先） |
| 2   | 作らない条件             | どれか1つに当たる → **作らない**                             |
| 3   | 作る条件                 | どれか1つに当たる → **作る**                                 |
| 4   | どれにも当たらない・迷う | **作らない**                                                 |

迷ったときに「作らない」へ倒すのは、外したときのコストが小さい側だからである。作らなかった決定の理由は仕組みの本文に残るので、記録そのものは失われない。

### 作らない条件

| 条件                    | 見分け方                                                                                                                                                                                     | 例                                                              | 代わりにどこへ書くか                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 判断していない          | 代替案が1つも書けない（選択肢が実質1つ）                                                                                                                                                     | 使える API が1つしか無いのでそれを呼ぶ                          | 何も書かない                                                               |
| ほかに正本がある        | 決めた内容そのものが書き方（`.claude/rules/`）・判断基準（`docs/policy/`）・いまの構造（`docs/design/`）・設定値（[configuration-policy](configuration-policy.md) が置き場所を決める）である | ADR の判定基準をポリシーに置く（正本がポリシーそのもの）        | そちら                                                                     |
| 既存 ADR と同じ軸の決定 | 既存 ADR の「決定の軸」への別の答えになっている                                                                                                                                              | 使うフレームワークを別のものに替える（採用を決めた ADR がある） | 決定そのものが入れ替わるなら supersede、条件・適用範囲が増えるだけなら更新 |

「ほかに正本がある」に当たるのは、決めた内容が正本の中身そのもののときだけである。代替案を比べて決めた結果を設計書や設定に書くだけなら、この条件には当たらない（当たると読むと、下の「作る条件」が1つも発火しなくなる）。

### 作る条件

| 条件                                                                                                | 例                                                                               |
| --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| コア部分（`docs/project-context/core-parts.md` が正本）についての決定で、変えるときに移行作業が要る | 使う言語・フレームワーク・DB の選択、コアのデータのテーブルのキー設計            |
| ほかのポリシー・Rule・ガイドが「ADR で決める」と名指ししている種類の決定                            | グローバル状態ライブラリの導入、コンポーネントライブラリの採用、初期技術スタック |

**移行作業**とは、その決定の上に作ったコード・データ・外部の利用者を、作り直したり移したりする作業を指す。設定・スクリプト・プロンプト・文書を直すだけで戻せるなら、コア部分の決定でも移行作業は要らないので作らない。

- ❌ 作らない：CI の検査に落ちる条件を1つ足す——検査スクリプトを直せば戻せる
- ❌ 作らない：レビューのレンズの分け方を変える——Skill と agent の定義を直せば戻せる

**コア部分一覧が無い、または空のプロジェクトでは、1つ目の作る条件には当たらないものとして扱う。** 一覧はプロジェクトごとに人間が書くもので、テンプレート同期の対象外なので、利用先には無いことがある。無いときに「コアかどうか」を AI が推測すると、重要性の判断を排除したこのポリシーの前提が崩れる。

## ADR にしない決定は、理由を本文に・却下案を Issue に残す

| 残すもの                                 | 書き先                                                                   | なぜそこか                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| いまそうしている理由                     | その仕組みの本文（SKILL.md・README・設計書・ファイル冒頭の責務コメント） | 仕組みを読む人が同じ場所で理由まで読める。本文を直すときに理由も一緒に直る |
| 却下した案・なぜ旧設計から変えたかの経緯 | 決定した Issue                                                           | 却下案は現物と突き合わせられず、本文に置くと腐る                           |

**書き先が無いことは、ADR を作る理由にならない。** README や設計書が無い仕組み（`scripts/` 配下のスクリプトなど）の決定は、そのファイル自身の冒頭の責務コメントか `--help` に書く。書き先を用意するために README を新設することもしない。後戻りしやすい決定のために、保守が要るファイルを増やさない。
