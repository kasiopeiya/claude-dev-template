# ADR 判定ポリシー

AIエージェントが、決めたことをどこに書くか（ADR・コミットの決定記録・仕組みの本文のどれにするか）を判断するときに参照する。判定は ADR を書き始める前——Issue の「対応方針」や Plan を書く段階——に行う。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - **ADR にするのは、後から「なぜこうしたのか」と問われそうで、その答えがほかに書かれていない決定だけ**
> - **ADR にするほどではない決定や迷った決定は、コミットメッセージに決定記録として残す。** 一覧は `git log` から自動生成する
> - **いまそうしている理由は、ADR にしてもしなくても仕組みの本文に書く。** 却下案と経緯は決定した Issue に残す

## ADR は同じ検討の繰り返しを防ぐために書く

決定の経緯が残っていないと、後から来た人や AI が「なぜこうしたのか」と疑問を持ったとき、以前やった検討をもう一度やることになる（グラウンドホッグデイ・アンチパターン）。AI は前のセッションを覚えていないので、経緯が無ければ過去の決定を平気で覆す提案をする。技術選定の根拠が社内の事情（組織の標準・予算・人員）であるときは、コードからは決して読み取れない。

いっぽうで ADR を増やすと、一覧（`docs/adr/adr-index.md`）が誰にも読まれなくなる。だから ADR は「後から問われる」ものに絞り、それより軽い決定はコミットメッセージに残す。コミットなら書くのは気楽で、一覧から引ける。

## 判定手順：上から順に当て、決まったら下は見ない

| 順  | 段                  | 判定                                                                                         |
| --- | ------------------- | -------------------------------------------------------------------------------------------- |
| 1   | 人間の指示          | 人間が明示的に ADR 作成を指示した → **ADR**（2・3より優先）                                  |
| 2   | 判断していない      | 代替案が1つも書けない（選択肢が実質1つ）→ **何も残さない**                                   |
| 3   | 2つの問い           | 両方 Yes → **ADR**。既存 ADR と同じ軸の決定なら、新しく作らずその ADR を supersede・更新する |
| 4   | 3で決まらない・迷う | **コミットの決定記録**                                                                       |

### 2つの問い

- **問い1**：この決定を知らない人や AI が後から見て、「なぜこうしたのか、別のやり方の方が良いのでは」と疑問を持ちそうか。自明な案を、自明でない理由で捨てているか
- **問い2**：その答え（なぜこうしたか）が、コード・設計書・ポリシー・そのファイルの冒頭コメントのどこにも書かれていないか

問い2が見るのは**理由**が書かれているかであって、決めた中身が書かれているかではない。中身がポリシーに書かれていても、なぜその形にしたかが書かれていなければ Yes になる。

コア部分（`docs/project-context/core-parts.md` に載った部分）についての決定は、変えたときの影響が大きいので問い1が Yes になりやすい。一覧に載っていない補助の道具の決定は、本文の理由かコミットの決定記録で足りることが多い。

### 判定の例

- ✅ ADR：レビュー系 subagent を、観点をまとめたレンズごとに並列で走らせる——「トークンコストがかかるのになぜ」と必ず問われる
- ✅ ADR：Policy と Rule の役割を分ける——「なぜ1か所にまとめず2か所に分けるのか」と問われる
- ✅ ADR：dev への deploy を main へのマージ後に行う（`samples/docs/adr/001`）——「なぜマージ前に deploy して確かめないのか」と問われる
- ✅ ADR：cdk-nag の抑制を1ファイルに集約する（`samples/docs/adr/002`）——「なぜリソースの隣に書かないのか」と問われる
- ❌ コミットの決定記録：`docs/adr/` をテンプレート同期の対象から外す——理由は同期スクリプトの `--help` に書ける
- ❌ コミットの決定記録：CI の検査に落ちる条件を1つ足す——理由は検査スクリプトの冒頭コメントに書ける

## コミットの決定記録の書き方

コミットメッセージの本文に、決定・理由・却下した案を書き、最後の行にトレーラー `Decision-Record: yes` を付ける。書式は `/git-commit` が定める。

このトレーラーの付いたコミットは、`docs/adr/adr-commit-list.md` の一覧に自動で載る。過去の決定を探すときは一覧を見るか、`git log --grep "^Decision-Record: yes$"` で引く。

## ADR にしてもしなくても、理由は本文に・却下案は Issue に残す

| 残すもの                                 | 書き先                                                                   | なぜそこか                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| いまそうしている理由                     | その仕組みの本文（SKILL.md・README・設計書・ファイル冒頭の責務コメント） | 仕組みを読む人が同じ場所で理由まで読める。本文を直すときに理由も一緒に直る |
| 却下した案・なぜ旧設計から変えたかの経緯 | 決定した Issue（ADR・コミットの決定記録にも書く）                        | 却下案は現物と突き合わせられず、本文に置くと腐る                           |

**書き先が無いことは、ADR を作る理由にならない。** README や設計書が無い仕組み（`scripts/` 配下のスクリプトなど）の決定は、そのファイルの冒頭の責務コメントか `--help` に理由を書き、経緯はコミットの決定記録に残す。書き先を用意するために README を新設しない。
