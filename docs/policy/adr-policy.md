# ADR 判定ポリシー

AIエージェントが、決めたことをどこに書くか（ADR にするか、別の場所に書くか）を判断するときに参照する。判定は ADR を書き始める前——Issue の「対応方針」や Plan を書く段階——に行う。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - **判定は「人間の指示 → 作らない条件 → 作る条件 → 迷ったら作らない」の順に当てる。** 上の段で決まったら下は見ない
> - **条件は、見れば分かる事実だけで書く。** 重要そうか・重いかを判定に使わない
> - **判断した決定は、ADR にしなくても理由を残す。** 書き先はその仕組みの本文（SKILL.md・README・設計書）で、却下案と経緯は決定した Issue に残す

## ADR は「一覧が読まれる件数」に絞る

判断した理由を残さないと、半年後に同じ案が蒸し返され、変えてよい決定と変えてはいけない決定の区別も付かなくなる。だから決定の理由は消さない。

いっぽうで ADR を増やすと、一覧（`docs/adr/adr-index.md`）が誰にも読まれなくなり、WHY の受け皿としては働かなくなる。件数が増えたぶんだけ1件の重みが薄まるので、**残す件数を絞ることが ADR を機能させる条件**である。

だから「理由を残すか」と「ADR にするか」を切り離す。判断した決定なら理由は残し、ADR にするのは下の判定に通ったものだけにする（判断していないものは理由も要らない）。

## 判定手順：上から順に当て、決まったら下は見ない

| 順  | 段                       | 判定                                                         |
| --- | ------------------------ | ------------------------------------------------------------ |
| 1   | 人間の指示               | 人間が明示的に ADR 作成を指示した → **作る**（2・3より優先） |
| 2   | 作らない条件             | どれか1つに当たる → **作らない**                             |
| 3   | 作る条件                 | どれか1つに当たる → **作る**                                 |
| 4   | どれにも当たらない・迷う | **作らない**                                                 |

迷ったときに「作らない」へ倒すのは、外したときのコストが小さい側だからである。作らなかった決定の理由は仕組みの本文に残るので、記録そのものは失われない。

### 作らない条件

| 条件                    | 見分け方                                                                                                                                                                                     | 例                                                              | 代わりにどこへ書くか                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 判断していない          | 代替案が1つも書けない（選択肢が実質1つ）                                                                                                                                                     | 使える API が1つしか無いのでそれを呼ぶ                          | 何も書かない                                                               |
| ほかに正本がある        | 決めた内容そのものが書き方（`.claude/rules/`）・判断基準（`docs/policy/`）・いまの構造（`docs/design/`）・設定値（[configuration-policy](configuration-policy.md) が置き場所を決める）である | ADR の判定基準をポリシーに置く（正本がポリシーそのもの）        | そちら                                                                     |
| 既存 ADR と同じ軸の決定 | 既存 ADR の「決定の軸」への別の答えになっている                                                                                                                                              | レビューのレンズを4つから5つに変える（分割を決めた ADR がある） | 決定そのものが入れ替わるなら supersede、条件・適用範囲が増えるだけなら更新 |
| 補助的な仕組みの決定    | 下の「補助的な仕組み」の節の3条件をすべて満たす                                                                                                                                              | `/doc-consistency` の重複確認をどの粒度で行うか                 | その仕組みの本文                                                           |

「ほかに正本がある」に当たるのは、決めた内容が正本の中身そのもののときだけである。代替案を比べて決めた結果を設計書や設定に書くだけなら、この条件には当たらない（当たると読むと、下の「作る条件」が1つも発火しなくなる）。

### 作る条件

| 条件                                                                                                     | 例                                                                               |
| -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 決定を変えるときに複数の仕組みを書き換える必要がある、またはほかの仕組みの本文がその決定を名指ししている | 3つの Skill が同じ判定順を前提にしている                                         |
| データの保存形式・構造／外部に公開するインターフェース／認証・認可・権限・秘密情報の扱いを決める         | テーブルのキー設計、公開 API のレスポンス形、トークンの保管先                    |
| コア部分の実装・設計書・手順を書き換える（コア部分は `docs/project-context/core-parts.md` が正本）       | レビューの仕組みのレンズ分割を変える                                             |
| ほかのポリシー・Rule・ガイドが「ADR で決める」と名指ししている種類の決定                                 | グローバル状態ライブラリの導入、コンポーネントライブラリの採用、初期技術スタック |

**コア部分一覧が無い、または空のプロジェクトでは、「コア部分の実装・設計書・手順を書き換える」の条件には当たらないものとして扱う。** 一覧はプロジェクトごとに人間が書くもので、テンプレート同期の対象外なので、利用先には無いことがある。無いときに「コアかどうか」を AI が推測すると、重要性の判断を排除したこのポリシーの前提が崩れる。

## 補助的な仕組みとは、コア部分一覧に載っていない道具の中で閉じる決定である

**補助的な仕組みの決定**とは、次の3つをすべて満たすものを指す。

1. 開発を助ける道具（Skill・agent・hook・スクリプト・ワークフロー）のうち、`docs/project-context/core-parts.md` に載っていないものについての決定である
2. コア部分の実装・設計書・手順を書き換えない
3. その道具の中で閉じる（決定を変えるときに書き換えるのはその道具だけで、ほかの仕組みの本文がその決定を名指ししていない）

保存形式・外部公開インターフェース・権限を決める場合でも、この3つを満たすなら補助として扱い、ADR にしない。補助の決定は1か所直せば変えられるので、ADR にする価値がない。

- ❌ 補助ではない：「`/doc-consistency` を通常の実装フローに含めない」——開発フロー（コア）を書き換える
- ✅ 補助である：「重複確認は指摘ごとに行う」——`/doc-consistency` の中で閉じる

## ADR にしない決定は、理由を本文に・却下案を Issue に残す

| 残すもの                                 | 書き先                                       | なぜそこか                                                                 |
| ---------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------- |
| いまそうしている理由                     | その仕組みの本文（SKILL.md・README・設計書） | 仕組みを読む人が同じ場所で理由まで読める。本文を直すときに理由も一緒に直る |
| 却下した案・なぜ旧設計から変えたかの経緯 | 決定した Issue                               | 却下案は現物と突き合わせられず、本文に置くと腐る                           |
