# IaCインフラ設計書作成ポリシー

AWS/IaC で構築したシステムの**インフラ設計書**と **IaC 設計書**を書く・レビューする人が、コードから読み取れない全体像・設計判断・組織/運用上の制約を過不足なく書けているかを判断する基準を得たいとき参照するドキュメント。読み終えたとき「良いインフラ設計書・IaC 設計書とはこういうもの」を自分の言葉で言え、テンプレートに沿って着手できることが目的。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - IaC ではコード自体がインフラの最大の SSoT。ゆえに両設計書は通常の設計書よりさらに**「全体を見渡す図」と「なぜ（設計判断）」に寄る**。具体パラメータ値（インスタンスサイズ・バケット名等）は書かない（コードと二重管理になり腐る）
> - **2文書に分ける**。インフラ設計書は「**何を組むか**」（構成図・ネットワーク・運用監視）、IaC 設計書は「**どう作り・変えるか**」（IaC 管理方針・スタック設計・命名規約）を持つ
> - **必須セクション**をテンプレートとして定める。必須とは「セクションを必ず**存在**させる」の意で、該当がなければ**「なし＋理由」で閉じてよい**（不在が「未検討」なのか「対象外」なのかを読者に伝えるため）

## 前提：IaC では「コードが最大の SSoT」だから、設計書はいっそう図とWHYに寄る

インフラも、構成そのものはコードを追わないと頭の中で再構築できない。しかも IaC ではコードが宣言的なインフラ定義そのものなので、**コードを読めば分かること（リソースの個別設定・具体値）を設計書に書き写すと、必ずコードと二重管理になって腐る**。

したがって両設計書が担うのは、コードからは読み取れない次の2種類だけ。

| 設計書が担うもの                       | なぜコードから読めないか                                                 |
| -------------------------------------- | ------------------------------------------------------------------------ |
| **全体を見渡す図**（構成・関係・流れ） | 構成は多数のファイル・スタックに散らばり、一望できない                   |
| **設計意図（WHY）**                    | 「なぜこの構成／このサービスか」「なぜこう分割したか」はコードに現れない |

> [!IMPORTANT]
> **（AI・必須）** 各記述に「これはコードを読めば分かるか？」を問う。分かるなら書かない。設計書の主役は**図**であり、削るときは文章から先に削って図を最後に残す。図は `/design-doc-mermaid` スキルで作成する（CLAUDE.md の方針。自前で Mermaid を書き起こさない）。

## 書かないもの：具体パラメータ値

インスタンスサイズ・バケット名・タイムアウト値などの**具体パラメータ値は書かない**。設計書とコードの二重管理になり、乖離の原因になる。ここはコードが SSoT のままでよい部分。

- 例外：**設計判断を支える根拠として値に触れる**のは可（例「同時実行が想定 100 未満のためスケールアウトは不要」）。この場合も値そのものではなく**なぜその値で足りるか**を書く。

## 境界：CDK コードの書き方とは別物

| 対象                       | 何を定めるか                                           | どこ                   |
| -------------------------- | ------------------------------------------------------ | ---------------------- |
| インフラ設計**書**（文書） | 全体像の図・設計判断・組織/運用の制約をどう書くか      | **本ポリシー**         |
| IaC 設計**書**（文書）     | IaC 管理範囲・スタック分割・命名規約をどう書くか       | **本ポリシー**         |
| CDK **コード**の設計       | リソース名の固定方針・Stack 抽象化など、コードの作り方 | cdk-design-policy      |
| CDK **コード**の書式       | import 形式・Construct レベルなど機械的ルール          | `.claude/rules/cdk.md` |

例えば「命名規約」は、**規約とその理由**を設計書に記録し（本ポリシー）、その**実装**はコード側ルールに従う——という役割分担。

## 2文書の分け方：何を組むか／どう作り・変えるか

読者も変更のきっかけも違うから分ける。どのセクションをどちらに置くかは、次章のテンプレート表の「置き場」列が決める。

**リソースに課される規約は IaC 設計書にまとめる。** 命名・タグ・暗号化・リージョンは、どれも「リソースに何を付けるか」への答えで、CDK コード上も同じ場所でまとめて効かせる。組織から課された規約か自分たちで決めた規約かにかかわらず、1箇所で読めるようにする。インフラ設計書側の「組織の制約」は、IaC 設計書への参照を書いて閉じる。

## 必須セクション（テンプレート）

両設計書は次のセクションで構成する。**すべて必須**だが、該当がなければ本文に「**なし**」＋一言理由を書いて閉じてよい（空欄で放置しない）。どの図にも**設計意図**を添える。図の直下に `<details><summary>設計意図</summary>` を置き、短い文章で書く（既定は必須。図だけで説明が閉じるなら置かない）。

セクションの並び順・番号は縛らない（下表の順序は一例）。「置き場」が**両方**のセクションは、各文書がそれぞれの領域分だけを書く。

| セクション               | 置き場   | 何を書くか（コードから読めないこと）                                                                                                                             | 該当なし時の書き方                                        |
| ------------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **# 基本方針**           | 両方     | 冒頭に置く。この設計が取る考え方1文と、そこから出てくる方針の箇条書き（表にしない。理由は添えず冒頭の1文が兼ねる）                                               | （必ず該当あり）                                          |
| **# アーキテクチャ概要** | インフラ | 下位の図群                                                                                                                                                       | —                                                         |
| 　全体インフラ構成図     | インフラ | システム全体の主要リソースと接続                                                                                                                                 | （通常は必ず該当あり）                                    |
| 　アカウントと環境構成   | インフラ | AWS アカウントと環境（例：dev/stg/prd）の関係。1アカウントに複数環境を同居させるか、環境間の主要な違い                                                           | 単一アカウント単一環境なら、その旨と理由                  |
| 　ネットワーク構成図     | インフラ | VPC・サブネット・VPC Endpoint などネットワーク境界。VPC が無くても、外部から到達できる範囲（公開する入口と、直接には到達させないリソース）が設計判断なら図にする | VPC も公開範囲の設計判断も無いなら「なし＋理由」          |
| **# 運用監視**           | インフラ | 監視・ログ・トレースの**全体像を図**で。項目選定の考え方は監視ポリシーへ委譲                                                                                     | 別設計書に切り出す場合は参照先を書く                      |
| **# IaC 管理方針**       | IaC      | どこまでを IaC で管理し、手動変更をどう扱うか（例：構築〜運用まで IaC、手動変更は禁止）                                                                          | —                                                         |
| 　手動作成リソース一覧   | IaC      | IaC 管理外のリソースを表で列挙（手動管理になるため）                                                                                                             | 「なし」（全リソースが IaC 管理下であることの確認になる） |
| **# スタック設計**       | IaC      | 下位を含む                                                                                                                                                       | —                                                         |
| 　スタック関係図         | IaC      | スタックの依存関係と参照方式（クロススタック参照／Parameter Store による間接参照 など）。スタックの中身（個々のリソース）は描かない                              | 単一スタックなら、その旨                                  |
| 　環境差分の実装設計     | IaC      | 環境（dev/stg/prd等）差分をコード上でどう表現しているか（図）と、なぜその設計にしたか                                                                            | 単一環境なら、その旨                                      |
| **# 前提と制約**         | 両方     | 変更しようとする人への警告を1節にまとめ、下位の2小節に分ける                                                                                                     | —                                                         |
| 　技術的制約             | 両方     | 触ると壊れる前提・意図的にやらないと決めたこと・受け入れた不便を表で                                                                                             | 「なし」                                                  |
| 　組織の制約             | IaC      | 組織が課す制約。さらに `####` の小節に分ける。インフラ設計書側は小節を持たず、IaC 設計書への参照を書いて閉じる                                                   | 「なし」                                                  |
| 　　タグ規則             | IaC      | 組織が課すタグ付けの規約                                                                                                                                         | 「なし」                                                  |
| 　　その他の制約         | IaC      | 暗号化要件（例：社内ルールで KMS 利用）・リージョン制約 など                                                                                                     | 「なし」                                                  |
| **# 命名規約**           | IaC      | 下位を含む。組織から課された規約も自分たちで決めた規約もここに集める                                                                                             | —                                                         |
| 　リソース命名           | IaC      | リソースに名前を付けるかどうかの方針と理由。組織が課す命名規約があればそれも書く                                                                                 | 「なし」                                                  |
| 　スタック命名           | IaC      | プレフィックス設計とその理由（プレフィックスはデプロイ時の対象選択などに使う）                                                                                   | 規約がなければ、その旨                                    |

### 命名規約の書き方（補足）

命名スキームはプロジェクトごとに異なる。**規約とその理由**を記録し、スキーム自体は各プロジェクトで定義する（決め打ちしない）。

- スタック命名のスキーム例：`{システム}-{環境}-{ステート}-{任意}-stack`（一例）

### スタック関係図の書き方（補足）

描くのはスタックとスタックの関係だけで、**中身のリソースは描かない**。中身を描くと、全体インフラ構成図と同じ情報が2枚目の図になってノイズになる。しかもリソースを1つ足すたびにこの図も直すことになり、必ず腐る。リソースの接続は全体インフラ構成図が持つ。

### 環境差分の実装設計の書き方（補足）

環境差分を**どう出すか（判断軸）**は cdk-design-policy の領分（Stack 内で分岐させず、値は設定へ・構造は Builder 層へ寄せる）。本セクションは**このプロジェクトでその判断軸をどう適用したか**を図と一言の理由で示す（例：値を `parameter.ts` に集約し、StackBuilder 経由で Stack へ渡す設計にしたのは、Stack 内部に環境分岐を作らないため）。

### 運用監視の書き方（補足）

インフラ設計書側の役割は「**監視・ログ・トレースの全体像を図で渡す**」ことに限定する。**どういう考え方で監視項目・アラームを選ぶか**（症状ベース・GSM など）は [monitoring-policy](monitoring-policy.md) が単一の基準を持つので、ここで再説明せず参照する。内容は独立した設計書に切り出してもよいが、**インフラ設計書側のセクションは省略しない**——切り出した場合は、そのセクションに参照先を書いて閉じる。

## レビュー観点（チェックリスト）

インフラ設計書・IaC 設計書をレビューするときは、**両方**を対象に次を確認する。片方だけ見ると、もう一方の抜けに気づけない。

### 両設計書に共通

- [ ] 冒頭に**基本方針**があり、考え方1文と、方針の箇条書きが1組書かれているか（表になっていないか）
- [ ] その文書が持つ必須セクション（テンプレート表の「置き場」で判定）がすべて存在するか（該当なしは「なし＋理由」で閉じているか）
- [ ] 主要な構成が**図**で示されているか（文章の壁になっていないか）
- [ ] 各図の直下の `<details><summary>設計意図</summary>` の中身が、構成図の描き直し・図の言い換えになっていないか（却下した代替案は書かず ADR へ出しているか）
- [ ] コードを読めば分かる具体パラメータ値を**書き写していない**か（二重管理していないか）
- [ ] 個々の設計判断が、中身を名指しした `##` セクションに立っているか（「重要なポイント」のような傘セクションを作っていないか。1セクション1決定で、書いてあるのは構成図に描かれていない内訳か）
- [ ] 「前提と制約」の節が技術的制約と組織の制約に分かれているか（該当なしは小節ごとに「なし」と明記されているか）
- [ ] 2文書の分担（何を組むか／どう作り・変えるか）を越えた記述が混ざっていないか

### インフラ設計書

- [ ] 組織の制約が IaC 設計書への参照で閉じているか（`####` の小節を持っていないか）
- [ ] リソースに課される規約（命名・タグ・暗号化・リージョン）が残っていないか

### IaC 設計書

- [ ] 手動作成リソースが漏れなく列挙されているか（なければ「なし」と明記されているか）
- [ ] スタック関係図にスタックの中身（個々のリソース）を描いていないか
- [ ] 命名規約にリソース命名とスタック命名の両方があるか
- [ ] 組織の制約が `####` の小節（タグ規則・その他の制約）に分かれているか

---

> [!IMPORTANT]
> 本ポリシーで最も重要な原則。
>
> - **コードが最大の SSoT**：設計書には全体像の図と設計判断（WHY）だけを書き、具体パラメータ値は書かない
> - **何を組むかと、どう作り・変えるかを別の文書に置く**：前者はインフラ設計書、後者は IaC 設計書が持つ
> - **必須セクションは「存在」を必須にする**：該当なしは「なし＋理由」で閉じ、未検討と対象外を読者が区別できるようにする
> - **文書の話に限定する**：コードの作り方は cdk-design-policy / cdk.md、監視項目の選び方は monitoring-policy へ委譲する
