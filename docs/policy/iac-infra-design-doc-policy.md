# IaCインフラ設計書作成ポリシー

AIエージェントが、AWS/IaC で構築したシステムの**インフラ設計書**と **IaC 設計書**を書く・レビューし、コードから読み取れない全体像・設計判断・組織/運用上の制約を過不足なく書けているかを判断する基準を得たいとき参照するドキュメント。読み終えたとき「良いインフラ設計書・IaC 設計書とはこういうもの」を自分の言葉で言えることが目的。**必須セクションとその書き方（How）**は [iac-infra-design-doc.md](../../.claude/rules/iac-infra-design-doc.md)（Rule）が定める。

> [!IMPORTANT]
> **TL;DR（このポリシーの決定事項）**
>
> - IaC ではコード自体がインフラの最大の SSoT。ゆえに両設計書は通常の設計書よりさらに**「全体を見渡す図」と「なぜ（設計判断）」に寄る**。具体パラメータ値（インスタンスサイズ・バケット名等）は書かない（コードと二重管理になり腐る）
> - **2文書に分ける**。インフラ設計書は「**何を組むか**」（構成図・ネットワーク・運用監視）、IaC 設計書は「**どう作り・変えるか**」（IaC 管理方針・スタック設計・命名規約）を持つ
> - 両設計書に**必須セクション**を置く（一覧は Rule）。必須とは「セクションを必ず**存在**させる」の意で、該当がなければ**「なし＋理由」で閉じてよい**（不在が「未検討」なのか「対象外」なのかを読者に伝えるため）

## 前提：IaC では「コードが最大の SSoT」だから、設計書はいっそう図とWHYに寄る

インフラも、構成そのものはコードを追わないと頭の中で再構築できない。しかも IaC ではコードが宣言的なインフラ定義そのものなので、**コードを読めば分かること（リソースの個別設定・具体値）を設計書に書き写すと、必ずコードと二重管理になって腐る**。

したがって両設計書が担うのは、コードからは読み取れない次の2種類だけ。

- **全体を見渡す図**（構成・関係・流れ）：構成は多数のファイル・スタックに散らばり、一望できない
- **設計意図（WHY）**：「なぜこの構成／このサービスか」「なぜこう分割したか」はコードに現れない

> [!IMPORTANT]
> **（AI・必須）** 各記述に「これはコードを読めば分かるか？」を問う。分かるなら書かない。設計書の主役は**図**であり、削るときは文章から先に削って図を最後に残す。図は `/design-doc-mermaid` スキルで作成する（documentation-policy の方針。自前で Mermaid を書き起こさない）。

## 書かないもの：具体パラメータ値

インスタンスサイズ・バケット名・タイムアウト値などの**具体パラメータ値は書かない**。設計書とコードの二重管理になり、乖離の原因になる。ここはコードが SSoT のままでよい部分。

- 例外：**設計判断を支える根拠として値に触れる**のは可（例「同時実行が想定 100 未満のためスケールアウトは不要」）。この場合も値そのものではなく**なぜその値で足りるか**を書く。

## 境界：CDK コードの書き方とは別物

| 対象                       | 何を定めるか                                           | どこ                                                    |
| -------------------------- | ------------------------------------------------------ | ------------------------------------------------------- |
| インフラ設計**書**（文書） | 全体像の図・設計判断・組織/運用の制約をどう書くか      | **本ポリシー**・`.claude/rules/iac-infra-design-doc.md` |
| IaC 設計**書**（文書）     | IaC 管理範囲・スタック分割・命名規約をどう書くか       | **本ポリシー**・`.claude/rules/iac-infra-design-doc.md` |
| CDK **コード**の設計       | リソース名の固定方針・Stack 抽象化など、コードの作り方 | cdk-design-policy                                       |
| CDK **コード**の書式       | Construct レベル・差分検知など機械的ルール             | `.claude/rules/cdk.md`                                  |

例えば「命名規約」は、**規約とその理由**を設計書に記録し、その**実装**はコード側ルールに従う——という役割分担。

## 2文書の分け方：何を組むか／どう作り・変えるか

読者も変更のきっかけも違うから分ける。どのセクションをどちらに置くかは、Rule の必須セクション表の「置き場」列が決める。

**リソースに課される規約は IaC 設計書にまとめる。** 命名・タグ・暗号化・リージョンは、どれも「リソースに何を付けるか」への答えで、CDK コード上も同じ場所でまとめて効かせる。組織から課された規約か自分たちで決めた規約かにかかわらず、1箇所で読めるようにする。インフラ設計書側の「組織の制約」は、IaC 設計書への参照を書いて閉じる。

## レビュー観点（チェックリスト）

インフラ設計書・IaC 設計書をレビューするときは、**両方**を対象に次を確認する。片方だけ見ると、もう一方の抜けに気づけない。

### 両設計書に共通

- [ ] 冒頭に**基本方針**があり、考え方1文と、方針の箇条書きが1組書かれているか（表になっていないか）
- [ ] その文書が持つ必須セクション（Rule の必須セクション表の「置き場」で判定）がすべて存在するか（該当なしは同表の「該当が無いときに書くこと」どおりに閉じているか）
- [ ] 主要な構成が**図**で示されているか（文章の壁になっていないか）
- [ ] 各図の直下の `<details><summary>設計意図</summary>` の中身が、構成図の描き直し・図の言い換えになっていないか（却下した代替案は書かず ADR へ出しているか）
- [ ] コードを読めば分かる具体パラメータ値を**書き写していない**か（二重管理していないか）
- [ ] 個々の設計判断が、中身を名指しした `##` セクションに立っているか（「重要なポイント」のような傘セクションを作っていないか。1セクション1決定で、書いてあるのは構成図に描かれていない内訳か）
- [ ] 「前提と制約」の節が技術的制約と組織の制約に分かれているか（該当なしは小節ごとに「なし」と明記されているか）
- [ ] 2文書の分担（何を組むか／どう作り・変えるか）を越えた記述が混ざっていないか

### インフラ設計書

- [ ] 組織の制約が IaC 設計書への参照で閉じているか（`####` の小節を持っていないか）
- [ ] リソースに課される規約（命名・タグ・暗号化・リージョン）が残っていないか

### IaC 設計書

- [ ] 手動作成リソースが漏れなく列挙されているか（なければ「なし」と明記されているか）
- [ ] スタック関係図にスタックの中身（個々のリソース）を描いていないか
- [ ] 命名規約にリソース命名とスタック命名の両方があるか
- [ ] 組織の制約が `####` の小節（タグ規則・その他の制約）に分かれているか

---

> [!IMPORTANT]
> 本ポリシーで最も重要な原則。
>
> - **コードが最大の SSoT**：設計書には全体像の図と設計判断（WHY）だけを書き、具体パラメータ値は書かない
> - **何を組むかと、どう作り・変えるかを別の文書に置く**：前者はインフラ設計書、後者は IaC 設計書が持つ
> - **必須セクションは「存在」を必須にする**：該当なしは「なし＋理由」で閉じ、未検討と対象外を読者が区別できるようにする
> - **文書の話に限定する**：コードの作り方は cdk-design-policy / cdk.md、監視項目の選び方は monitoring-policy へ委譲する
