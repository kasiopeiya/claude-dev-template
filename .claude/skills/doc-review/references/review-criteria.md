# 文書レビュー観点

文書レビューを行う AI が、どの観点を見て、何を違反とするか迷ったときに引く観点一覧。ハーネスの中で判定基準を置く唯一の場所であり（元になる規定は下の NOTE のポリシー2本）、観点をレンズへ束ねた対応表（doc-reviewer-agent の「レンズ一覧と担当観点」）には判定基準を書き写さない。

観点ごとに **準拠／違反／対象外** を判定し、違反は「severity の決め方」に従って severity 付きの指摘にする。点数は付けない。

観点は番号でなく**観点名で識別する**（agent 定義・レポート書式からも観点名で参照する）。番号を振ると、観点の増減で番号がずれ、参照側が無言で壊れるためである。

> [!NOTE]
> **（AI・必須）** 以下の判定基準は、速度のため `docs/policy/documentation-policy.md` と `docs/policy/documentation-policy-for-humans.md` から書き下した派生コピーである。どちらかが改訂されたら、ここも追従して見直すこと。

## 条件付き観点の読み方

観点名に**（〜のみ対象）**と注記のあるものは条件付き観点で、該当する文書だけを判定する（非該当は対象外）。注記のない観点は全文書共通。

- **種別**：`/doc-review` が `references/doc-types.md` で1回だけ決め、レンズに渡す
- **人間向け文書**：`docs/policy/documentation-policy-for-humans.md` の frontmatter `applies-to` に当たる文書。これも `/doc-review` が決めて渡す
- **パス**：注記にパスがあれば、種別にかかわらずその文書も対象にする

## 観点ごとの判定手順

表だけで判定しきれない観点の手順。見出しは観点名と同じにする。

### 完全性

種別ごとの必要セクション：

- **DESIGN**：概要、設計方針、実装詳細
- **PRD**：概要、目的、業務要件、要件
- **ARCHITECTURE**：概要、システム構成、AWSリソース
- **ISSUE_SPEC**：概要、依存、受け入れ基準
- **POLICY**：対象読者・目的、判断基準（宣言）

上に無い種別は対象外とする。

### 明確性

曖昧な表現のキーワード：

- 「適宜」「適切に」「必要に応じて」
- 「など」「とか」「等」（文末）
- 「〜的な」「〜っぽい」
- 「基本的に」「原則として」（例外が不明確）

用語の定義：初出の専門用語に説明があるか、略語の正式名称があるか。**POLICY は、一般的な専門用語・略語の説明を求めない**。このプロジェクト固有の語だけを見る。

よくある表記揺れの組：

- RP / Relying Party
- OP / OpenID Provider
- API Gateway / API GW / APIGW
- CloudFront / CF
- DynamoDB / DDB
- Lambda / ラムダ

### 同一文書内の規定衝突

長い文書ほど節が増え、部分改訂のたびに衝突が生まれるため、能動的に探さないと素通りする。

1. 「〜する」「〜してはならない」「〜の場合は〜」の形で書かれた規定を、節をまたいで全文から拾う。差分だけを見てはならない
2. 同じ対象（同じ語・同じ場面）を扱う規定同士を組にする
3. 組ごとに「同じ入力を与えたとき、両方に従えるか」を確かめる。従えないなら衝突として指摘する

衝突の典型：

- **同じ場面に逆の判定**：ある節「未決の問いは凍結前にすべて解消する」／別の節「未決のまま残してよい」
- **必須と任意の食い違い**：表で「必須」とした項目を、後続の節で「省略してよい」と書いている
- **例外の後出し**：「例外なく適用する」と宣言した規定に、別の節で条件付きの除外を足している

**報告のしかた**：どちらが正しいかを断定してはならない。どちらを残すかは書き手の判断であり、レビュアーが決めると誤った側に寄せたまま確定するからである。衝突する**両方の出典（節名・行番号）と、それぞれが与える判定**を並べて示し、どちらかに寄せることだけを求める。

### わかりやすさ

1. 冒頭の「対象読者」から、想定する知識レベルを取り出す
2. その知識レベルで理解できる説明になっているかを見る（例：対象読者がアプリケーションエンジニアなら、AWS サービスの解説があるか。専門用語の初出に簡単な説明があるか）

**POLICY は、一般的な技術・概念の補足の不足を指摘しない**。読者は一般的なソフトウェア工学の知識を持つ AI であり、一般的な技術・概念の解説は観点「一般知識の説明なし」で削る対象になる。

### 対象読者と目的

「対象読者」「目的」「概要」などのキーワードや、「本ドキュメントは」で始まる説明文は、探す手がかりにすぎない。合否は観点一覧の「違反と判定する条件」で決める。違反なら、具体的な追加例を改善案に添える。

### 図表の量

Mermaid ブロック・表・箇条書きの数を数え、文章量とのバランスを見る（目安は観点一覧の「違反と判定する条件」）。**図の数が多いこと自体を準拠の理由にしてはならない**——文章を図に詰め替えただけの図は、可視化ではなくノイズである（観点「無価値な図（逆変換テスト）」が削る）。

### 目的適合

1. 冒頭の対象読者・目的（・スコープ外）を基準として取り出す。宣言が無ければ冒頭・見出し構成から目的を推測する（推測に基づく指摘は [推奨] 止まりとし、その旨を明記する）
2. 各セクションについて「この内容は冒頭の目的のどの部分に奉仕するか」を1対1で照合する
3. どの目的にも奉仕しない／他文書の目的に属する／スコープ外に当たる記述を**列挙**し、**正しい配置先（別文書）への移動、または削除**を提案する

判定は「正しい情報か」ではなく「**この文書の目的に資するか**」で行う。正しいだけで目的に資さない記述（網羅のための列挙・読者の判断を変えない修飾）も違反とする。

### リンクの最小性

documentation-policy.md「他文書へのリンクは既定で張らない」に基づき、**本文中の他文書リンクを1本ずつ**検査する。まず Grep（パターン `\]\([^)]*\.md[^)]*\)`、output_mode: content、`-n` 付き）で全リンクを列挙してから判定する。目視で拾おうとすると取りこぼす。

判定テスト（**リンク削除テスト**）：「そのリンクを消したとき、読者はこの文書だけで判断・行動できるか？」できないなら、本文が足りていない証拠として指摘する。

- **結論を書かず「詳細は X を参照」で節を終えている**：読者が飛ばないと判断できない。結論を1〜2文で本文に転記させる
- **同一リンク先を1文書で2回以上張っている**：初出の1回に減らし、以降は文書名だけにする
- **`[原則2](x.md)` `[x §1](x.md)` のようにリンク先の内部番号を名指し**：リンク先の改訂で無言で壊れる。内容を一言で転記させる
- **理由・考え方をリンク先に委ね、この文書だけでは読み通せない**：DRY より SRP。結論を転記して単体完結させる

値・定義・一覧（用語集・ADR・rules）への SSOT リンクは正しい用法であり、指摘してはならない。

**「リンクがあるほど親切」という理由で指摘を見送ってはならない**——リンクは書く側には一瞬だが、読む側と保守する側にコストを回す。書き手が最も無自覚な箇所である。

### 無価値な図（逆変換テスト）

documentation-policy.md「図にする前に『逆変換テスト』を通す」に基づき、各図（Mermaid ブロック）を1つずつ次でチェックし、該当する図は「箇条書き・表へ戻す」を指摘する。

- **一直線（A→B→C）で分岐・合流・ループ・並行がない**：文章の言い換え。箇条書きへ戻す
- **1対1の対応・単純な列挙にすぎない**：箇条書きへ戻す（3列以上なら表）

判定テスト：「この図を表・箇条書きに戻したとき、文章を読まずに構造を掴めるか？」掴めるなら無価値な図として指摘する。掴めなくなる図——多対多・階層・状態遷移を含む図——は、テキストへ完全に復元できても価値がある（測るのは情報量ではなく認知負荷）。

### 2列以下の表／散文の列挙

documentation-policy-for-humans.md「項目の並びは箇条書きを既定にし、3列以上になるときだけ表にする」に基づき、次を能動的に探す。

- **文の中に、動詞を含む項目を3つ以上並べた列挙**：箇条書きに出す。「図・表・箇条書き」のような名詞の並びは対象外
- **1項目が名前のほかに2つ以上の情報を持つ並びが、散文のまま**：3列以上の表にする
- **2列以下の表**：名前と説明は用語リスト、名前と決まった値は値ごとにまとめた箇条書き、悪い例と良い例の対は `- ❌ 悪い例 → ✅ 良い例` に直す

判定は列数だけで行う。**「2項目の対比だから」「表の方が整って見える」を、2列以下の表を見逃す理由にしてはならない**——「項目と属性に分けられるか」で判定すると、どんな並びも表になってしまうからである。

ただし**分岐・合流・ループのある流れ、多対多の関係、階層、状態遷移は、箇条書き・表ではなく図（Mermaid）を提案する**。単一の主張・理由は対象外。**例外**：要件定義書（`docs/requirements.md`）は2列の表を指摘しない（`requirements-doc-policy.md` が2列でも表にすると上書きしている）。

### TL;DR

documentation-policy-for-humans.md「冒頭に「決定事項」を3行で先出しする（TL;DR）」に基づき、文書冒頭に `TL;DR`／「決定事項」の要約ブロックがある場合に次を見る。

- 決定1件1行の箇条書きになっていなければ違反（1段落べた書きは行数に関わらず違反）
- 本文（見出し行を除く）が4行以上あれば違反
- 突出した決定がある文書に限る。用語集・API一覧・テーブル定義・コーディング規約集・設計書（`docs/design/**` と `samples/docs/design/**`）は TL;DR 自体が無くてよく、対象外

### 目次

観点一覧の「違反と判定する条件」が定める行数を超える文書で次を見る。

- `## 目次` が対象読者の直後にあり、`##` と `###` の見出しがアンカーリンクで並び、`###` が `##` の下にネストしているか。各行に「決めていること」を添えた ADR の目次だけは `##` のみでよい
- 文書タイトル（`#`）と `## 目次` 自身が目次に入っていないか。入っていれば指摘し、両見出しの行末に `<!-- omit from toc -->` が付いているかも確認する

### 俯瞰の一覧

documentation-policy-for-humans.md「1つの文書の中でも俯瞰を先に置く」に基づく。

- 見るのは並びの直前で、文書の冒頭ではない。文書の行数も関係しない
- 目次があることは、一覧が無くてよい理由にならない。目次は話題しか示さず、一覧は各項目の中身を1行で示す

### 設計の理由・背景

「なぜ」「理由」「背景」「目的」のキーワードを手がかりに、設計判断ごとに理由があるかを見る。

### シーケンス図の妥当性

1. ` ```mermaid ` で始まるブロックのうち、`sequenceDiagram` を含むものを抽出する
2. 各ブロックで、participant の定義と `->>`（メッセージフロー）があるかを確認する。autonumber・Note の使用は推奨（無くても違反にしない）

### 異常ケース

設計の段階で見落とした異常ケースは、実装・テストまで素通りしてバグになる。書かれた仕様に、次の3種類の揺さぶりを1つずつ当てる。

- **入力**：空・0件・上限超え・不正な形式・重複・想定外の型
- **状態**：上流・依存先の失敗やタイムアウト、処理の途中での停止、リソースの枯渇、データが先に変わっている
- **順番**：同時実行、再実行・再試行、想定と逆の到着順、途中からの再開

揺さぶりごとに「この仕様どおりに作ると、どう振る舞うか」を文書の記述だけから答える。答えが破綻する（無限の再試行、データの不整合、二重処理など）か、文書から答えが出ないなら違反とする。API エンドポイントの記載があるときは、エラー時の応答（エラーの種類と返す内容）が書かれているかもここで見る。

**報告のしかた**：引用は、揺さぶりを当てた仕様の原文とする（扱いが無いことが問題なら、その処理を書いた節の全文を欠落確認範囲として引く）。指摘には、当てた入力・状態・順番と、そのとき起きること（または決まらないこと）を1文で書く。**文書が扱う範囲の外にある異常（その設計が担当しない層の障害など）は指摘しない**。

### 種別ごとの特別観点

- **ARCHITECTURE**：AWS リソース構成、コスト見積もり、セキュリティ考慮事項（「セキュリティ」「認証」「認可」「脆弱性」「攻撃」「防御」のキーワードを手がかりにする）
- **DESIGN**：API 設計の具体性。API エンドポイントの記載があるとき、リクエスト例・レスポンス例があるか（エラーケースは観点「異常ケース」が担当する）
- **PLAN**：依存関係の明示、受け入れ基準（AC）の具体性
- **ISSUE_SPEC**：AC のチェックリスト形式、依存 Issue の記載
- **GUIDELINE**：ルールの具体例、NG例の提示、新しく足した判定条件に、発火する入力の例（実出力の引用など）が添えてあるか
- **REFERENCE**：用語・項目の一貫性（表記揺れなし）、網羅性、SSOT 性（同じ定義が他文書と重複せず一箇所に集約）
- **HUB**：目的・対象読者の明記、配下文書への全リンクが有効、ハブから辿れない孤立文書がない、索引に徹する（本文で重複説明を抱えない）

上に無い種別（POLICY・ADR・GUIDE・GENERAL など）は対象外とする。POLICY・ADR はそれぞれの特有観点の行で見る。

### 配置と言語

- 置き場所：対象読者ごとの置き場所は `docs/reference/docs-directory-definitions.md`、リネーム禁止パスは README「変更してはならないパス」で引く
- 言語：日本語で書かれているか（CLAUDE.md「回答は日本語」）

### 要件定義書との照合

呼び出し側（`/design` など）が指示したときだけ判定する。指示が無ければ対象外とする。`docs/requirements.md` を Read し、機能要件・非機能要件・SLO のそれぞれについて、文書の記述が満たしているか・矛盾していないかを照合する。とくに SLO は、アーキテクチャの構造が目標を満たせるかに直結する。

## severity の決め方

違反は次の3段階で severity を付ける。観点の「違反と判定する条件」に severity の指定があるときは、そちらに従う。

- **[必須]**：読み手が誤った判断・行動をする、または文書が役目を果たせない（規定の衝突、目的の欠落など）
- **[推奨]**：いまは読めるが、保守の際に食い違う、または読み手が迷う（値の重複、曖昧語など）
- **[提案]**：読みやすさ・分かりやすさの改善（軽微な表記・構成のゆらぎなど）
