# Check Plan

Plan ファイルを **Issue 化（`/to-issues`）の前** に監査する。通常は `/to-plan` から自動で呼ばれるが、単体でも実行できる。

監査の本体は [`plan-reviewer-agent`](../../agents/plan-reviewer-agent/plan-reviewer-agent.md) が行う。Plan を書いたセッションが自分で点検すると、書かれていない前提を会話の記憶で補ってしまい、欠落に気づけないからである。**判定の観点は agent 定義が正典であり、ここには書き写さない。**

あわせて [`simplicity-advocate-agent`](../../agents/simplicity-advocate-agent/simplicity-advocate-agent.md)（問い役）が、Plan のタスクごとに「頼まれていないか」「もっと単純に済まないか」を問う。問い役は判定しない。問う規則も agent 定義が正典である。

このスキルが担うのは、次のことだけである。

- 会話と Plan の突き合わせ（agent は会話を見られない）
- 問いへの回答
- Plan の修正とユーザーへの確認

## 1. 対象 Plan の特定

上から順に見て、最初に当たったものを対象にする。

1. 引数でパスが渡されたらそれを使う。slug なら `~/.claude/plans/<slug>.md`、無ければ `~/.claude/plans/*-<slug>.md` を探す。
2. この会話で `/to-plan` または Plan モードが書き出したファイル。
3. Plan が会話上のテキストにしか無ければ、先に `/to-plan` でファイルにする（agent はファイルしか読めない）。
4. どれも無ければユーザーに確認する。`~/.claude/plans/` の最新ファイルは候補として示すだけにする（Plan モードが書き出した別件の Plan が混ざっているため）。

## 2. plan-reviewer-agent と問い役を起動する

`plan-reviewer-agent` と `simplicity-advocate-agent` を、1つのメッセージで同時に Task 起動する。会話の要約・作業の経緯・「ここを見てほしい」といった注文は、どちらにも渡さない。渡した時点で agent は書き手の前提を共有し、切り離した意味が消える。

- **`plan-reviewer-agent`**：Plan ファイルの絶対パス（`~` を展開したもの）だけを渡す
- **`simplicity-advocate-agent`**：Plan の `人間の発言：` の行・スコープの「やること」・タスク一覧の3つを、原文のまま写して渡す。**Plan のパスは渡さない**（パスを渡すと「設計判断とその根拠」など書き手の言い分まで読める）

問い役を起動するのは1回目だけで、手順4の再監査では起動しない。

起動したら結果を待たずに手順3を進める。

## 3. 会話と Plan を突き合わせる

agent は会話を見られないので、次の転記漏れと写し違いはここでしか見つからない。

- **grill-me で確定した仕様**：決定事項・判断の根拠・却下した代替案とその理由が、Plan の「grill-me で確定した仕様」に書かれているか
- **Not-now リスト**：全行が「やらないこと」欄に、トリガーと一緒に転記されているか
- **Plan モードでの調査結果**：判断の前提にした事実が Plan に残っているか
- **人間の発言と印**：`人間の発言：` の行と、決定の理由に付けた「」が、会話の人間の原文と一字一句同じか。人間が AI の選択肢・推奨を選んだ決定に（AI案を選択）が付いているか

## 4. 問いに答え、統合して Plan を修正する

### 問いに答える

問い役が返した問いに1件ずつ、残すか外すかと、その理由を答える。

- **外さない**：人間が決めたこと（「」の決定と（AI案を選択）の決定）から来たタスクと、ポリシーが求めるタスク。答えにその出どころを書いて残す。外すかは、報告を見た人間に任せる
- **外す**：タスク一覧と、その出どころの行（確定仕様・影響範囲など）から消す。消したタスクは、スコープの「やらないこと」に `<論点> — <何が起きたら決める必要が出るか>` の形で1行移す（例：「`needs-human-review` を付ける — 人間が求めたら」）。消すだけにすると、別セッションが足し直しうる

問いは重大度を持たず、合否（下記の Critical 0件）に数えない。

### 統合して修正する

`plan-reviewer-agent` の表に、手順3の各項目を1行ずつ足す。会話に該当する内容が無い項目は N/A とする。

合否・再監査回数の規定は [ai-review-gate-policy](../../../docs/policy/ai-review-gate-policy.md) に従う。

- 違反があれば、重大度にかかわらずすべて**Plan ファイルを修正する**（[ai-review-gate-policy](../../../docs/policy/ai-review-gate-policy.md)「残してよい例外」に当たらない限り、確認を挟まず直す）。その回に「残してよい例外」以外の Critical があったときだけ、修正後に `plan-reviewer-agent` をもう一度起動し、指摘が解消したかを確かめる。再監査のたびに手順2と同じくパスだけを渡し、前回の指摘は渡さない。
- 指摘が、この会話で人間が決めたことと食い違うときは、方針を変えない。その決定を「人間が決めたこと」として理由と一緒に Plan に書き足し、それを修正とする。理由には手順3と同じ印を付ける（人間の言葉は「」、AI の案を選んだものは（AI案を選択））。人間に問い直すのは、人間が判断の前提にした事実が誤っていたと確かめたときだけにする（監査の指摘で人間の判断を上書きしないため）。
- 監査は最大2回（初回を含む）。Critical が0件になった回で合格とし、「次は `/to-issues <Planパス>` で Issue 化できます」と案内する。
- 2回目の監査で指摘が出たら、Plan ファイルを修正したうえで再監査せずに「次は `/to-issues <Planパス>` で Issue 化できます」と案内する。

## 5. 報告

統合した表を報告する。形式は `plan-reviewer-agent` の出力形式に従う。

続けて、問い役の問いと手順4の答えを、表とは別に全件並べる。残したものも外したものも並べ、外したものは「やらないこと」に移した1行も添える。
