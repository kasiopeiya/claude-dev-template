# 進捗報告

引数（期間と `--all`）: `$ARGUMENTS`

人間だけが打てる。

`/perf-report` との違い：`/perf-report` は経営寄りの読み手に向けた HTML で、人ごとに分けない。この Skill はチームの会議やチャットに貼る Markdown で、人ごとに分ける。

既定は打った人（`gh` にログインしている人）の分だけにする。打つ人が欲しいのはたいてい自分の報告で、全員分だと自分の欄を探す手間と、要らない人の総括を書く時間がかかるからである。全員分が要るときは `--all` を付ける。

## なぜ一覧をスクリプトに任せるか

AI に Issue を数えさせると、レビュー通知や親 Issue を数えるかが打つたびにぶれ、報告どうしを比べられない。そこで、一覧は `scripts/progress-report.mjs` が出し、AI は Issue の分類と総括の文章だけを書く。分類は並べ方を変えるだけで、載せる Issue と件数はスクリプトが決めたままにする。誰の分を出すかの絞り込みも、同じ理由でスクリプトが行う。

## 手順

### 1. 一覧を取る

```bash
npm run --silent progress-report -- $ARGUMENTS
```

- **失敗したら**：標準エラーをそのまま伝えて終える。Issue を手で数えて補わない
- **`workIssueCount` が 0 のとき**：期間内に作業 Issue が無かったこと（`--all` が無ければ、自分の分が無かったこと）を1行で伝えて終える。このとき JSON は `{"repository":"owner/repo","from":"2020-01-01","to":"2020-01-01","workIssueCount":0,"assigneeSections":[]}` の形になる

JSON の `assigneeSections` は人ごとの欄の配列で、1つの欄は次のキーを持つ。

| キー         | 中身                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------ |
| `assignee`   | ログイン名。assignee の無い Issue の欄は「担当なし」                                       |
| `workIssues` | その人の作業 Issue。1件ごとに `number`・`title`・`body`・`closingPullRequestTitles` を持つ |

### 2. 一覧を並べる

`assigneeSections` を、出てきた順のまま並べる。`assignee` はそのまま1行に書く（`#` は付けない）。その下で、その人の `workIssues` を何の作業かで分類し、分類ごとに `### <分類名>` の見出しを立てて、Issue を `- #<number> 「<title>」` の1行ずつ並べる。

- **分類の材料は、その Issue の `title` と `body` だけにする**
- **分類名は、何の作業かを名指しする**：✅ 「要件定義書の改善」「要件定義ハーネスの仕組み改善」 ❌ 「その他」「改善」（何の作業か分からない）。1件だけの分類があってよい
- **Issue を足さない・省かない**：1件は1つの分類にだけ入れる。`--all` を付けたとき、assignee が複数の Issue が全員の欄に載るのも仕様である
- **並べる順は出てきた順から決める**：分類の中の Issue は出てきた順のまま並べ、分類どうしは、中の最初の Issue が出てきた順に並べる
- **`title` は書き換えない**：タイトル先頭の着手順の数字（`3. `・`1〜3. `）は、スクリプトが外してある

### 3. 総括を書く

人ごとに、**3文までの1段落**で総括を書く。総括は一覧の要約なので、Issue を1件ずつ拾わず、主な流れを2〜3個に絞って書く。「行」で数えないのは、Markdown では長い1行も1行に数えられ、長さの上限にならないためである。

材料は、その人の欄の `body` と `closingPullRequestTitles` だけにする。「担当なし」の欄にも、ほかの欄と同じく総括を書く。材料を増やすために `gh` や `git` を打たない。

- ✅ 「/perf-report を、ひな形を埋めるスクリプトと AI の考察で作る形に作り替えた。着手判定と実装フローの Skill 選びをスクリプトに移し、/progress-report を新設した。」（主な流れだけを2文で書いている）
- ✅ PR タイトルが「/perf-report に差分行数の分布を足す」なら、「/perf-report に差分行数の分布を足した」と書く
- ❌ 「報告の手間が半分になった」と書く（本文にも PR タイトルにも無い効果を足している）

### 4. 出力する

次の形の Markdown を、コードブロック1つでターミナルに出す。ログイン名・番号は例。

```text
alice

### 進捗報告の仕組み
- #11 「進捗報告用のSkillを作成する」
- #14 「...」

### 要件定義書の改善
- #12 「...」

（総括）

bob

### 要件定義ハーネスの仕組み改善
- #13 「hoge」

（総括）
```

- 期間の見出しと、チーム全体の総括は足さない（足す要望が出たら、Skill を直すかどうかを人間と決める）
