# コードレビュー観点

コードレビューを行う AI・人間が、どの観点を見て、何を違反とするか迷ったときに引く観点一覧。

観点ごとに **準拠／違反／対象外** を判定し、違反は「severity の決め方」に従って severity 付きの指摘にする。点数は付けない。

観点には全ファイル共通のものと、**特定のファイル種別・要素にのみ適用される条件付き観点**がある。条件付き観点は対象外のファイルでは判定せず「対象外」とする。

> [!IMPORTANT]
> **（AI・必須）** 観点一覧の行は能動的に探す対象＝レビューの背骨である。ここには**機械（ESLint/knip）で測れない判断項目だけ**を載せる。書き方の規約のうち ESLint/knip/Prettier が error で落とせるもの（型 `any`・Import 順序・未使用宣言・関数長・引数数・マジックナンバー・ネスト深度など）は CI ゲートで担保し、本一覧からは外す（次の「CI ゲートで機械的に担保される観点」参照）。機械化できない判断項目は一覧の行にしないと素通りするため、行にすることが品質の生命線となる。

> [!TIP]
> **（AI・人間にも）** 人間レビュワーと共通の観点（インターフェース・コメント・名前の妥当性をどう見るか）は [code-review-guide「Part B：レビューの観点」](../../../../docs/guide/code-review-guide.md) を参照。

## CI ゲートで機械的に担保される観点（判定対象外）

次の観点は ESLint / knip / Prettier が **error で機械的に検知**するため、LLM の判定から外す（CI ゲートを SSOT とし、二重に判定しない）。設定の実体は `eslint.config.mjs` / `knip.jsonc` / `.prettierrc.js`、しきい値の根拠は `.claude/rules/typescript.md` を参照。

- **型安全性（`any` 禁止）**：ESLint `@typescript-eslint/no-explicit-any`
- **関数の長さ（50行）**：ESLint `max-lines-per-function`
- **引数の数（3個）**：ESLint `max-params`
- **マジックナンバー**：ESLint `no-magic-numbers`（src 限定）
- **非同期処理（浮いた Promise・誤用）**：ESLint `@typescript-eslint/no-floating-promises` / `no-misused-promises`
- **未使用宣言（変数・引数・optional 含む）**：ESLint `@typescript-eslint/no-unused-vars`（`args:'all'`）＋ knip
- **不要な export（本番コードからも未参照）**：knip（未使用 export 検知）。テストからのみ参照される export は検出しないため、下の観点一覧「テスト専用 export」で見る
- **Import 順序・冒頭集約**：ESLint `import-x/order` / `import-x/first`
- **ネスト深度・複雑度**：ESLint `max-depth` / `complexity` / `sonarjs/cognitive-complexity`
- **改行スタイル（1行に収まる引数・オブジェクト・配列はインライン）**：Prettier `objectWrap: 'collapse'`（`format:check`）
- **テスト内の if 文禁止（テストファイルのみ）**：ESLint `no-restricted-syntax`（`IfStatement`）
- **テストケース名の日本語必須（テストファイルのみ）**：ESLint `no-restricted-syntax`（`it`/`test`/`describe` 名）

下の観点一覧の観点は**観点名で識別する**（他ドキュメントからも観点名で参照する）。番号を振ると、観点の増減で番号がずれ、参照側が無言で壊れるためである。

## レビュー観点

観点名に**（〜のみ対象）**と注記のあるものは条件付き観点で、該当ファイルのみ判定する（非該当は対象外）。注記のない観点は全ファイル共通。

| 観点                                                               | チェック内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | 違反と判定する条件                                                                                                                           |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **命名規則・変数名の妥当性**                                       | 名前が用途を伝え、命名の規約に合うか。利用目的や用途が名前から想像できるか（❌ `mainFunc` ⭕ `accountFunc`）。名前と実際の振る舞いのずれは観点「名前と実装の一致」が担当する                                                                                                                                                                                                                                                                                                                                      | 用途が名前から読み取れない、同じものを指す名前が揺れている、または命名の規約に反する名前がある                                               |
| **名前と実装の一致**                                               | 関数・変数が名前どおりに動くか。名前が振る舞いを隠していないか（`getUser` が裏で更新している、`isValid` が値を書き換える、など）。名前の分かりやすさそのものは観点「命名規則・変数名の妥当性」が担当する                                                                                                                                                                                                                                                                                                          | 名前から読める振る舞いと、実装の振る舞いが食い違う箇所がある                                                                                 |
| **境界と異常値**                                                   | 実際に届きうる値——`null`/`undefined`/空配列/空文字/`0`/最大最小値/型境界——で、ロジックが正しい結果を返すか（off-by-one、`0` を偽として扱う、空配列の集計など）。信頼境界から入る値の扱いを決めているかは観点「エラーハンドリング」が担当し、内部の関数どうしの引数への防御的チェックは求めない                                                                                                                                                                                                                    | 届きうる値のうち、ロジックが誤った結果を返す、または落ちる値を具体的に示せる                                                                 |
| **例外の経路**                                                     | throw されうる箇所から呼び出し元までの経路。catch での握り潰し、失敗時に状態が半端に更新される経路、リソースが解放されない経路。try ブロックの長さは観点「tryブロックの長さ」、エラーメッセージの中身は観点「エラーハンドリング」が担当する                                                                                                                                                                                                                                                                       | 例外が握り潰される、または失敗時に状態・リソースが半端に残る経路がある                                                                       |
| **非同期の実害**                                                   | await 漏れ・浮いた Promise の検知は CI ゲートが担保する。ここでは**その実害**——実行順序の逆転・競合・二重実行・`Promise.all` の誤用（1つの失敗で残りの結果を捨てる、順序依存の処理を並列にする）——を判定する                                                                                                                                                                                                                                                                                                      | 非同期処理の順序・並列の扱いが原因で、結果が誤る、または処理が重複する経路を示せる                                                           |
| **副作用と不変条件**                                               | 引数・共有状態・イミュータブルであるべき値を想定外に書き換えていないか。呼び出し側が前提にしている不変条件（整列済み・重複なし・合計が一致する、など）を壊していないか。副作用を名前が隠していることは観点「名前と実装の一致」が担当する                                                                                                                                                                                                                                                                          | 呼び出し側が見ている値・共有状態を想定外に書き換える、または不変条件を壊す箇所がある                                                         |
| **インターフェース**                                               | 関数・モジュールが外部に見せる境界。引数・戻り値がその関数の意味に対し過不足ないか。利用側が誤用しにくいか（不正な状態を型で排除できているか、同じ型の引数が並んで順序を取り違えやすくないか）。optional の要否は観点「不要な optional 宣言」が担当する                                                                                                                                                                                                                                                           | 引数・戻り値に過不足がある、または不正な状態・引数の取り違えを型で防げるのに許している                                                       |
| **重複コード（DRY・文脈判断）**                                    | **DRY は常時遵守の原則ではない。**SRP を優先した意図的なコピペは許容する。重複が**偶有的（除去すべき）か本質的（無理に共通化すると誤った結合になる）か**を文脈で判断し、偶有的な重複・誤った共通化の兆候のみ指摘する。文脈把握が要るため機械検知（jscpd 等）にはしない                                                                                                                                                                                                                                            | 偶有的な（除去すべき）重複、または誤った共通化がある                                                                                         |
| **単一責任**                                                       | 関数・モジュールの責務の明確性。判定軸は `docs/policy/application-design-policy.md` の**一文テスト**（SSOT。判定基準は本一覧に転記しない）                                                                                                                                                                                                                                                                                                                                                                        | 責務を一文で言えない単位がある（一文に "and" が混ざる）                                                                                      |
| **不要な optional 宣言**                                           | 常に渡される引数・必ず存在するプロパティなのに `?` を付けていないか（未使用宣言そのものの検知は CI ゲートが担保。ここは「本来 required にすべきものを optional にしていないか」という設計判断に集中する）                                                                                                                                                                                                                                                                                                         | required にすべき引数・プロパティに `?` が付いている                                                                                         |
| **コメント**                                                       | `docs/policy/code-comment-policy.md` に準拠しているか（SSOT。実装コメントは WHY・doc comment は契約・ファイル冒頭コメントは責務と前提・名前で消せるコメントの有無）。具体基準はポリシー側に置き本一覧に転記しない                                                                                                                                                                                                                                                                                                 | ポリシーに反するコメントがある、またはポリシーが求めるコメントが無い                                                                         |
| **エラーハンドリング**                                             | 信頼境界から入る値の欠損・極値・型の逸脱の扱いが決まっているか（判定軸は `docs/policy/application-design-policy.md` の「信頼境界から入る値は、異常値の扱いを決めよ」。内部の関数どうしの引数への防御的チェックは求めない）。あわせてエラーメッセージが原因を伝えるか。境界を越えた後のロジックの誤りは観点「境界と異常値」、例外の伝わり方は観点「例外の経路」が担当する                                                                                                                                          | 境界から入る値の扱いが決まっていない値・区分がある、またはエラーメッセージが原因を伝えない                                                   |
| **セキュリティ**                                                   | ハードコード・環境変数の適切な扱い（非 null 断定 `process.env.X!` を含む）・インジェクション対策                                                                                                                                                                                                                                                                                                                                                                                                                  | 機密の実値の埋め込み・インジェクションの余地・環境変数の欠落を検知しない扱いがある                                                           |
| **tryブロックの長さ**                                              | try ブロック内のコード行数。長い try ブロックは例外発生箇所の特定を困難にし、意図しない例外の捕捉につながる                                                                                                                                                                                                                                                                                                                                                                                                       | 21行以上の try ブロックがある（41行以上は Recommended、21〜40行は Suggested）                                                                |
| **ネスト回避の小手先**                                             | ネスト深度そのものは CI ゲート（`max-depth`／複雑度）が担保する。ここでは**数を見た目だけ減らす回避**——ネスト逃れの `.then`/`.catch` チェーン化、多段三項など——を検出する。ヒットは即違反ではなく、複雑さを温存したまま平坦化しただけかを文脈で判定する。正しい対処は責務分割・早期return（`.claude/rules/typescript.md`「ネスト制限は『設計を見直せ』というシグナル」）                                                                                                                                          | 複雑さを温存したまま平坦化しただけの箇所が1つでもある（Recommended 以上）                                                                    |
| **テスト専用 export**                                              | 本番コードからは呼ばれず、テストからだけ import されている `export` がないか（`.claude/rules/typescript.md`「`export` は外部から参照されるものだけに付ける」の違反）                                                                                                                                                                                                                                                                                                                                              | テストからだけ import される export がある                                                                                                   |
| **不要なpublic公開**                                               | クラスのメンバ変数・メソッドに `public`（または修飾子なし）が付いているが、クラス外から参照されていないか。外部から使われないメンバは `private` または `protected` にすること                                                                                                                                                                                                                                                                                                                                     | クラス外から参照されない public メンバがある                                                                                                 |
| **構成管理ポリシー準拠**                                           | `docs/policy/configuration-policy.md` に準拠しているか。**判定基準は同ポリシーを唯一の正典（SSOT）とし本一覧には転記しない**（ポリシーの追補で本行を更新せずに済むよう、具体チェックはポリシー側だけに置く）。構成値を扱わないファイルは対象外                                                                                                                                                                                                                                                                    | ポリシーに反する箇所がある（機密実値の埋め込み等は Critical。観点「セキュリティ」にも当たるときは、指摘は1件だけ出し、両方の行を違反とする） |
| **アプリ設計ポリシー準拠**                                         | `docs/policy/application-design-policy.md` に準拠しているか（SSOT）。判定基準はポリシー側に置き本一覧に転記しない                                                                                                                                                                                                                                                                                                                                                                                                 | ポリシーに反する箇所がある                                                                                                                   |
| **ロギングポリシー準拠**                                           | `docs/policy/application-logging-policy.md` に準拠しているか（SSOT）。判定基準はポリシー側に置き本一覧に転記しない。ログ出力を含まないファイルは対象外                                                                                                                                                                                                                                                                                                                                                            | ポリシーに反する箇所がある（個人情報・認証情報の出力等は Critical）                                                                          |
| **フロントエンド設計ポリシー準拠**（フロントエンドコードのみ対象） | `docs/policy/frontend-design-policy.md` に準拠しているか（SSOT）。判定基準はポリシー側に置き本一覧に転記しない。非フロントエンドファイルは対象外                                                                                                                                                                                                                                                                                                                                                                  | ポリシーに反する箇所がある                                                                                                                   |
| **単体テストポリシー準拠**（テストコードのみ対象）                 | `docs/policy/unit-test-policy.md` に準拠しているか（SSOT）。判定基準はポリシー側に置き本一覧に転記しない。テストファイル以外は対象外                                                                                                                                                                                                                                                                                                                                                                              | ポリシーに反する箇所がある                                                                                                                   |
| **異常系テストの網羅**（実装コードのみ対象）                       | 実装の異常系分岐に、対応するテストがあるか。対応するテストファイルは `docs/policy/test-strategy-policy.md` の配置規約（`test/` 配下に実装のディレクトリ構造をミラーする）で実装ファイルのパスから引き、実装の分岐と1つずつ突き合わせる。判定基準（テストを書く分岐・書かない条件）は `docs/policy/unit-test-policy.md` を唯一の正典（SSOT）とし本一覧には転記しない。同ポリシー「テスト対象外」に当たる実装ファイルとテストファイル自体は対象外。テストコード側の書き方は観点「単体テストポリシー準拠」が担当する | テストを書かない条件に当たらない分岐にテストが無く、そのテストが無いことで素通りするバグを引用付きで示せる。テストファイルが無い場合も違反   |

## severity の決め方

違反は次の3段階で severity を付ける。観点の「違反と判定する条件」に severity の指定があるときは、そちらに従う。

- **Critical**：放置すると誤動作・セキュリティ事故・データ損失につながる（実害を示せるロジックの誤り、機密実値の埋め込みなど）
- **Recommended**：いまは動くが、変更や保守の際に壊れやすい（設計原則・ポリシーの違反など）
- **Suggested**：読みやすさ・分かりやすさの改善（命名・コメントの軽微なゆらぎなど）

## 観点一覧の外の確認点（確認点として報告）

観点一覧の判定には含めないが、レビュー時に必ず確認し「確認点」セクションとして報告する。

- **設定値の妥当性**：タイムアウト・保存期間・リトライ回数などの設定値が要件に合っているか

## 種別ごとの重点観点

- **Handler**：セキュリティ・エラーハンドリング・異常系テストの網羅
- **Utility**：単一責任
- **Page / Component**：フロントエンド設計ポリシー準拠・命名規則・変数名の妥当性・単一責任
- **Context**：フロントエンド設計ポリシー準拠
- **Test**：単体テストポリシー準拠・命名規則・変数名の妥当性
- **Module**：重点なし
