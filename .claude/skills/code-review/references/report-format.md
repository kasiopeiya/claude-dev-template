# レビューレポートフォーマット

code-reviewer-agent が Phase 3 でレポートを出すときの書式。観点の判定基準は review-criteria.md に置く。

点数・総合評価・良い点は、どの欄にも書かない。結果を使う側（/code-dev など）は指摘の有無と severity だけで直すかを決めており、良い点を求めると、見る観点の少ないレビューでは良い点のでっち上げを招く。

## 個別ファイルレポート

```
## Code Review Report

### 📁 ファイル情報
- **ファイル**: `<ファイルパス>`
- **種別**: <Test / Handler / Utility / Page / Context / Component / Module>
- **最終更新**: <git log による最終コミット情報>

### 📋 観点ごとの判定

<!--
review-criteria.md の観点一覧を上から順に全行書き出す（行を省かない）。観点名は一覧の行名と一字一句同じにする。
判定は 準拠 / 違反 / 対象外 のいずれか。違反の行には、下の「改善が必要な点」に出した指摘の数を書く。
-->

| 観点 | 判定 | 指摘の数 |
| --- | --- | --- |
| <観点一覧の行名> | <準拠 / 違反 / 対象外> | <違反なら件数、それ以外は -> |

---

### 🔧 改善が必要な点

#### 🚨 必須（Critical）
<!-- 放置すると誤動作・セキュリティ事故・データ損失につながる違反（review-criteria.md「severity の決め方」） -->

- **<観点名>**: <具体的な問題の説明>
  - **場所**: `<ファイルパス>:<行番号>`
  - **引用**: `<対象ファイルからコピーしたコード1〜3行。欠落の指摘なら、欠落を確認した範囲のコード>`
  - **提案**: `<改善後のコード例>`
  - **理由**: <なぜこの改善が必要か>

#### ⚠️ 推奨（Recommended）
<!-- いまは動くが、変更や保守の際に壊れやすい違反 -->

- **<観点名>**: <具体的な問題の説明>
  - **場所**: `<ファイルパス>:<行番号>`
  - **引用**: `<対象ファイルからコピーしたコード1〜3行。欠落の指摘なら、欠落を確認した範囲のコード>`
  - **提案**: `<改善後のコード例>`
  - **理由**: <なぜこの改善が必要か>

#### 💡 提案（Suggested）
<!-- 読みやすさ・分かりやすさの改善 -->

- **<観点名>**: <具体的な提案>
  - **場所**: `<ファイルパス>:<行番号>`
  - **引用**: `<対象ファイルからコピーしたコード1〜3行。欠落の指摘なら、欠落を確認した範囲のコード>`
  - **提案**: `<改善後のコード例>`
  - **理由**: <なぜこの改善が良いか>

#### ❓ 確認点（Review Questions）
<!-- 観点一覧の外。設定値の妥当性・動作への影響など、実装者に念のため確認しておきたいポイント -->
<!-- 例: タイムアウト値が要件に合っているか、ログ保存期間が適切か、など -->

- **<確認したい観点>**: <具体的な確認内容>
  - **場所**: `<ファイルパス>:<行番号>`
  - **現状**: `<現在の設定や実装>`
  - **確認事項**: <何を確認してほしいか・どのような懸念があるか>
```
