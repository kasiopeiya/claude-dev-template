# アーキテクチャレビュー観点

`/arch-review` が並列起動するレンズの担当観点一覧。観点ごとに **準拠／違反／対象外** を判定し、違反は「severity の決め方」に従って severity 付きの指摘にする。点数は付けない。レンズの数・名前・担当観点の対応は `architecture-reviewer-agent` 定義の「レンズ一覧と担当観点」が正典であり、本一覧には書き写さない。指摘を出してよい条件（引用の箇所数）は `architecture-reviewer-agent`「レビューの前提」が唯一の正典であり、本一覧には書き写さない。

観点には全レビュー共通のものと、**新規開発（0 からの立ち上げ）のときのみ判定する条件付き観点**がある。条件付き観点は行名に「（新規開発のみ対象）」と付け、既存改修では対象外とする。「決定の遅延」は新規開発・既存改修を問わず全レビュー共通で判定する（新規開発では特に重要という位置づけ）。

判定基準の詳細（何を違反とするか）は各正典 policy が SSOT であり、本一覧には転記しない。

## 観点一覧

| 観点                                             | 何を見るか                                                                                                            | 正典 policy                                                                                                                       |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **変更容易性／方針と詳細の分離**                 | 依存性のルール（ソース依存が安定方針へ内向きか）。DB・UI・外部サービス・言語・FW が境界の外へ追い出され差し替え可能か | `docs/policy/application-architecture-policy.md`「変更容易性」／ `docs/policy/refined-engineer-judgment-principles.md` 冒頭の定義 |
| **依存の設計侵入**                               | 外部ライブラリ（ORM 等）が Domain Entity と密結合し、設計の中核に食い込んでいないか                                   | `docs/policy/dependency-policy.md`                                                                                                |
| **テスト容易性**                                 | 境界がテストダブルでの差し替えを可能にし、ドメインを隔離してテストできる構造か                                        | `docs/policy/application-architecture-policy.md`「テスト容易性」                                                                  |
| **凝集と結合（Connascence）**                    | ファイルをまたぐ結合を強度×局所性（対角線ルール）で判定する                                                           | `docs/policy/application-architecture-policy.md`「凝集と結合」                                                                    |
| **特性の均衡（過剰設計）**                       | いま不要な拡張点・先回りした抽象化（投機的な境界）を作っていないか                                                    | `docs/policy/application-architecture-policy.md`「メタ原則」／ `docs/policy/refined-engineer-judgment-principles.md`「YAGNI」     |
| **決定の遅延**                                   | まだ決めなくてよい詳細（DB 製品・外部サービス等）を早期に具体実装で固定していないか                                   | `docs/policy/refined-engineer-judgment-principles.md`「決定を遅らせる」                                                           |
| **曳光弾（新規開発のみ対象）**                   | 薄い縦スライス（walking skeleton）を先に通し育てる形か（big-design-up-front でないか）                                | `docs/policy/new-development-policy.md`                                                                                           |
| **コアから着手（新規開発のみ対象）**             | ドメイン／コアから着手し、FW・DB・画面の詳細を後回しにできているか                                                    | `docs/policy/new-development-policy.md`                                                                                           |
| **意図を表出する構造（Screaming Architecture）** | ディレクトリ・レイヤー構成が FW／インフラではなくドメイン（何のためのシステムか）を語るか                             | `docs/policy/application-architecture-policy.md`「意図を表出する構造」                                                            |
| **初期ディレクトリ構成（新規開発のみ対象）**     | 初期ディレクトリ構成が FW 既定の技術レイヤー割りでなくドメインを語るか                                                | `docs/policy/new-development-policy.md`                                                                                           |

## 「揺れうる」の定義（複数の観点で使う共通語）

要件定義書・ADR にその詳細が「揺れうる」と書かれているとは、将来・移行予定・未定・選定中などの語で書かれた記述があるとき、または ADR の Status が「提案（Proposed）」など未確定を示すときを指す。記載が無い詳細は「揺れうる」に数えない（＝確定済み扱い）。ただし、要件・ADR のどこにも製品・実装が1つも選ばれていない詳細は「未決」であり確定済みではない——境界＋スタブ（決定の遅延の理想手順）で留めている限り、「決定の遅延」「特性の均衡」のどちらでも違反にしない。

## severity の決め方

重大度（Critical / High / Medium）の定義は [ai-review-gate-policy](../../../../docs/policy/ai-review-gate-policy.md) が正典。観点一覧の全10行について、次のとおり severity を割り当てる。

| 観点                                         | Critical                                                                                    | High                                                                                                                                                                                                             | Medium                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 変更容易性／方針と詳細の分離                 | 境界が無く（詳細がドメインに直接癒着しており）、かつその詳細が上の「揺れうる」に当たるとき  | 境界が無いが、揺れうるに当たらない詳細のとき                                                                                                                                                                     | —                                                  |
| 依存の設計侵入                               | —                                                                                           | 外部ライブラリが Domain Entity と密結合しているとき                                                                                                                                                              | —                                                  |
| テスト容易性                                 | —                                                                                           | テストダブルでの差し替えができず、ドメインを隔離してテストできないとき                                                                                                                                           | —                                                  |
| 凝集と結合（Connascence）                    | ✕（強結合×遠い局所性）が**ドメイン層をまたいだ**とき（定義は agent 定義「層の決め方」参照） | ✕（ドメイン層をまたがないもの）、または △ のとき                                                                                                                                                                 | —                                                  |
| 特性の均衡（過剰設計）                       | —                                                                                           | 投機的な抽象化・不要な拡張点があるとき                                                                                                                                                                           | —                                                  |
| 決定の遅延                                   | —                                                                                           | 早すぎる詳細の固定があるとき                                                                                                                                                                                     | —                                                  |
| 曳光弾（新規開発のみ対象）                   | —                                                                                           | big-design-up-front になっているとき                                                                                                                                                                             | —                                                  |
| コアから着手（新規開発のみ対象）             | —                                                                                           | 詳細（FW・DB・画面）から先に着手しているとき                                                                                                                                                                     | —                                                  |
| 意図を表出する構造（Screaming Architecture） | —                                                                                           | 最上位がドメイン名を一切語らず、FW／インフラ由来の名前、または技術レイヤー名（`domain/`・`usecase/`・`controllers/`・`services/`・`repositories/` 等、アーキテクチャパターン上の役割名）だけで構成されているとき | 大枠はドメインを語れているが一部にゆらぎがあるとき |
| 初期ディレクトリ構成（新規開発のみ対象）     | —                                                                                           | 初期ディレクトリ構成が FW 既定の技術レイヤー割りになっているとき                                                                                                                                                 | —                                                  |

Connascence の ✕・△ は `docs/policy/application-architecture-policy.md`「凝集と結合」のマトリクスで引く（本一覧・agent 定義のどちらにもマス目を書き写さない。マトリクスの改訂に自動で追従させるため）。

### 例（Critical と High の対比）

- 変更容易性／方針と詳細の分離：要件定義書に「将来オンプレ DB への移行がありうる」と書かれた永続化で、ドメインが特定 DB の SDK を直接 import している → Critical。同じ漏れでも、揺れうるとの記載が要件・ADR に無ければ High
- 凝集と結合：`domain/order.ts` と `infrastructure/orderRepository.ts` が注文状態の値 `'PAID'` を別々に持つ（Value・強×遠い）→ ドメイン層をまたぐ ✕ → Critical。`infrastructure/`↔`handlers/` だけの ✕ のように、どちらの端もドメイン層でなければ → High
- 意図を表出する構造：最上位が `controllers/`・`services/`・`repositories/` だけでドメイン名が出てこない → High。最上位は `order/`・`billing/` とドメインを語るが、共通部品だけ `utils/` のような技術名で置かれている → Medium

変更プローブ（「差し替えて壊す」レンズが実行）で詳細側の変更がドメイン層または上位層へ貫通したと実測できた場合は、「変更容易性／方針と詳細の分離」の「境界が無い」ことの直接証拠として使う（プローブの貫通自体は severity を決めない）。
