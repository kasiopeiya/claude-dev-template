要件定義書（PRD）をレビューしてください。あなたはレビュー本体を行わず、**レンズごとに割って並列に走らせ、返ってきた結果を統合する**役です（`--stage` のときは、統合のあと指摘を直す役も兼ねます）。

1体に全部を見せると、チェックリスト全行・BABOK 全項目・非機能要件カタログ・入力資料を同時に照合することになり、読むものが多すぎて見きれません。判定がぶれると要件定義書はいつまでも凍結できません。

## Phase 1: 入力を特定し、レンズを並列に起動する

引数から `--stage <記載段階>` を取り除いたうえで、残りが空の場合は `docs/requirements.md` を対象とします。先頭にファイルパスがある場合はそれを対象とし、その後ろがあれば入力資料（RFC・ヒアリング議事録等）のパスとして扱います。

### `--stage` を読み、判定対象とレンズを決める

`--stage` が無ければこの節を飛ばし、文書全体・全レンズで判定します（凍結判定）。ある場合は（例：`/requirements-review --stage 2` は、記載段階2以下の項目を判定する）、要件定義書を記載段階の途中で見ます。未記載の後段階の項目を欠落と見ないためです。

`.claude/rule-bodies/requirements-doc.md` の「項目一覧」「記載段階」節（「前段階から後段階へ書いてよいもの」を含む）「相互参照（トレーサビリティ）」を Read し、次を求めます。

1. `--stage` の値が項目一覧の `記載段階` 列に現れなければ、「指定された記載段階がありません: <値>」と出力して終了する
2. **判定対象の項目**：`記載段階` 列がその値以下の項目。サブ項目は親の項目の段階に従う
3. **後段階が埋める列**：「前段階から後段階へ書いてよいもの」が挙げる列のうち、判定対象の項目の表にあり、かつその列を埋める段階が `--stage` の値より後のもの。埋める段階が値以下の列は、空欄を欠落として判定する
4. **起動するレンズ**：`requirements-reviewer-agent` のレンズ一覧を Read し、判定対象の項目を担当する節を持つレンズを選ぶ。次の2つを足し、1つを外す
   - 足す：L1。原則の節（What/How・出所ラベルなど）は書いた本文に当てる観点で、台帳の突合も持つので、毎回起動する
   - 足す：判定対象の項目の表が追跡列を持つときは、相互参照の節を担当するレンズ
   - 外す：L5。可読性は凍結判定で見る

各レンズが何を見て何を見ないか（見るのは差分ではなく判定対象の項目の全文、など）は、`requirements-reviewer-agent` の「判定対象が渡されたとき」が正典です。

### 入力資料を特定し、レンズを並列に起動する

**入力資料の特定（起動前に必ず実施）**：ポリシーのチェックリストには入力資料との突合が不可欠な行（出所ラベル・網羅性〔要求の全数仕分け〕）があります。次の順で入力資料を特定してください。

1. 引数で入力資料パスが渡されていればそれを使う
2. 渡されていなければ、要件定義書の「背景・入力元」セクションから参照を辿る（辿れる参照が無い場合、それ自体を「背景・入力元の不備」として NG 指摘する）
3. どちらでも特定できない場合、入力資料に依存するチェック行を**推測で判定せず「判定不能（入力資料未提供）」とレビュー結果に明記**し、合否は保留側（凍結不可）に倒す

続いて `requirements-reviewer-agent` を、**レンズごとに1回ずつ、1メッセージ内でまとめて** Task 起動します。逐次に投げると、読む量を分けた意味（速さ）が消えます。各起動には次を渡してください。

- **レンズ名**：レンズ一覧のうち1つ
- **対象パス**：レビュー対象の要件定義書
- **入力資料のパス**：特定できたもの（L1 が使う。無ければ渡さない）
- **台帳のパス**：`.claude/rule-bodies/requirements-doc.md`「仕分け台帳」節が定める置き場。対象と同じディレクトリに `requirements-triage.md` があれば、そちらを渡す（L1 が使う。どちらも無ければ渡さず、網羅性と凍結条件を「判定不能（台帳なし）」として保留側に倒す）
- **`--stage` のときだけ**：記載段階の値・判定対象の項目・後段階が埋める列

**レンズの一覧と担当は `requirements-reviewer-agent` の定義が正典です。** ここに書き写しません——2箇所に持つと、割り方を変えたときに片方が古いまま残ります。

## Phase 2: 統合とカバレッジ検証

### 指摘を統合する

各レンズのレポートを1つにまとめます。

- **同じ箇所への重複指摘は1件にまとめる。** 引用が重なっていれば同じ指摘とみなす
- **引用の無い指摘は、統合の時点で落とす**
- severity（Critical / High / Medium）はレンズの判定を尊重し、統合側で下げない
- **修正案が食い違ったら裁定する**：同じ箇所に別々のレンズが逆向きの修正案を出したら、ポリシーの条文（該当が無ければ `docs/policy/refined-engineer-judgment-principles.md`）を引用して一方を採り、捨てた修正案と根拠を添える。迷ったら AI が決める。ただし、どちらを採っても人間が決めるべき条件「要件／プロダクト方針が変わる」に当たるとき、またはどちらかを採ると人間が決めるべき条件「不可逆・外部に出る」に当たるときだけは裁定せず（[issue-policy](../../../docs/policy/issue-policy.md)「人間が決めるべき Issue の条件」。ほかの条件には広げない）、Phase 3 でその食い違い1件をラベル `needs-human-decision` で起票する。本文には、食い違った各指摘の観点名と引用を書き写す。同じワークフローの前回のレビューでこの手順により起票した Issue と同じ指摘なら、起票せず、既存の Issue 番号のまま起票済みとして扱う。同じ指摘かどうかは ai-review-gate-policy の「再レビューで同じ指摘が出たら、既存の Issue 番号で数える」で決める

### カバレッジを検証する

`docs/policy/requirements-doc-policy.md` の「レビューチェックリスト」表と「業務要件の品質検証（BABOK チェックリスト）」を Read し、**どのレンズも判定していない観点**を洗い出します。

`--stage` のときは、突き合わせる対象を、起動したレンズの担当行のうち、`requirements-reviewer-agent` の「判定対象が渡されたとき」が飛ばす・判定しないと定めた行を除いた行に限ります。

判定済みとみなすのは、**各レンズの「判定した観点」に名前が挙がっている観点だけ**です。そこに無い観点は「未判定」として、観点名をそのまま報告に載せます。**これはレビュー対象の欠陥ではなく、レンズの割り方の穴です。** 黙って埋めず（1体で後から見に行くと、分けた意味が消えます）、穴として見えるようにします。

## Phase 3: ゲート判定と起票

**ゲート判定**：合否は [ai-review-gate-policy](../../../docs/policy/ai-review-gate-policy.md) の合格条件（残してよい例外以外の Critical が0件）で決めます。`--stage` のときは、下の「対象の全指摘」を、起動したレンズの指摘と Phase 1 で出した「背景・入力元の不備」を合わせたものとします。対象の全指摘を通じた Critical の合計から、Phase 2 の「修正案が食い違ったら裁定する」で `needs-human-decision` として起票した（または既存の Issue 番号のまま扱った）食い違いに含まれる Critical 指摘の件数を引き、残りが0件なら ✅ 凍結可（`--stage` のときは ✅ 合格）、1件以上なら 🚫 要修正、と判定します。根拠を1〜2文で書き、起票・照合した Issue 番号があればそこに書きます。未判定の観点が残っている場合も、その事実を判定の根拠に併記します。

- **`--stage` のとき**：出す合否は「<記載段階>までの項目が合格か」で、凍結してよいかの判定ではありません。✅ か 🚫 の横に記載段階を書きます。
- **`--stage` が無い（凍結判定）とき**：Critical の条件に加え、台帳が無い（または判定不能の観点が残る）ときは Critical が0件でも ✅ とせず 🚫 要修正とします。台帳があれば Read し、`仕分け` が `未決` の行と `行き先` にチケット番号（書き方は Rule `requirements-doc.md` の「全項目に共通するルール」）が残る行が無いことを凍結条件にします。1行でもあれば 🚫 要修正とし、その行の ID を根拠に書きます。これらは追跡するチケットが既にあるので、新しく起票しません。

### `--stage` のとき：食い違い以外は起票せず、同じセッションで直す

`--stage` の判定は、記載段階を書いたセッションが続けて直す場面です。修正役がいるので、ai-review-gate-policy「直す範囲は毎回すべて」に従い、次の「起票」は食い違いだけに絞り（食い違い1件ごとに1 Issue）、ほかはここで直します。

1. 指摘を、重大度にかかわらずすべて直す（`Edit`）。直さずに Issue にして残してよいのは、同ポリシーの「残してよい例外」（上の `needs-human-decision` の食い違い）だけで、その食い違いだけを下の「起票」の手順で起票する
2. 残してよい例外以外の Critical があった回が上限の回より前なら、直したあと Phase 1 からやり直す。**再レビューには前回の指摘を渡さない**。Critical が0件になった回で合格とし、その回の High・Medium も直して終える
3. 上限の回（ai-review-gate-policy「レビューは最大2回まで」）の指摘も重大度を問わず直し、再レビューせずに終える
4. 入力資料や台帳が無く「判定不能」になった観点は、直せないので再レビューに回さない。判定不能が残るときは、Critical が0件でも ✅ とせず、🚫 要修正（<記載段階>）とし、判定不能の観点を根拠に書いて終える

### 起票

レビュー結果を出力したら、続けて `gh issue create` で GitHub Issue を起票してください。**ユーザーへの確認は行いません**（CLAUDE.md の broken-window ルール）。

**起票の対象は、原文の引用が付いた指摘だけです。** 引用の無い指摘は裏が取れていないので、Issue にしません。引用付きの指摘が1件も無ければ起票しません。

| 起票対象       | 粒度                | タイトル                                      | なぜ                                                                            |
| -------------- | ------------------- | --------------------------------------------- | ------------------------------------------------------------------------------- |
| Critical       | 1件ごとに1 Issue    | `[Critical] 要件定義書: <問題の概要>`         | 凍結を止める欠陥は1件ずつ着手・クローズされる。束ねると一部だけ直った状態が残る |
| High ＋ Medium | 全件まとめて1 Issue | `[High・Medium] 要件定義書レビュー指摘まとめ` | 1件ずつ判断するほど重くない。件数分に割ると Critical の Issue が埋もれる        |

タイトルの先頭ラベルは省略しないでください——Issue 一覧を眺めただけで、凍結を止める指摘かどうかが分かる必要があります。タイトルの先頭には段番号を付けてください（例：`1. [Critical] …`）。振り方は [`/quick-issue`](../quick-issue/SKILL.md) の「段番号の振り方」に従います。起票の前後は [`/link-root-issue`](../link-root-issue/SKILL.md) の SKILL.md を Read して従ってください。段番号は、起票前に「ルートを決める」段で決めたグループから数えます。

本文の書き方・起票前セルフチェックは `.claude/skills/quick-issue/SKILL.md`、ラベルは `docs/policy/issue-policy.md` が正典です。Read して従ってください。起票する Issue には `broken-window` を付けます。ラベルはポリシーの定めに加えて `requirement`（説明：要件定義書のレビュー指摘に起因するIssue）を必ず付けます——要件定義の指摘だけを後から一括で追うためです。

Issue 本文の「現状」には、レビュー結果の**引用・理由・修正案**を書き写してください（レビュー結果を読み返さずに着手できるように）。

未判定の観点は Issue にしません。対象文書の欠陥ではないので、`requirements-reviewer-agent` のレンズの割り方を直す話になります。
