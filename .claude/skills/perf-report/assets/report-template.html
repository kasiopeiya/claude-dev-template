処理した量

定義 completed で close した Issue から、PR のレビュー通知・子を持つ親・phase・週次の Issue・メモ（ラベルが無く本文が空）を除いた件数
定義元は、レビュー通知が docs/policy/pr-review-policy.md、親・phase・週次が docs/policy/issue-policy.md、メモが scripts/perf-report.mjs
close した日（日本時間）で週に分ける（月曜始まり）
全日そろった週とは、月曜から日曜までをすべて数え、今日より前に終わった週をいう
読み方 小さな Issue を流し続ける運用が、週単位で途切れていないかを見る
少ない週は、要件定義など件数に出にくい作業の時期のことがある
限界 件数は成果や価値の大きさを表さない
週ごとの件数は大きくぶれるので、1週の増減で良し悪しを判断しない
白抜きの週は日数が足りず、他の週と比べられない

AI に任せた度合い

期間内に作業 Issue が無いため、図を描きません。

定義 Issue に付いたラベルだけで機械的に分類した件数
ai-fixable は issue:decided の有無を問わない
分類なしは、3択のラベルが無いものと needs-human-decision のまま close したもの
読み方 人の手をどれだけ残しているかを見る。他のプロジェクトで人をどこに置くかの目安になる
限界 ラベルは着手前の分類で、実際の作業の記録ではない
Issue を作るまでの相談は含まない（人間と相談して方針を決めた Issue も AI 単独に入る）

着手から PR が出るまでの時間

測れた Issue が無いため、図を描きません。

定義 ai-fixable の作業 Issue で、ボードの Status が最初に In Review（PR が Issue に紐づいた時点）になった時刻と、その直前に In progress になった時刻の差
{{targetIssueCount}}件のうち{{measuredIssueCount}}件で数えた。In progress と In Review の両方の記録が無い Issue は数えない
割合は四捨五入のため、合計が100%にならないことがある
読み方 AI の作業のスピード感をつかむ目安にする
1件は小さく割った Issue で、大きな機能を作る時間ではない
8時間以上の帯は、エラーや判断待ちで止まっていた時間として読む
限界 人間が同じ作業にかかる時間との比較ではなく、何倍速いかは言えない
Issue を作るまでの相談、自動検査、レビュー、マージの時間は含まない
AI が動いていた時間そのものではなく、人間の指示を待つ時間なども入る
失敗してやり直す前の時間は含まないので、その分だけ実際より短く見える

人間レビューの対象

定義 マージした PR のうち、needs-human-review が付いた割合
付く条件は docs/policy/pr-review-policy.md のレビュー方針の表が決める
読み方 人間の確認に回る変更がどれだけ残るかを見る
他のプロジェクトで、確認に要る人の量を考える目安になる
限界 対象になった割合で、人間が読んだ割合やかかった時間ではない
この割合だけでは、レビューがボトルネックかどうかは言えない
{{humanReviewTargetCount}}件のうち{{policyOrCicdCount}}件は判断基準や自動検査の変更（policy・cicd）で、プロダクト開発では内訳が変わる
対象はルールで決まる。ルールが変わると割合も変わる

変更の小ささ

定義 期間内にマージした PR の追加行数と削除行数の合計
割合は四捨五入のため、合計が100%にならないことがある
読み方 1回の変更を小さく保てているかを見る
平均は一部の大きな変更に引っ張られるので、中央値を中心に読む
200行と300行は、このプロジェクトが決めた分割の線（docs/policy/pr-review-policy.md）
限界 小さく回せている事実を示すだけで、有効さの証明ではない
