イントロダクション

背景

このレポートは、AI 駆動開発の実績から学びを得て、次の開発プロジェクトに活かすためにまとめたものです。ハーネス（AI の開発を支える仕組み）を分析し、改善する根拠にもします。

工数削減の効果は、このレポートでは測らない

経営層が最も知りたいのは、AI で工数がどれだけ減ったかです。欧州・中東の経営層1,854人への調査でも、AI の投資対効果は、導入で最も解決しにくい課題の1つに挙がっています（Deloitte, 2025）。しかし、このレポートではこれを測れません。同じ作業を人間だけで行った場合と比べる対照実験が1プロジェクトではできず、体感も実測とずれるためです。

体感は、実測の代わりになりません。回答した開発者・技術者の8割以上が、AI で生産性が上がったと感じています（DORA, 2025）。一方で、経験のある開発者16人が246件の課題に取り組んだ研究では、AI を使うと19%遅くなったのに、本人たちは終えた後も20%速くなったと信じていました（METR, 2025）。METR はその後、この結果は古くなり、いまは AI で速くなっている可能性が高いと注記しました。ただし、新しい推定も信頼できないとしています。AI 無しで働く条件への参加を断る開発者が増え、選ばれ方の偏りで正しく測れなくなったためで、本人が申告する速さも当てにならないと改めて述べています（METR, 2026）。

工数削減を測れた研究は、課題が決まっているか、成果物の件数だけを数えるものです。GitHub Copilot の対照実験では、「JavaScript で HTTP サーバを作る」という1つの課題を全員に与え、Copilot を使った組が使わない組より55.8%速く終えました（Peng et al., 2023）。3社の開発者4,867人を対象にした実務での対照実験では、AI を使える組の完了タスク数が26%増えましたが、効果は経験の浅い開発者に偏り、コードの質は測られていません（Cui et al., 2025）。しかし実際の開発の多くは、何を作るかや、どこまでできれば完成かが作業の中で決まっていく非定型業務（オープンエンドなタスク）です。決まった課題や件数だけの結果は、そのまま当てはめられません（METR, 2025）。DORA も、AI の投資対効果は導入直後に一時的に下がる J カーブを描くとし、その計算は確度の低い見積もりだと断っています（DORA, 2026）。

代表的な指標と、このレポートの立ち位置

開発チームの成果を測る代表的な指標は、DORA のソフトウェアデリバリーの指標です。いまは、変更のリードタイム・デプロイ頻度・失敗したデプロイからの復旧時間・変更失敗率・デプロイのやり直し率の5つです（DORA Metrics Guide, 2026）。

これらが使われるのは、作業の量ではなく、本番へ届けた結果を測るからです。コードの行数やベロシティのような作業量の指標は、行数を増やしたり見積もりを大きくしたりするだけで良く見せられるので、生産性の指標にするのは危ういとされています（Forsgren et al., 2018）。

しかし、デプロイやリリースのやり方は組織のルールで決まることが多く、1チームの工夫では動かしにくい値です。また、この期間は本番へ届けるプロダクトのコードがありません。

そこでこのレポートは、チームの中で完結する Issue と PR の記録から、いまのチームの働き方を測ります。ただし、Issue の件数や PR の差分行数は、上で危ういとした作業量の指標に近いものです。指標を目標にすると、指標をよく見せること自体が目的になり、指標が役に立たなくなります。グッドハートの法則と呼ばれる現象で、DORA も指標を目標にすると数字をごまかす動きを招くと注意しています（DORA Metrics Guide, 2026）。そのため、ここで測る数字は目標値にはしません。

それでも、冒頭の「AI で工数がどれだけ減ったか」に、間接的に答える材料にはなります。人間と比べた削減率は出せませんが、AI 駆動開発でどのくらいの工数がかかるかを見積もるときの参考値にはなるからです。たとえば、人間と方針を詰める工程（要件定義など）では人間レビューの対象が多く工数削減をあまり見込めない、構築の工程では AI 単独の分類が多くスループットも高い、といった工程ごとの違いにあたりを付けられるはずです。あくまで参考値ですが、測れない問いに対してできることはやる、という立場です。そのため、ここで測る数字は、ハーネスを改善する材料と、次のプロジェクトの工数を見積もる参考値として読みます。

今回の測定項目

測るのは、どのくらいの仕事を AI に任せられ、人間の仕事がどこに残るかを示す、次の5つです。ただし数字だけでは、何が起きているかは分かっても、なぜ起きたかは分かりません（DORA, 2025）。そのため、指標ごとに、結果がなぜそうなったかの考察を添えます。

測定項目 狙い
Issue処理スループット（週あたり作業 Issue） AI 駆動開発でどのくらいの Issue を捌けるかの目安になる。件数が伸びない時期は、AI に任せにくい工程の候補として読む
AIへの委譲度 ほぼ AI 単独なら、人間の仕事は作業そのものより、Issue を作る判断やレビューに移っていると読める。AI 単独が少なければ、ハーネスがまだ洗練されていない可能性がある
Issue１つあたりのリードタイム分布 ほとんどの作業を AI が行うので、AI の作業時間に近い目安になり、タスクをどのくらいで捌けるかのあたりを付けられる。人間と比べた削減効果は測れない
人間レビュー対象の割合 人間の確認に回る量が分かる。大きな変更はレビューが難しく、AI が生成したコードは1行あたりの確認の負担が人間が書いたコードより大きくなりうるとされる（DORA, 2025）。AI でコードの量が増えると確認の負担が膨らみ、手動のレビューの門が追いつかなくなるとされ（DORA, 2026）、AI の利用が多いチームではマージした PR が98%増える一方でレビュー時間が91%増えたという報告もある（Faros AI, 2025）。人間の確認が全体を止める場所になりうるので、ボトルネックを探す入口として測る。ハーネス改善の材料にもなる
変更の小ささ 1回の変更の大きさが分かる。小さいバッチで働くことは開発と組織の成果を予測し、AI の導入がプロダクトの成果に与える良い効果を強めるとされる（DORA, 2025）。AI の導入とともにデリバリーの安定性が推定7.2%下がり、小さいバッチなどの基本を守ることが要るとされた（DORA, 2024）。件数と時間は、この大きさを前提に読む
