# パフォーマンスレポート

読み手は経営寄りの人で、このやり方を他のプロジェクトへ広げるかを判断する。ハーネスを改善する人も読む。

## 手順

HTML を手で書かない。文章の指示で書かせると、合意した見た目からずれるためである。AI が書くのは考察の文だけで、ひな形への埋め込みはスクリプトが行う。

### 1. 集計結果を保存する

先に日時を取り出す。出た値を、この後の `<日時>` にそのまま書く。

```bash
date +%Y%m%d-%H%M%S
```

```bash
mkdir -p tmp/perf-report
npm run --silent perf-report -- $ARGUMENTS > tmp/perf-report/<日時>-perf-report-aggregate.json
```

考察ファイルの名前は、保存した名前から1対1で決まる（手順2）。前に打った分の考察ファイルが、別の集計結果に使われないためである。

- **失敗したら**：エラーをそのまま伝えて終える。件数を手で数えて補わない（打つたびに数字がぶれるため）

### 2. 考察ファイルを書く

手順1で保存した集計結果を読み、同じフォルダに、名前の末尾 `-aggregate.json` を `-discussion.json` に替えた考察ファイルを書く。5指標のキーは `throughput`（Issue処理スループット）・`delegation`（AIへの委譲度）・`speed`（Issue１つあたりのリードタイム分布）・`review`（人間レビュー対象の割合）・`size`（変更の小ささ）で、どれも抜かさない。

```json
{
  "throughput": ["なぜその結果になったかの推測を書き、〜と考えられる"]
}
```

指標ごとに「考察」の文を配列で書き、1文を1要素にする。HTML では1文が箇条書きの1行になり、考察の後にひな形の固定の文（「読むときの注意」）が続く。

集計結果には、件数のほかに作業 Issue とマージした PR の1件ごとの記録（`workIssueRecords`・`mergedPullRequestRecords`）がある。着手から PR までの分は、AI 単独で測れた Issue にだけ付く。

### 3. HTML を作る

```bash
npm run --silent perf-report-html -- tmp/perf-report/<日時>-perf-report-aggregate.json
```

HTML を書き、その絶対パスを返す。

- **失敗したら**：考察ファイルが無い・崩れている・指標のどれかが抜けている・「考察」の文が「と考えられる」で終わらない・集計結果のタイトルをそのまま含む・出典の形が崩れている・考察で引いてよい参考文献に無い出典があるときは、エラーに原因が並ぶ。考察ファイルを直して、この段だけを打ち直す。手順1は打ち直さない。期間の終わりの既定が今日なので件数がずれ、考察と図の数が食い違うためである。考察ファイル以外の原因なら、エラーをそのまま伝えて終える
- **置き場**：`tmp/perf-report/{yyyymmdd}-perf-report-{from}-{to}.html`。同じ日に同じ期間で打つと、HTML は上書きされる

### 4. 描画を確かめる

`.claude/skills/html/references/pr.md` の「描画を確かめて直す」の手順を、HTML を置いたフォルダで行う。ただし、崩れを見つけても HTML を直さない。直しても、打ち直すと消えるためである。

### 5. 出力先を伝える

HTML の絶対パスを伝える。手順4で崩れを見つけたら、その箇所も添える。

## 考察の書き方

読み手が図から得られないもの、つまり結果がなぜそうなったかを書く。

- **推測の文は「〜と考えられる」で終える**：どの文が推測かを、読み手が文ごとに見分けられるようにするためである。スクリプトが「考察」の文末を検査し、合わなければ止まる
- **図を見れば分かることの言い換えは書かない**：「件数が増えた」は図で分かる
- **図から読めない事実が理由の説明に要るときは、考察の文の中に書く**（例：「…なので、…と考えられる」）：事実だけの文を別に置かない。図の下に AI が書く節を「考察」1つに保ち、「読むときの注意」をひな形の固定の文だけにしておくためである
- **理由は1件ごとの記録のタイトルから、その期間の作業の傾向を読み取って書く**（例：「設計書の整備が続いた週は…と考えられる」）：帯ごとの件数だけでは、どの作業がその値になったかが分からないためである
- **タイトルはそのまま引用せず、何の作業かを言葉で言い換える**：タイトルにはパスやラベル名が入り、下の「載せないもの」に反するためである。スクリプトがタイトルをそのまま含む文を検査し、あれば止まる
- **研究と比べるときは、ひな形の参考文献の項目の中のコメントに「考察で引いてよい結果」として書かれた結果だけを書き、出典を「（DORA, 2024）」の形で「と考えられる」より前に置く**（例：「小さいバッチは AI の良い効果を強めるという報告（DORA, 2025）と同じく、作業を小さく割ったことが効いたと考えられる」）。1文に出典が2つあるときは、かっこを分けて並べる（「（DORA, 2024）（DORA, 2025）」）
  - 理由：記憶から研究の結果を書くと、出典に無いことを書きうるためである
  - 文末は「と考えられる」のまま：研究が正しいかではなく、このデータがなぜそうなったかの推測だからである
- **件数はスクリプトが数えた値だけを使い、数え直さない。1件ごとの記録も数え直さない**：考察の数と図の数が食い違わないようにするためである
- **値が無い指標には、「考察」に `期間内に値が無いので考察しない` の1文だけを書く**：どの指標にも考察がある、という形を保つためである。値が無いのは事実なので「と考えられる」で終えない。スクリプトは、値が無い指標（期間内に作業 Issue・測れた Issue・マージした PR が無い）に限って、この1文を文末の検査から外す。言い換えると止まる
- **長さの上限は設けない**：理由を書き切ることを優先する

## 載せないもの

工数削減・時間短縮・体感値は、考察にも、出力先を伝える返事にも書き足さない。1プロジェクトでは対照実験ができず、体感は実測とずれるためである。

リポジトリの中のファイルやフォルダの名前（ポリシー文書・スクリプトのパスなど）と、Issue・PR のラベル名や番号、ボードの列名は、ひな形にも図にも考察にも載せない。意味を言葉で書く。レポートは開発メンバー以外にも配り、その人たちはリポジトリを開けず、ラベル名を見ても意味が分からないためである。
