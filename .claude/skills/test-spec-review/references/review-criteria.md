# テストの要件準拠レビュー観点

テストが要件定義書の規則を確かめているかをレビューする AI・人間が、どの観点を見て、何を違反とするか迷ったときに引く観点一覧。

観点ごとに **準拠／違反／対象外** を判定し、違反は「severity の決め方」に従って severity 付きの指摘にする。点数は付けない。観点は**観点名で識別する**（他ドキュメントからも観点名で参照する）。

## 言葉の定義

- **規則**：要件定義書に書かれた、システムが守るべき決まり1つ
- **制約の規則**：値や操作に「何を受け付け、何を拒むか」を定める規則（例：会員番号は10桁固定・半角数字のみ／同じ要求の2回目は受け付けない）
- **条件**：制約の規則の記述が書き出している、受け付けるために満たすべきこと1つ。上の会員番号の例なら「10桁」と「半角数字のみ」の2条件
- **条件を破る入力のテスト**：その条件だけを破る入力を渡し、拒まれること（エラー・`false`・拒否の結果など）を assert するテスト。入力を渡すだけで、拒まれることを assert しないテストは数えない
  - 数えない例：会員番号に `'abc'` を渡して拒むテストは、「10桁」と「半角数字のみ」の両方を破るので、どちらの条件のテストにも数えない
  - 数えない例：9桁の会員番号を渡して戻り値を受け取るだけで、拒まれることを assert しないテスト
- **計算・定義の規則**：値の求め方や決まった値を定める規則。拒む入力が無いので、破る入力のテストは考えられない（例：付与ポイントは購入額の1%）
- **具体値**：計算・定義の規則の記述に書かれた値・式・例（上の例なら「1%」）
- **具体値どおりの期待値のテスト**：入力を渡し、具体値から求まる値を assert するテスト（上の例なら、1,000円を渡して10ポイントを assert する）
  - 数えない例：期待値を実装の定数から計算する（`toBe(1000 * POINT_RATE)`）。実装の定数が要件と違っても通る

## 判定方針

違反・準拠・対象外・解釈が分かれるときの扱いは、[共通規約](../../../rule-bodies/review-agent-common.md)「判定の定義」に従う。この観点一覧で足すのは次のとおり。

- **条件は、規則の記述に書かれたものだけを数える。** 一般の知識（RFC など）から条件を補わない。規則が「メールアドレス形式」としか書いていなければ、条件は「メールアドレス形式である」の1つで、形式でない入力を1つ拒むテストがあれば満たす。補うと、正しい実装まで違反にする
- **具体値も、規則の記述に書かれたものだけを使う。** 記述から期待値が1つに決まる入力だけを判定する。規則が端数の扱いを書いていなければ、1,050円を10ポイントとするテストも11ポイントとするテストも、食い違いとしない
- **制約か計算・定義かは、規則の記述が何を定めているかで見分ける**（「言葉の定義」のとおり）。要件定義書の書式（ID の付け方・表の列の名前など）では見分けない。1つの規則が両方を定めていれば、制約の部分は「条件を破る入力のテスト」で、計算・定義の部分は「具体値どおりの期待値のテスト」で照らす
- **規則が曖昧なことは指摘しない。** 要件定義書の質は `/requirements-review` が見る
- **テストの書き方（AAA・命名など）は見ない。** `/code-review` のテストレンズが見る
- **対象外**：観点ごとに決める。「条件を破る入力のテスト」は、照らす規則（範囲が決める。差分が触れる規則・名指しした機能の規則・全部の規則）のうち制約の規則が、「具体値どおりの期待値のテスト」は、照らす規則のうち計算・定義の規則が、1つも無いとき

## 観点一覧

| 観点                             | チェック内容                                                                     | 違反と判定する条件                                                                                                                                |
| -------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **条件を破る入力のテスト**       | 照らす制約の規則の条件ごとに、その条件を破る入力のテストがあるか                 | 条件のどれか1つについて、渡されたテストファイルのどこにも、破る入力のテストが無い                                                                 |
| **具体値どおりの期待値のテスト** | 照らす計算・定義の規則ごとに、具体値から求まる期待値を assert するテストがあるか | 規則のどれか1つについて、渡されたテストファイルのどこにも具体値どおりの期待値のテストが無い。または、期待値が具体値から求まる値と違うテストがある |

### Critical の例

- 規則「付与ポイントは購入額の1%」を照らすとき、1,000円を渡して20ポイントを assert するテストがある

### High の例

- 規則「会員番号は10桁固定・半角数字のみ」を照らすとき、テストに9桁や11桁の入力を拒むテストが無い（「半角数字のみ」を破る入力のテストはある）
- 規則「同じ要求を2回目以降に受けたら受け付けない」を照らすとき、同じ要求を2回送るテストが無い
- 規則「付与ポイントは購入額の1%」を照らすとき、ポイントの計算のテストが無い

## severity の決め方

重大度（Critical / High / Medium）の定義は [ai-review-gate-policy](../../../../docs/policy/ai-review-gate-policy.md) が正典。

**条件を破る入力のテストと、具体値どおりの期待値のテストの欠けは High にする。** いまの実装が要件を守っていても、テストが無ければ、変更で要件が破れたときに CI を通る。いま要件に反しているかは、このレビューでは確かめない（テストの欠けだけを見る）ので、Critical にはしない。

**ただし、期待値が具体値から求まる値と違うテストがあるときは Critical にする。** そのテストが通るなら実装が要件に反しており、通らないなら CI が止まる。どちらでも、テストが要件を確かめる役目を果たせない。
