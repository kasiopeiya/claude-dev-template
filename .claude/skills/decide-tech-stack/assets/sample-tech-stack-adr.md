# ADR-001: 会員ポイント管理システムの初期技術スタックを決める

> [!NOTE]
> 本書は `/decide-tech-stack` が出力する初期技術スタックADRの**記述サンプル**である。題材は架空で、要件は同じ題材の [sample-requirements.md](../../elicit-requirements/sample-requirements.md) を出所としている。
> 目的は「各欄に何を、どの粒度で書くか」の具体像を与えること。
> **記入ルールの正典は [tech-stack-adr-template.md](tech-stack-adr-template.md) であり、本書はそれを再掲しない。**

> [!IMPORTANT]
> **TL;DR（この決定の要点）**
>
> - 国内リージョン必須と社内標準から AWS / TypeScript / GitHub Actions を据え、伸縮性が要るコンピュートに Lambda、IaC に CDK、環境は dev/stg/prd の3アカウントとした
> - Web フレームワーク・DB 製品・EC/POS 連携方式は決めず、最初の曳光弾で確かめる

## 前提

| No  | 要件・制約                                                          | 出所                                                 | 何を縛るか                         |
| --- | ------------------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------- |
| P1  | 会員個人情報・残高は国内リージョンに保持する（真の制約）            | sample-requirements.md「制約と前提」                 | クラウドプロバイダ・リージョン     |
| P2  | 失効処理は毎朝5:00までに完了。セール時は平常の5倍が年数回・数日続く | sample-requirements.md「非機能要件 B. 性能・拡張性」 | コンピュート（伸縮性）             |
| P3  | 言語・クラウド・ソース管理は社内標準（TypeScript / AWS / GitHub）   | 情報システム部 技術標準 v3                           | 言語 / ランタイム・クラウド・CI/CD |
| P4  | 本番切替前にリハーサルを1回以上行い、異常時は旧運用へ切り戻せる     | sample-requirements.md「非機能要件 D. 移行性」       | 環境構成                           |
| P5  | 運用担当は平日9–18時。夜間はオンコールの一次対応のみ                | sample-requirements.md「非機能要件 C. 運用・保守性」 | コンピュート（運用負荷）           |
| P6  | ディレクトリ構成は全社の構成ガイドに従う                            | `docs/guide/directory-structure-guide.md`            | ディレクトリ構成方針               |

## 決定した技術スタック

| No  | 項目                    | 選定                                      | 区分 | 理由                                                                                                   |
| --- | ----------------------- | ----------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------ |
| 1   | 言語 / ランタイム       | TypeScript / Node.js 22                   | 制約 | P3：社内標準が TypeScript。EC 連携の既存ライブラリも TypeScript 製                                     |
| 2   | パッケージマネージャ    | npm                                       | -    | Node.js に同梱でCIに追加設定が要らない。pnpm・yarn とは比較していない                                  |
| 3   | クラウドプロバイダ      | AWS                                       | 制約 | P1（国内リージョン必須）と P3（社内標準）で選択の余地がなかった                                        |
| 4   | コンピュート            | AWS Lambda                                | 選択 | 平常とセール5倍の差を、増減の運用なしで吸収できる。コストの読みやすさを捨てた（[詳細](#コンピュート)） |
| 5   | IaC ツール              | AWS CDK                                   | 選択 | アプリと同じ TypeScript で書け、構成ミスを型で落とせる。移植性を捨てた（[詳細](#iac-ツール)）          |
| 6   | 環境構成                | dev / stg / prd の3環境（アカウント分離） | 選択 | P4 のリハーサルを本番同等の環境で回すため。アカウント3つ分の運用を引き受けた（[詳細](#環境構成)）      |
| 7   | CI/CD プラットフォーム  | GitHub Actions                            | 制約 | P3：ソース管理が GitHub で、他 CI の持ち込みは社内承認が要る                                           |
| 8   | 静的解析 / フォーマッタ | ESLint + Prettier                         | -    | TypeScript での既定の組み合わせに従った。Biome とは比較していない                                      |
| 9   | テストランナー          | Vitest                                    | -    | 設定が少なく起動が速い。Jest とは比較していない                                                        |
| 10  | リポジトリ構成          | monorepo（npm workspaces）                | -    | EC/POS 連携アダプタとバッチが同じ型定義を共有するため。polyrepo とは比較していない                     |
| 11  | ディレクトリ構成方針    | package by feature                        | 制約 | P6：構成ガイドが package by feature を定めている                                                       |

## 各項目の詳細

### コンピュート

| 案                   | 概要                                     | 利点                                                                | 代償・欠点                                                                                     | 採否 |
| -------------------- | ---------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---- |
| AWS Lambda           | リクエスト単位で起動する関数として動かす | 平常時とセール5倍の差を、台数の増減を運用せずに吸収できる（P2・P5） | 実行時間の上限があり、失効処理の長時間バッチは分割が要る。コストが実行回数に比例して読みにくい | 採用 |
| Amazon ECS (Fargate) | コンテナを常時起動し、台数で伸縮させる   | 実行時間の制限がなく、失効処理をひとつのプロセスで書ける            | 伸縮の設定と平常時の余剰台数を運用で持つ必要があり、夜間オンコール体制（P5）と噛み合わない     | 却下 |
| Amazon EC2           | 仮想マシンを自前で構成して動かす         | ミドルウェアを自由に選べ、既存の運用手順を流用できる                | OS のパッチ適用・EOL 管理が運用に丸ごと乗る（非機能要件 C. の更新方針を満たしにくい）          | 却下 |

**決め手**：セール時5倍の変動（P2）を運用の手数なしで吸収することを最優先し、コストの読みやすさを捨てた。バッチの実行時間上限は、失効処理を会員ID範囲で分割することで回避する。

### IaC ツール

| 案                            | 概要                                                               | 利点                                                                                 | 代償・欠点                                                                                                | 採否 |
| ----------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- | ---- |
| AWS CDK                       | TypeScript でリソースを書き、CloudFormation テンプレートに合成する | アプリと同じ言語・型定義を共有でき、構成ミスをコンパイル時に落とせる。記述量も少ない | CloudFormation の制約（デプロイ単位・リソース上限）をそのまま被る。合成結果を読めないと障害時に追いにくい | 採用 |
| Terraform                     | HCL で書き、独自の state ファイルで差分を管理する                  | AWS 以外にも同じ書き方が使える。適用前の差分（plan）が読みやすい                     | state の保管とロックを自前で運用する必要がある。言語が別になり、アプリと型定義を共有できない              | 却下 |
| CloudFormation（YAML 直書き） | AWS 純正のテンプレートをそのまま書く                               | 追加ツールが要らず、CI に何も入れなくてよい                                          | 条件分岐・繰り返しが書きにくく、環境差分の共通化手段が乏しい。記述量が3案で最も多い                       | 却下 |

**決め手**：アプリと同じ TypeScript で書けることを最優先し、マルチクラウドへの移植性を捨てた。P3 で AWS に固定されている以上、移植性の価値が小さいと判断した。

### 環境構成

| 案                                | 概要                                    | 利点                                                                          | 代償・欠点                                                                 | 採否 |
| --------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ---- |
| dev / stg / prd（アカウント分離） | 3環境を別々の AWS アカウントに置く      | 本番同等の stg で切替リハーサル（P4）を回せる。権限とコストが環境ごとに切れる | アカウント3つ分の初期設定と運用が増える。IaC のパラメータ管理も3系統になる | 採用 |
| dev / prd の2環境                 | 開発用と本番用だけを持つ                | 環境が少なく、初期構築と運用が最も軽い                                        | 本番同等の場が無く、切替リハーサル（P4）を本番で行うことになる             | 却下 |
| 単一アカウント内で環境を分離      | 1アカウントの中を命名規則とタグで分ける | アカウント管理が1つで済む                                                     | 権限の分離が弱く、本番リソースを開発作業で壊す事故を構造的に防げない       | 却下 |

**決め手**：切替を1回で成功させる要求（P4）を満たすため本番同等の stg を確保し、アカウント3つ分の運用コストを引き受けた。

## 受け入れるリスク・制約

| 受け入れる制約・リスク                           | 影響範囲                                         | 緩和策                                                                        |
| ------------------------------------------------ | ------------------------------------------------ | ----------------------------------------------------------------------------- |
| AWS に固定され、他クラウドへ移せない             | クラウド固有サービスを使うすべてのコード         | ビジネスロジックからは AWS SDK を直接呼ばず、境界のインターフェース越しに使う |
| Lambda の実行時間上限が失効処理の作り方を縛る    | 日次失効バッチ                                   | 会員ID範囲で分割し、1実行あたりの処理量を上限内に収める                       |
| 環境が3つあり、IaC のパラメータ管理が3系統になる | インフラ定義・CI/CD のデプロイジョブ             | 環境差分は1ファイルに集約し、環境ごとのコードの分岐を作らない                 |
| 比較せずに決めた選定がある（No.2・8・9・10）     | 後から乗り換えるとCI設定と全ファイルに影響しうる | 不都合が出た時点で比較し直す。今は乗り換える理由が無いことだけを確認した      |

## 意図的に保留したもの

| 保留項目                              | いま決めない理由                                                              | いつ決めるか                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Web / API フレームワーク              | 曳光弾ではハンドラを直接書けば足り、今決めるとドメインが特定FWに従属する      | 残高照会APIの縦スライスを作るとき                            |
| DB 製品・スキーマ                     | 取引の一貫性要求（RPO 1時間）を満たす形が、失効処理の実装を書くまで確定しない | 付与・利用の縦スライスで、実際の書き込みパターンが見えた時点 |
| EC / POS との連携方式（同期・非同期） | 連携先の応答時間の実測が無く、今決めると誤った前提を固定する                  | EC 連携の疎通試験でレイテンシを実測した後                    |
| 監視・アラートの製品                  | 監視対象は上のスライスが決まらないと確定しない                                | 最初の曳光弾が本番相当環境で動いた時点                       |
