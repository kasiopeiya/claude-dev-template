# ADR-001: 会員ポイント管理システムの初期技術スタックを決める

> [!NOTE]
> 本書は `/decide-tech-stack` が出力する初期技術スタックADRの**記述サンプル**である。題材は架空で、要件は同じ題材の [sample-requirements.md](../../elicit-requirements/sample-requirements.md) を出所としている。  
> 目的は「各欄に何を、どの粒度で書くか」の具体像を与えること。  
> **記入ルールの正典は [tech-stack-adr-template.md](tech-stack-adr-template.md) であり、本書はそれを再掲しない。**

> [!IMPORTANT]
> **TL;DR（この決定の要点）**
>
> - 国内リージョン必須と社内標準から AWS / TypeScript / GitHub Actions を据え、伸縮性が要るアプリケーション実行基盤に Lambda、IaC に CDK、環境は払い出せる dev / prd の2アカウントとした
> - Web フレームワーク・DB 製品・EC/POS 連携方式は決めず、最初の曳光弾で確かめる

## 決定した技術スタック

| No  | 項目                     | 選定                                 | 区分 | 理由                                                                                                                                                                                                                                  |
| --- | ------------------------ | ------------------------------------ | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 言語 / ランタイム        | TypeScript / Node.js 24              | 制約 | P3：社内標準が TypeScript。CDKの言語は実質的にTypeScript一択。アプリも同じ言語を使うことで、最小人数での運用ができるようにした。                                                                                                      |
| 2   | パッケージマネージャ     | npm                                  | 制約 | P6：開発テンプレートがnpm採用。pnpm・yarn とは比較していない                                                                                                                                                                          |
| 3   | クラウドプロバイダ       | AWS                                  | 制約 | P1・P3：AWS以外は組織制約により使用不可。                                                                                                                                                                                             |
| 4   | アプリケーション実行基盤 | AWS Lambda                           | 選択 | 平常とセール5倍の差を、増減の運用なしで吸収できる。コストの読みやすさを捨てた（[詳細](#アプリケーション実行基盤)）                                                                                                                    |
| 5   | IaC ツール               | AWS CDK                              | 選択 | アプリと同じ TypeScript で書け、構成ミスを型で落とせる（[詳細](#iac-ツール)）                                                                                                                                                         |
| 6   | 環境構成                 | dev / prd の２環境（アカウント分離） | 選択 | P7：組織の制約により２環境しか払い出しできない。その枠内で権限分離を優先した（[詳細](#環境構成)）                                                                                                                                     |
| 7   | CI/CD プラットフォーム   | GitHub Actions                       | 制約 | P3：ソース管理が GitHubが標準、GitHubと最も簡単に連携・実装できるGitHub Actionsを選択。開発テンプレートでも使用                                                                                                                       |
| 8   | 静的解析 / フォーマッタ  | ESLint + Prettier                    | 制約 | P6：開発テンプレートで使用。Biome とは比較していない                                                                                                                                                                                  |
| 9   | テストランナー           | Vitest                               | 制約 | P6：開発テンプレートで使用。設定が少なく起動が速い。Jest とは比較していない                                                                                                                                                           |
| 10  | リポジトリ構成           | monorepo（npm workspaces）           | 選択 | コーディングエージェントのSkillやPolicyのメンテナンス性の問題からモノレポ構成を採用。AIが横断的に検索・編集できる点もモノレポを選択する動機になる。EC/POS 連携アダプタとバッチが同じ型定義を共有するため。（[詳細](#リポジトリ構成)） |

## 各項目の詳細

### アプリケーション実行基盤

**決め手**：セール時5倍の変動（P2）を運用の手数なしで吸収することを最優先し、コストの読みやすさを捨てた。バッチの実行時間上限は、失効処理を会員ID範囲で分割することで回避する。

| 案                   | 概要                                     | 利点                                                                | 代償・欠点                                                                                     | 採否 |
| -------------------- | ---------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---- |
| AWS Lambda           | リクエスト単位で起動する関数として動かす | 平常時とセール5倍の差を、台数の増減を運用せずに吸収できる（P2・P5） | 実行時間の上限があり、失効処理の長時間バッチは分割が要る。コストが実行回数に比例して読みにくい | 採用 |
| Amazon ECS (Fargate) | コンテナを常時起動し、台数で伸縮させる   | 実行時間の制限がなく、失効処理をひとつのプロセスで書ける            | 伸縮の設定と平常時の余剰台数を運用で持つ必要があり、夜間オンコール体制（P5）と噛み合わない     | 却下 |
| Amazon EC2           | 仮想マシンを自前で構成して動かす         | ミドルウェアを自由に選べ、既存の運用手順を流用できる                | OS のパッチ適用・EOL 管理が運用に丸ごと乗る（非機能要件 C. の更新方針を満たしにくい）          | 却下 |

### IaC ツール

**決め手**：アプリと同じ TypeScript で書けることを最優先し、マルチクラウドへの移植性を捨てた。P3 で AWS に固定されている以上、移植性の価値が小さいと判断した。

| 案                            | 概要                                                               | 利点                                                                                 | 代償・欠点                                                                                                | 採否 |
| ----------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- | ---- |
| AWS CDK                       | TypeScript でリソースを書き、CloudFormation テンプレートに合成する | アプリと同じ言語・型定義を共有でき、構成ミスをコンパイル時に落とせる。記述量も少ない | CloudFormation の制約（デプロイ単位・リソース上限）をそのまま被る。合成結果を読めないと障害時に追いにくい | 採用 |
| Terraform                     | HCL で書き、独自の state ファイルで差分を管理する                  | AWS 以外にも同じ書き方が使える。適用前の差分（plan）が読みやすい                     | state の保管とロックを自前で運用する必要がある。言語が別になり、アプリと型定義を共有できない              | 却下 |
| CloudFormation（YAML 直書き） | AWS 純正のテンプレートをそのまま書く                               | 追加ツールが要らず、CI に何も入れなくてよい                                          | 条件分岐・繰り返しが書きにくく、環境差分の共通化手段が乏しい。記述量が3案で最も多い                       | 却下 |

### 環境構成

**決め手**：アカウント2つという枠（P7）の中で、本番を壊さない権限分離を最優先し、本番同等のリハーサル環境を諦めた。P4 のリハーサルは dev で代用し、埋まらない差分は「受け入れるリスク・制約」に記録する。

| 案                                  | 概要                                              | 利点                                                      | 代償・欠点                                                           | 採否 |
| ----------------------------------- | ------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------- | ---- |
| dev / prd の2環境（アカウント分離） | 払い出せる2アカウントを開発用・本番用に割り当てる | 権限とコストが環境ごとに切れる。P7 の払い出し上限に収まる | 本番同等の場が無く、切替リハーサル（P4）は dev で代用することになる  | 採用 |
| dev / stg / prd の3環境             | 本番同等の stg を別アカウントで持つ               | 切替リハーサル（P4）を本番同等の環境で回せる              | P7 でアカウントが2つまでのため、そもそも用意できない                 | 却下 |
| 単一アカウント内で環境を分離        | 1アカウントの中を命名規則とタグで分ける           | アカウント管理が1つで済み、払い出し枠を1つ余らせられる    | 権限の分離が弱く、本番リソースを開発作業で壊す事故を構造的に防げない | 却下 |

### リポジトリ構成

**決め手**：Skill・Policy の保守性と、AI が横断して読めることを最優先し、CI の変更検知を自前で組む手間を引き受けた。

| 案                         | 概要                                                  | 利点                                                                                       | 代償・欠点                                                                                                                          | 採否 |
| -------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ---- |
| monorepo（npm workspaces） | アプリ・インフラ・エージェント定義を1リポジトリに置く | Skill・Policy を1箇所で保守でき、AI が横断的に検索・編集できる。型定義もそのまま共有できる | リポジトリが大きくなり、CI の変更検知を自前で組む必要がある                                                                         | 採用 |
| polyrepo                   | アプリとインフラを別リポジトリに分ける                | リポジトリごとに CI が軽く、権限も分けやすい コミット履歴が分離できる                      | Skill・Policy がリポジトリごとに散る。型定義の共有にパッケージ公開が要る Lambdaの環境変数などインフラからアプリへの連携実装が困難。 | 却下 |

## 受け入れるリスク・制約

| 受け入れる制約・リスク                                                 | 影響範囲                                         | 緩和策                                                                        |
| ---------------------------------------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------- |
| AWS に固定され、他クラウドへ移せない                                   | クラウド固有サービスを使うすべてのコード         | ビジネスロジックからは AWS SDK を直接呼ばず、境界のインターフェース越しに使う |
| Lambda の実行時間上限が失効処理の作り方を縛る                          | 日次失効バッチ                                   | 会員ID範囲で分割し、1実行あたりの処理量を上限内に収める                       |
| 本番同等の環境が無く、切替リハーサル（P4）を dev で代用する            | 本番切替の手順・移行の受入基準                   | dev のデータ量を本番相当に寄せて回す。埋まらない差分は切戻し手順で補う        |
| 開発テンプレートに従っただけで、選定自体は検証していない（No.2・8・9） | 後から乗り換えるとCI設定と全ファイルに影響しうる | 不都合が出た時点で比較し直す。今は乗り換える理由が無いことだけを確認した      |

## 意図的に保留したもの

| 保留項目                              | いま決めない理由                                                              | いつ決めるか                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Web / API フレームワーク              | 曳光弾ではハンドラを直接書けば足り、今決めるとドメインが特定FWに従属する      | 残高照会APIの縦スライスを作るとき                            |
| DB 製品・スキーマ                     | 取引の一貫性要求（RPO 1時間）を満たす形が、失効処理の実装を書くまで確定しない | 付与・利用の縦スライスで、実際の書き込みパターンが見えた時点 |
| EC / POS との連携方式（同期・非同期） | 連携先の応答時間の実測が無く、今決めると誤った前提を固定する                  | EC 連携の疎通試験でレイテンシを実測した後                    |
| 監視・アラートの製品                  | 監視対象は上のスライスが決まらないと確定しない                                | 最初の曳光弾が本番相当環境で動いた時点                       |
