# Issue 監査の観点

`issue-auditor-agent` が Issue 1件を監査するときに、どの観点を見て、何に当たったら既定の GO から外すかを引く観点一覧。判定基準はここが正典であり、どのレンズがどの観点を担当するかは [`issue-auditor-agent`](../../../agents/issue-auditor-agent/issue-auditor-agent.md) の「レンズ一覧と担当観点」が決める。

観点ごとに **該当／非該当／判定不能** のどれかを付ける。点数は付けない。

- **該当**：原文またはコマンド出力を引用して、下の「該当と判定する条件」に当たると示せる
- **非該当**：当たらない。引用が取れず違和感どまりのものもここに入れ、「未確認」と書く
- **判定不能**：現物を確認できず、該当とも非該当とも言えない（対象箇所が本文に書かれていない・パスが曖昧で開けない、など）

**該当が1つも無く、判定不能も無ければ GO である。** 判定不能が1つでもあれば、その観点の判定は人間判断になる。

下の観点は**観点名で識別する**（他の文書からも観点名で参照する）。番号を振ると、観点の増減で番号がずれ、参照側が無言で壊れるためである。

## 観点一覧

| 観点                             | チェック内容                                                                                                                              | 該当と判定する条件                                                                                                                                          | 該当したときの判定 |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| **対象箇所の実在**               | 本文「現状」の対象箇所に挙がったパス・シンボルが、いまもあるか                                                                            | Read・Grep で開いた結果、対象箇所が存在しない                                                                                                               | 不要               |
| **完了条件の充足**               | 本文「完了条件」が、もう満たされていないか                                                                                                | 完了条件にある読むだけのコマンドを実行した結果、または対象箇所の原文から、完了条件が既に満たされていると示せる                                              | 不要               |
| **重複**                         | 同じ課題を扱う open の Issue が他に無いか                                                                                                 | `gh issue list --search` で、同じ対象箇所の同じ課題を扱う Issue が見つかる                                                                                  | 不要               |
| **困りごとの再現性**             | 本文「この変更が必要な理由」1行目の困りごとが、いまも起きるか                                                                             | 2行目「実際に起きたこと」を再現手順として、読むだけのコマンドまたは対象箇所の原文で確かめた結果、1行目の困りごとが起きないと引用つきで示せる                | 不要               |
| **既に別の仕組みで守られている** | 本文「この変更が必要な理由」の2行目に挙げた課題を、既存の CI ゲート・hook・lint が既に止めていないか                                      | 次の2つの引用がそろう——①その課題を止めている CI ゲート・hook・lint の定義、②その検査パターン・対象範囲が2行目の具体的なファイル・文言に当たることを示す引用 | 不要               |
| **方針のポリシー準拠**           | 本文「対応方針」が、該当するポリシーの条文に反していないか                                                                                | 方針がポリシーの条文に反し、かつ正しい方針をポリシーの条文を引用して一意に引ける                                                                            | 方針差し替え       |
| **方針の前提と現物の一致**       | 本文が「こうなっている」と書いた記述が、対象箇所の現物と合っているか                                                                      | 本文の記述と現物が食い違い、かつ現物に合わせた方針を一意に書ける                                                                                            | 方針差し替え       |
| **新設を含む方針の縮小**         | 方針が新しいファイル・コマンド・ジョブ・依存を作るとき、もっと小さい仕組みで同じ効果を出せないか                                          | 下の「新設を含む方針の縮小」の問いに、より小さい案を1つ挙げられる                                                                                           | 方針差し替え       |
| **ラベルの当否**                 | `ai-fixable`／`issue:needs-human-decision` のどちらが付いているかが、`/quick-issue`「どちらを付けるか」の名指し例外への当否と合っているか | 名指し例外への当否と、付いているラベルが食い違う。ただし `issue:decided` 付きの Issue は、名指し例外を理由に差し戻さない                                    | ラベル訂正         |

**判定不能の観点があるときは人間判断**を返す。これが判定を保留する唯一の出口である。引用が取れないだけの違和感は判定不能ではない——非該当にして「未確認」と書く。読み切れていないのはこちら側かもしれないからである。

## 判定の優先順位

判定が複数に分かれたときは、次の順で上にあるもの1つにする。レンズの中で絞るときも、`/issue-check` が2つのレンズの結果を統合するときも、同じ順を使う。

**不要 ＞ 人間判断 ＞ 方針差し替え ＞ ラベル訂正 ＞ GO**

- **不要が最上位**：close する Issue の方針を直しても意味がない
- **人間判断が書き換えより上**：決め切れない観点が残っているうちは、AI が本文やラベルを書き換えない
- **方針差し替えがラベル訂正より上**：方針を差し替えるときは、ラベルの変更も「提案ラベル」で一緒に伝えられる

## 該当と非該当の線引き

判定が割れやすい観点には、当たる例と当たらない例を1つずつ挙げる。

| 観点                         | 該当する例                                                                                  | 非該当の例                                                                               |
| ---------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 重複                         | 2件が同じファイルの同じ規定を直そうとしている                                               | 同じファイルの別の節を直す2件。直す対象が違えば片方を閉じると作業が落ちる                |
| 困りごとの再現性             | 対象箇所の原文を読むと、1行目の困りごとに当たる状態が既に無い                               | 2行目に書かれた個別の事例だけが直っていて、1行目の困りごと自体は原文を読むと今も成り立つ |
| 既に別の仕組みで守られている | CI ワークフロー・hook の検査パターンが、2行目のファイル・文言をそのまま対象範囲に含んでいる | ゲートは存在するが、対象パス・パターンが2行目の事例とは別物で、実際には拾わない          |
| 方針のポリシー準拠           | ポリシーが禁じている置き場所へ書くと方針に書いてある                                        | ポリシーに条文が無く、書き方の好みが分かれるだけ                                         |
| 方針の前提と現物の一致       | 方針が前提にしている関数・節が、いまは別の名前・別の場所にある                              | 本文が触れていない箇所が変わっているだけで、方針の前提は今も成り立つ                     |

## 困りごとの再現性の当て方

- **読むだけのコマンドや原文で再現できない困りごと**（AI の振る舞い・レビューの見逃しなど、外から機械的に確かめられないもの）には当てない。非該当のまま GO とする
- **本文に `/quick-issue` テンプレートの「この変更が必要な理由」が無い Issue には当てない**
- **Issue の出どころで区別しない。** `issue:decided` 付きの Issue にも、`/to-issues` 由来の Issue にも同じように当てる

## 既に別の仕組みで守られているの当て方

- **ゲートの定義だけでは当てない。** 2行目の事例をそのゲートが実際に止めることまで、検査パターン・対象範囲の引用で示す
- **本文に「この変更が必要な理由」の3行が無い Issue には当てない**
- **Issue の出どころで区別しない。** `issue:decided` 付きの Issue にも、`/to-issues` 由来の Issue にも同じように当てる

## 新設を含む方針の縮小

**既定は「作らない」。** 対応方針が次のどれかを含むなら、GO を出す前に必ず「これより少ない手数・小さい仕組みで同じ効果を出せないか」を1つ挙げる（`docs/policy/refined-engineer-judgment-principles.md`「YAGNI——必要になるまで作らない」「Less is more——少ないほど豊か」）。挙げられなかったときだけ非該当にする。

- **新しいファイルを作る**：既存ファイルへの追記で足りないか
- **新しいコマンド・ジョブを足す**：既存のコマンド・ジョブに検査を1つ足せないか
- **新しい依存を足す**：標準機能・既存の依存で書けないか

「将来要るかもしれない」は新設の理由にならない。書いたものは以後ずっと読み・直し・壊さないよう守るコストを生む（コードは負債）。

**ただし機械ゲート化そのものを否定してはならない。** 同じ原則集は「機械が合否を出せる決まりを文章で守らせるな」とも定めている。落とすのは作る必要が薄いものであって、**文章で守らせている決まりを機械へ移す提案は通す側**である。
