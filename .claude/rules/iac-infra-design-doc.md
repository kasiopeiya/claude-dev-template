# インフラ設計書・IaC 設計書の必須セクション

インフラ設計書・IaC 設計書に何を書き何を書かないか（コードが最大の SSoT・2文書の分け方）は [iac-infra-design-doc-policy.md](../../docs/policy/iac-infra-design-doc-policy.md) が定める。ここでは、それを踏まえた**必須セクションとその書き方（How）**だけを定める。基本方針の書式・見出しの並び・設計意図トグルは、設計書全般の Rule [design-doc.md](design-doc.md) に従う。

## 対象読者

AIエージェントが、インフラ設計書・IaC 設計書を書く・レビューし、どのセクションをどちらの文書に置くか、該当が無いときどう閉じるかに迷ったとき。

## 必須セクション

両設計書は次のセクションを持つ。**見出しはすべて置き、消さない。** 該当が無いセクションは、「該当が無いときに書くこと」列の中身を本文に書いて閉じる（空欄で放置しない。未検討と対象外を読者が区別できなくなる）。

- **置き場**：そのセクションを持つ文書。「両方」は、各文書が自分の領域の分だけを書く
- **—**：下位の節を束ねる親の節。親は「なし」で閉じず、下位の節をそれぞれ閉じる
- **なしにしない**：どのシステムにも必ずある。書けないなら未検討である

- ✅ `### スタック関係図` の本文に「単一スタック。〇〇のため分割しない」と書く
- ❌ 見出しだけ置いて本文を空にする／親の `## 前提と制約` に「なし」とだけ書き、下位の小節を置かない／「なしにしない」の `## IaC 管理方針` を「なし」で閉じる

`##` の並びは次のとおり。design-doc.md の「構成図」に当たるのは、インフラ設計書はアーキテクチャ概要、IaC 設計書は IaC 管理方針とスタック設計である。下の表の行の順は、この並びを縛らない。

- インフラ設計書：基本方針 → アーキテクチャ概要 → 前提と制約 → 運用監視
- IaC 設計書：基本方針 → IaC 管理方針 → スタック設計 → 前提と制約 → 命名規約

| セクション                 | 置き場   | 何を書くか（コードから読めないこと）                                                            | 該当が無いときに書くこと                         |
| -------------------------- | -------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `## 基本方針`              | 両方     | 冒頭に置く。書式は design-doc.md                                                                | なしにしない                                     |
| `## アーキテクチャ概要`    | インフラ | 下位の節を束ねる                                                                                | —                                                |
| `### 全体インフラ構成図`   | インフラ | システム全体の主要リソースと接続                                                                | なしにしない                                     |
| `### アカウントと環境構成` | インフラ | AWS アカウントと環境（dev/stg/prd 等）の関係（1アカウントに同居させるか）と、環境間の主要な違い | 単一アカウント・単一環境であることと理由         |
| `### ネットワーク構成図`   | インフラ | ネットワーク境界（下記）                                                                        | VPC も外部からの入口も無いことと理由             |
| `## 運用監視`              | インフラ | 監視・ログ・トレースの全体像の図                                                                | なしにしない（下記）                             |
| `## IaC 管理方針`          | IaC      | どこまでを IaC で管理し、手動変更をどう扱うか（例：手動変更は禁止）                             | なしにしない                                     |
| `### 手動作成リソース一覧` | IaC      | IaC 管理外のリソースの表                                                                        | 「なし」と、全リソースが IaC 管理下であること    |
| `## スタック設計`          | IaC      | 下位の節を束ねる                                                                                | —                                                |
| `### スタック関係図`       | IaC      | スタックの依存関係と参照方式（クロススタック参照など）                                          | 単一スタックであることと理由                     |
| `### 環境差分の実装設計`   | IaC      | 環境差分をコード上でどう表現しているか（図）と、その理由                                        | 単一環境であること（理由はインフラ設計書が持つ） |
| `## 前提と制約`            | 両方     | 変更しようとする人への警告。下位の小節に分ける                                                  | —                                                |
| `### 技術的制約`           | 両方     | 触ると壊れる前提・やらないと決めたこと・受け入れた不便の表                                      | 「なし」と理由                                   |
| `### 組織の制約`           | 両方     | 組織が課す制約（下記）                                                                          | —                                                |
| `#### タグ規則`            | IaC      | 組織が課すタグ付けの規約                                                                        | 「なし」と理由                                   |
| `#### その他の制約`        | IaC      | 暗号化要件（例：KMS 必須）・リージョン制約など                                                  | 「なし」と理由                                   |
| `## 命名規約`              | IaC      | 組織が課した規約も、自分たちで決めた規約も集める                                                | —                                                |
| `### リソース命名`         | IaC      | リソースに名前を付けるかどうかの方針と理由。組織が課す規約があればそれも                        | なしにしない                                     |
| `### スタック命名`         | IaC      | プレフィックス設計とその理由（デプロイ対象の選択などに使う）                                    | 規約が無いことと理由                             |

- **ネットワーク構成図**：VPC があれば VPC・サブネット・VPC Endpoint などの境界を描く。無ければ、外部から到達できる入口と、直接には到達させないリソースの境界を描く
- **運用監視**：監視項目・アラームの選び方は [monitoring-policy](../../docs/policy/monitoring-policy.md) が持つので、説明し直さない。別の設計書に切り出しても節は消さず、参照先を書いて閉じる
- **組織の制約**：IaC 設計書は下位の `####` 小節に分け、それぞれを閉じる。インフラ設計書は小節を持たず、IaC 設計書への参照だけを書いて閉じる（IaC 設計書側が「なし」でも同じ）

## 命名規約は、規約に理由を添えて書く

命名の型はプロジェクトごとに異なるので、この Rule では型を1つに決めない。

- ✅ スタック名を `{システム}-{環境}-{ステート}-{任意}-stack` とし、ステートを入れるのはデプロイ時にステートフルなスタックだけを選べるようにするため、と書く
- ❌ 規約だけを書いて理由が無い／実在のスタック名を全部並べる（コードを読めば分かる）

## スタック関係図には、スタックの中身を描かない

中身のリソースを描くと、全体インフラ構成図と同じ情報を持つ2枚目の図になる。リソースを1つ足すたびにこの図も直すことになり、必ず腐る。リソースの接続は全体インフラ構成図が持つ。

- ✅ スタックを箱にし、矢印に参照方式（クロススタック参照など）を添える
- ❌ 各スタックの箱の中に Lambda・DynamoDB などのリソースを描く

## 環境差分の実装設計は、判断軸をどう適用したかを書く

環境差分を**どう出すか（判断軸）**は [cdk-design-policy](../../docs/policy/cdk-design-policy.md) の領分である（Stack 内で分岐させず、値は設定へ・構造は Builder 層へ寄せる）。

- ✅ 値を `parameter.ts` に集約し、StackBuilder 経由で Stack へ渡す図に「Stack 内部に環境分岐を作らないため」と添える
- ❌ cdk-design-policy の判断軸を説明し直す／環境ごとの具体値（インスタンスサイズ等）を並べる
