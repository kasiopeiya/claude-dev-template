# 手順書の書き方

手段・実行環境の選択と優先順位（CLI最優先・画面ショット回避・実行環境の固定・具体コマンドのハードコード可）は [runbook-policy.md](../../docs/policy/runbook-policy.md) が定める。ここでは、それを踏まえた**書き方（How）**だけを定める。

## 対象読者

AIエージェントが、手順書（`docs/runbook/` 配下）を書く・レビューし、可変部の書き方・ステップの割り方・前提条件や検証方法の書き方に迷ったとき。

> [!NOTE]
> 見出し末尾の（→〇〇）は、runbook-policy.md が挙げる再現性の条件のうち、その書き方が担保するものを指す。

## コピペでそのまま動く形にする（→一意性・持続性）

可変部は `<...>` で明示し、固定部と混ぜない。固定部（CLI名・サブコマンドなど）は具体的に書き、`<...>` は環境やリソースごとに変わる値だけに使う。

```bash
# ✅ 可変部を明示。固定部はそのまま動く
aws s3 cp ./asset/init.sql s3://<bucket-name>/init.sql
```

- ❌ NG：`aws s3 cp ./asset/my-bucket-dev/init.sql my-bucket-dev/init.sql`（バケット名を固定部に埋め込む）
- ✅ OK：上記の例（バケット名だけを `<bucket-name>` に外出しする）

## 1ステップ＝1アクション、番号付きで順序を固定する（→一意性）

手順書は順序が命。1ステップに複数操作を詰めると、どこで失敗したか分からず再現性が崩れる。番号付きリストで順序を固定し、1ステップ＝1アクションに保つ。

- ❌ NG：バケットを作成し、ポリシーを付与してからファイルを置く
- ✅ OK：1. バケットを作成する → 2. ポリシーを付与する → 3. ファイルを置く

## 前提条件を冒頭に明示する（→完全性）

実行前に揃っていなければならないもの（権限・ツール・事前状態・対象環境）を冒頭にまとめる。前提が抜けると読者は途中で詰まる。

<details>
<summary>前提条件に書く項目の例</summary>

- 必要な権限・ロール（例：dev環境への書き込み権限）
- 必要なツールとバージョン（例：プロジェクト指定のCLI）
- 事前に完了していること（例：基盤リソースが構築済み）
- 対象環境（例：dev のみ。本番では実行しない）

</details>

## 各ステップに「期待される結果・確認方法」を添える（→検証可能性）

各ステップの後、正しく進んでいるかを読者自身が判定できるようにする。これが無いと、読者は誤った状態のまま先へ進むか、不安で止まる。

```bash
aws ecs describe-services --cluster <cluster-name> --services worker --query 'services[0].status' --output text
# 期待される結果: INACTIVE が返れば停止完了
```

## 予期される失敗と対応策を添える（→適応可能性）

手順どおりに進めても失敗は起きる。**よくある失敗**（権限不足・リソース未作成・バージョン不一致など）と、その見分け方・対応策を表で添える。これが無いと、読者は失敗した瞬間に手が止まり、著者不在では回復できない（再現性が切れる）。

「期待される結果・確認方法」が正常に進んだ確認なら、この節は異常時の回復——両者は対になる。

| 症状（返るエラー等）  | 原因                 | 対応                                                 |
| --------------------- | -------------------- | ---------------------------------------------------- |
| `AccessDenied` が返る | 実行ロールの権限不足 | 前提条件の権限を確認し、不足していれば付与を依頼する |
| `NoSuchBucket` が返る | 基盤リソースが未作成 | 事前手順（基盤構築）が完了しているか確認する         |

書き方の注意:

- **想像で網羅しない。** 公開前の通し検証や実運用で**実際に遭遇した失敗**を蓄積する。上表の症状は分類の例であり、遭遇していない失敗をそのまま書く対象ではない。机上で並べた失敗リストは腐りやすく、当たらない
- **高頻度・高影響に絞る。** すべての失敗を書くと読まれない（シンプルさが優先）
- **1件も遭遇していないときは、表を置かず節ごと省く。** 実運用で失敗に遭遇した時点で足す

## 見出し・トピックセンテンスに要点を置く（→一意性）

読者は見出しと冒頭1〜2文しか読まない。見出しだけで「このセクションで何を実行するか」が分かるようにする。

- ❌ NG：`## 手順3`
- ✅ OK：`## DB を初期化する`
