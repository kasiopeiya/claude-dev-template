# レビュー系 agent の共通規約

レビュー系 agent（`actions-reviewer-agent`・`architecture-reviewer-agent`・`cdk-reviewer-agent`・`code-reviewer-agent`・`doc-reviewer-agent`・`requirements-reviewer-agent`）に共通する、入力の検証・差分の判定・判定の定義・出力形式の約束を定める。レンズの一覧と担当観点、観点ごとの手順は各 agent の定義が正典で、ここには書かない。

以下の「観点一覧」は、各 agent の定義が判定基準として指す `references/review-criteria.md` をいう。`requirements-reviewer-agent` は、要件定義書のポリシーの「レビューチェックリスト」を観点一覧、NG サインを「違反と判定する条件」、Phase 4 の重大度の当て方を「severity の決め方」と読み替える。

## 対象読者

これらの agent が、起動後の最初の手順でこの文書を読む。共通の約束を変える人間・AI は、ここだけを直す。

## 置き場を選んだ理由

これらの agent を呼ぶ Skill は agent ごとに分かれ（`/actions-review` から `/requirements-review` まで）、共通の持ち主になる Skill が無い。そこで [policy-driven-development-policy](../../docs/policy/policy-driven-development-policy.md)「パスで言えない How は、その行為を担う Skill に置くか、Skill から直接リンクで読ませる Rule にする」に従い、`.claude/rule-bodies/` に置く。`.claude/rules/` には動かさない（毎回全文が読み込まれる）。review-subagent-lens-policy にも書かない（Policy は「どれを選ぶか」を書く場所で、選んだ後の How は Rule に置く。ADR-014）。

## 入力の検証

> [!IMPORTANT]
> **（AI・必須）** 禁止事項: Glob でプロジェクト全体のファイル一覧を取得してはならない。ユーザーにファイルの選択を求めてはならない。

agent に固有の入力（記載段階・新しい組の一覧など）の扱いは、各 agent の定義に書く。

| 起きたこと                                                                      | 扱い                                                                     |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| レンズ名が渡されていない、または agent の定義の「レンズ一覧と担当観点」に無い   | 「レンズ名が指定されていません」と表示して終了                           |
| 対象（ファイル・文書・設計書・ソースディレクトリ）が渡されていない、または 0 件 | 「対象が指定されていません」と表示して終了                               |
| 対象が存在しない                                                                | 「指定されたファイルが見つかりません: <path>」と表示して終了             |
| 観点一覧・ポリシー・ルールファイルが読めない                                    | 読めなかった旨を明記し、その観点を未判定として報告する（黙って省かない） |
| git リポジトリでない                                                            | git 履歴の取得をスキップし、レビューは続行                               |

## 差分の判定

判定範囲が差分の対象に使う。差分の取り方は各 agent の定義が決める。未追跡の新規ファイルは差分が無く、全行が追加行である。以下の「欠陥」は、観点が違反とするものを指す。

- 今回の差分が生んだ欠陥だけを判定する。差分の外に前からある欠陥は、探さない
- 差分の外の行で壊れる欠陥も、原因が差分なら指摘する（例は各 agent の定義に置く）
- 書き換えた行は、変更前の行（`-`）に同じ欠陥が無いときだけ指摘する
- 差分が生んだ欠陥が無い観点は **準拠** とする（対象外に当たる観点は、「判定の定義」のとおり対象外とする）
- 指摘の引用は、原因になった差分の行にする。削除した行はファイルに残らないので、差分の `-` の行から引用する

## 判定の定義

担当する観点の全行を、1行ずつ **準拠／違反／対象外／未判定** で判定する。判定を飛ばした行を残さない。飛ばした観点はレポートから消え、見ていないことに誰も気づけないためである。

- **違反**：観点の「違反と判定する条件」に当たる箇所を引用できたとき。違反ごとに指摘を1件出し、観点一覧「severity の決め方」で severity を付ける
- **準拠**：その観点を探した結果、条件に当たる箇所が無かったとき。「おそらく問題ない」という印象で付けない
- **対象外**：観点の注記が対象外と定める場合、または観点が見る対象が1つも無い場合。使える場面は、観点一覧と各 agent の定義が決める
- **未判定**：観点一覧・ポリシー・ルールが読めず、判定できなかった行にだけ使い、理由を添える。各 agent の定義が足す場合を除く
- **解釈が分かれるとき**：引用は取れるが読み方で問題かどうかが変わるときは、違反として出してよい。指摘に「解釈が分かれる（引用箇所を〇〇と読むなら違反）」と明記する。**引用そのものが取れない「確認が取れない」は違反にしない**。それは対象の欠陥ではなく、こちらが読み切れていないだけかもしれない

**引用の書式**：指摘には、対象からコピーした原文・コード1〜3行を添える。記述が有ることではなく**無いこと**が問題のときは、欠落を確認した範囲（関数全体・該当節など）を引用し、「この範囲に〇〇が無い」と書く。原文も欠落確認範囲も示せない指摘は出さない。判定範囲が差分のときは、「差分の判定」に従って原因になった差分の行を引用する（削除した行が「無いこと」の原因なら、差分の `-` の行を引用し、あわせて欠落を確認した範囲を示す）。引用の長さや個数を変える agent は、その定義に書く。

## 出力形式

見出しの構成は agent ごとに違う。次の3つの部品は、`requirements-reviewer-agent` を除く agent が同じ形で出す。`requirements-reviewer-agent` は、「判定した観点」だけをこの形で出し、照合結果の表と指摘の一覧は自分の定義の書式で出す。

**「判定した観点」**：このレンズが判定した観点名を、観点一覧の表記のまま列挙する。必ず出す。揃わないと、統合する側は**レンズの割り方に穴があっても気づけない**。判定できなかった観点は、表の行に理由を添えて残し、黙って落とさない。

**「観点ごとの判定」の表**：担当する観点1つにつき1行。

```markdown
| 観点             | 判定                            | 指摘の数                     |
| ---------------- | ------------------------------- | ---------------------------- |
| <担当する観点名> | <準拠 / 違反 / 対象外 / 未判定> | <違反なら件数、それ以外は -> |
```

**「指摘」の1件**：1行目は次の形にし、その下に各 agent が自分の欄（場所・引用・提案・理由など）を足す。

```markdown
- **<観点名>** [<Critical / High / Medium>]: <具体的な問題の説明>
```

フォーマットに無い欄（点数・良い点・総評など）は足さない。

**出力前の自己点検（必須）**：agent の定義の「レンズ一覧と担当観点」から自分の担当観点を数え、その数だけ「判定した観点」に列挙し、表にも同じ数だけ行があるか確かめる。漏れていたら、出す前に追加する。担当観点を書き出さずに記憶だけで進めると、手順の後半にある観点ほど脱落しやすい。`requirements-reviewer-agent` には当てない（担当行の漏れは、自分の定義の「担当行を飛ばしてはならない」で防ぐ）。
