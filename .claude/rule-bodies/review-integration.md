# レビュー結果を統合する共通手順

レビュー系 Skill が、各レンズのレポートを1つに統合するときの手順（How）。レンズを並列に起動して結果を統合するレビュー系 Skill が、統合の前にこのファイルを Read して従う。統合はメインセッションで行い、判断は手順4の食い違いの裁定だけにする（[review-subagent-lens-policy](../../docs/policy/review-subagent-lens-policy.md)「統合はメインセッションで行い、判断は食い違いの裁定だけにする」）。

## 置き場を選んだ理由

この手順を使う Skill は複数あり、持ち主の Skill が1つに決まらない。そのため、[policy-driven-development-policy](../../docs/policy/policy-driven-development-policy.md) の「パスで言えない How は、…Skill から直接リンクで読ませる Rule にする」に従い、Rule にする。置き場は同ポリシーの「Skill などから直接リンクで読ませる Rule は…`.claude/rule-bodies/` に置く」が決めている。`.claude/rules/` に置くと、Skill のリンクと無関係に毎回全文が読み込まれるためである。

## 対象読者

統合を担うレビュー系 Skill を実行していて、レンズのレポートをどの順に整えてよいか、食い違いをどう扱うか、合否をどう数えるかに迷った AI エージェント。

## 共通手順

次の順で行う。Skill ごとに違う内容（数える範囲・足す手順など）は、その Skill の `SKILL.md` に書いてある。`SKILL.md` に「手順Nに足す」とあれば、この手順Nに重ねて行う（例：「手順1に足す：2箇所を引用する指摘は、少なくとも一方が差分の行にあれば残す」とあれば、手順1で落とす条件に当たっても、その指摘は残す）。`SKILL.md` に「手順Nの代わり」とあれば、そこに書かれた部分だけを置き換え、ほかの文と例はそのまま使う。

1. **引用の無い指摘を落とす。** 判定範囲が差分のときは、引用が Phase 1 で取った差分の追加行（`+`）・削除行（`-`）のどれにも無い指摘も落とす。範囲の制限をレンズの自己申告に頼らないためである。
2. **同じ観点で引用が重なる指摘だけを1件にまとめる。**
   - まとめる例：2つのレンズが、同じ観点で同じ行を引いている（片方の引用がもう片方を含む場合も同じ）
   - まとめない例：同じ行を引いていても、観点が違う（例：「明確性」と「目的適合」）
   - まとめた後：1件の severity は、元の指摘のうち最も重いものを採る。修正案（レンズの書式で「改善案」「提案」と呼ぶものを含む）が違うときは併記する（逆向きなら手順4で裁定する）。例：一方が High、他方が Medium なら、High の1件にして両方の修正案を書く
3. **severity を変えない。** レンズの判定を尊重する。
4. **修正案が食い違ったら裁定する。** 同じ箇所に別々のレンズが逆向きの修正案を出したら、ポリシーの条文（該当が無ければ `docs/policy/refined-engineer-judgment-principles.md`）を引用して一方を採り、捨てた案と根拠を添える。迷ったら AI が決める。
   - 逆向きの例：同じ行に、あるレンズが「この記述を削る」、別のレンズが「この記述に条件を書き足す」と出した
   - 逆向きでない例：同じ行に、2つのレンズがそれぞれ別の語の言い換えを出した（両方とも適用できる）
   - 例外：どちらを採っても人間が決めるべき条件「要件／プロダクト方針が変わる」に当たるとき、またはどちらかを採ると人間が決めるべき条件「不可逆・外部に出る」に当たるときだけは裁定しない（[issue-policy](../../docs/policy/issue-policy.md)「人間が決めるべき Issue の条件」。ほかの条件には広げない）。その食い違い1件を、[`/quick-issue`](../skills/quick-issue/SKILL.md) の書式でラベル `needs-human-decision` を付けて `gh issue create` で起票し、ほかの指摘の処理は続ける。起票の前後は [`/link-root-issue`](../skills/link-root-issue/SKILL.md) の SKILL.md を Read して従う。段番号は `/quick-issue` の「段番号の振り方」に従う。本文には、食い違った各指摘の観点名と引用を書き写す。
   - 同じワークフロー（レビューと修正を繰り返す1回の流れ。`/auto-dev` など）の前回のレビューでこの手順により起票した Issue と同じ指摘なら、起票せず、既存の Issue 番号のまま起票済みとして扱う（手順7で引く対象にも含める）。同じ指摘かどうかは [ai-review-gate-policy](../../docs/policy/ai-review-gate-policy.md) の「再レビューで同じ指摘が出たら、既存の Issue 番号で数える」で決める。
5. **「次のステップ」の優先度は severity から機械的に決める。** Critical→高・High→中・Medium→低。
6. **観点一覧の行名で穴を照合する。** 実行中の Skill の `references/review-criteria.md`（例：`/doc-review` なら `.claude/skills/doc-review/references/review-criteria.md`）の観点一覧の全行を、どれかのレンズの「判定した観点」と突き合わせる。判定済みとみなすのは、各レンズの「判定した観点」に名前が挙がっている観点だけ。無ければ「未判定」として観点名をそのまま報告する。**これはレビュー対象の欠陥ではなく、レンズの割り方の穴である。** 黙って埋めない。
7. **合否を判定する。** ai-review-gate-policy の合格条件（残してよい例外以外の Critical が0件）で決める。Critical の合計から、手順4で `needs-human-decision` として起票した食い違いに含まれる Critical 指摘の件数を引く（起票した食い違いの件数ではない）。残りが0件なら ✅ 合格、1件以上なら 🚫 要修正とする。起票した Issue 番号は「Issue にして残す Critical」に書く。
