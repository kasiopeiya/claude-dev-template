# Issue を更新する共通手順

既存の GitHub Issue を更新するときの手順（How）。Issue の本文・タイトル・ラベル・コメントを書き換える Skill が、書き換える前にこのファイルを Read して従う。

## 置き場を選んだ理由

この手順を使う Skill は複数あり、持ち主の Skill が1つに決まらない。そのため、[policy-driven-development-policy](../../docs/policy/policy-driven-development-policy.md) の「パスで言えない How は、…Skill から直接リンクで読ませる Rule にする」に従い、Rule にする。置き場は同ポリシーの「Skill などから直接リンクで読ませる Rule は…`.claude/rule-bodies/` に置く」が決めている。`.claude/rules/` に置くと、Skill のリンクと無関係に毎回全文が読み込まれるためである。

## 対象読者

Issue を更新する Skill を実行していて、`gh` を並列で叩いてよいか、本文をどう取得して書き戻すか、書き戻す前に何を確かめるかに迷った AI エージェント。

## `gh` の叩き方

**`gh` を並列で叩かない。** 1件ずつ順に処理する。同じ Issue へ本文・タイトル・ラベル・コメントの更新が同時に飛ぶと、あとから投げたほうが前の更新を消す。

- ❌ 1つの応答で `gh issue edit` と `gh issue comment` を、依存が無いからとまとめて呼ぶ。`&` や `xargs -P` で同時に走らせる
- ✅ 1つの `gh` の結果を受け取ってから、次の `gh` を呼ぶ

## 本文を取得して書き戻す

本文は、取得 → 差し替え → 書き戻しの順で変える。`<スクラッチパッド>` はセッションが使える一時ファイルの置き場、`<番号>` は本文を書き換える Issue の番号である（子 Issue の本文を書き換えるなら、子の番号）。

1. 取得する。

   ```bash
   gh issue view <番号> --json body --jq .body > <スクラッチパッド>/issue-<番号>.md
   ```

2. 書き出したファイルを Read し、Edit で該当セクションだけを差し替える。**本文全体を書き直さない。** 全体を書き直すと、差し替えない節まで書き直すことになり、原文が書き換わって失われる。
3. 書き戻す。

   ```bash
   gh issue edit <番号> --body-file <スクラッチパッド>/issue-<番号>.md
   ```

本文はファイルを経由して渡す。`gh issue edit <番号> --body "$UPDATED_BODY"` のようにシェルの変数で渡し、`echo "$BODY" | sed …` で書き換えると、`\` などの解釈で本文が変わりうる。何を変えたかを Read で確かめることもできない。

チェックボックスを `- [ ]` から `- [x]` に変えるだけのときも、同じ手順にする。該当する行を Edit で書き換える。該当する行が無ければ、書き戻さずに次へ進む（エラーにしない）。

## 割り込みを確かめる（取得と書き戻しのあいだに別の処理をはさむとき）

取得から書き戻しまでのあいだに、人間の応答を待つ・ほかの Issue を処理する・ほかの Issue の本文を読むなど、別の処理をはさむときは必ず行う。取得 → Edit → 書き戻しを続けて行い、はさむ処理が無いときだけ省いてよい。そのあいだに別セッションが本文を変えていると、そのまま書き戻せば他セッションの編集が消える。

1. 取得した直後に、原本の写しを作る。

   ```bash
   cp <スクラッチパッド>/issue-<番号>.md <スクラッチパッド>/issue-<番号>.orig.md
   ```

2. 書き戻す直前に、本文を引き直して原本と比べる。

   ```bash
   gh issue view <番号> --json body --jq .body | diff - <スクラッチパッド>/issue-<番号>.orig.md
   ```

3. 差分が出たら、その Issue の更新（本文・ラベル・コメント）をすべてやめ、別セッションが本文を変えた事実を報告する。複数の Issue を処理しているなら、ほかの Issue は続ける。
